# @better-compute/provider-aws

The Amazon EC2 provider for better-compute. EC2 instances (GPU instances included) become the instances of provider pools, with the same API, reconcilers and guarantees as the other cloud providers: offers, create, get, delete, power, reinstall, list, and discovery and attach; managed Kubernetes runs on EKS. It calls AWS over plain `fetch` through [`@better-compute/aws-core`](../aws-core) (SigV4, the EC2 protocol, credentials); there is no AWS SDK.

It is not in the `better-compute` umbrella: install it where you use it.

```sh
pnpm add @better-compute/provider-aws
```

```ts
import { vps } from '@better-compute/vps';
import { aws } from '@better-compute/provider-aws';

vps({ providers: [aws] });
```

`aws` is `awsProvider()` with default options. `awsProvider({ fetch, endpoints, credentials, externalIdPrefix, platformAccounts, rateLimit, consistencyWindowMs, ssmImagePrefixes, imageOwners, kubeTransport, platformRoleArn })` takes host options: `credentials` is the host's own AWS identity (default: the ambient chain of environment, web identity, container and IMDSv2 credentials), `platformAccounts` lists the AWS account ids a tenant's role may never be in, `endpoints` (`ec2`, `sts`, `ssm`, `servicequotas`, `pricing`, `eks`) is for emulators and VPC endpoints, `ssmImagePrefixes` lists private SSM parameter prefixes raw images may name, and `imageOwners` lists the AWS account ids whose private AMIs raw images may name (see Images). None of them come from account config.

## Accounts

One provider account is one AWS account in one region. A fleet in several regions is several accounts with the same credentials.

| Field                        | Default    | Meaning                                                                                                                                         |
| ---------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `region`                     | (required) | The AWS region, `us-east-1`. Checked against the region grammar: it is the only config text that reaches a host name.                           |
| `zones`                      | (required) | Availability Zone names as this account sees them (`us-east-1a`), or Local Zones (`us-west-2-lax-1a`). Offers and creates are limited to these. |
| `credentials`                | –          | A secret reference to `{ "accessKeyId", "secretAccessKey" }`. Allowed, but a role is better.                                                    |
| `assumeRoleArn`              | –          | The IAM role to assume, in the region's partition.                                                                                              |
| `webIdentityRoleArn`         | –          | Keyless: the IAM role the account's own workload identity assumes (AssumeRoleWithWebIdentity). Excludes `credentials` and `assumeRoleArn`. |
| `subnetId`                   | –          | The subnet create uses (else the zone's default subnet).                                                                                        |
| `securityGroupIds`           | –          | The security groups create uses.                                                                                                                |
| `instanceProfile`            | –          | The instance profile ARN passed to every `RunInstances` of the account. Never give its role an EKS access entry: see `eksNodeInstanceProfile`. |
| `rootVolumeGiB`              | `100`      | Root EBS volume size (8–16384).                                                                                                                 |
| `rootVolumeType`             | `gp3`      | `gp3`, `gp2` or `io2`.                                                                                                                          |
| `kmsKeyId`                   | –          | The KMS key for EBS encryption (else the account's default EBS key).                                                                            |
| `metadataHopLimit`           | `1`        | The IMDSv2 hop limit (2 when containers on the instance need IMDS).                                                                             |
| `associatePublicIp`          | `true`     | Give instances a public IPv4 address (with a subnet).                                                                                           |
| `discoverTag`                | –          | `key=value`: discovery yields only instances carrying this tag.                                                                                 |
| `ipamPoolId`                 | –          | Networks: allocate each VPC range from this Amazon VPC IPAM pool (the network's `cidr` gives the size).                                         |
| `securityGroupsPerInterface` | `5`        | Networks: the account's security groups per network interface quota; network tags past it are `QUOTA_EXCEEDED`.                                 |
| `spot`                       | `false`    | Offer and launch Spot capacity (`<zone>/<type>:spot`).                                                                                          |
| `quotas`                     | `true`     | Cap offers at the EC2 vCPU quota headroom (Service Quotas).                                                                                     |
| `pricing`                    | `off`      | `off`, `on-demand` (the AWS Price List) or `all` (adds Spot prices).                                                                            |
| `allowPurchases`             | `false`    | Allow buying capacity (Capacity Blocks, new ODCRs) in this platform account. Spends money.                                                      |
| `efa`                        | `off`      | `auto`: an EFA-capable type launches with one EFA interface per network card (needs `subnetId` or a network). See [ML fabric](#ml-fabric). |
| `eventQueueUrl`              | –          | The SQS intake queue the account's EventBridge rules feed (`aws event-rules`), in this account and region. See [Events](#events). |
| `eventSources`               | `aws.ec2`, `aws.health` | The EventBridge sources taken from the queue; `aws.guardduty` is opt-in. Anything else is dropped. |
| `costs`                      | –          | `region` or `account`: read this account's costs from Cost Explorer (see Costs). Absent or `off`: none. |

`awsConfig.parse` checks field shapes (`INVALID_INPUT`); the provider checks the region, that every zone is in it, and the role ARN's shape and partition (`INVALID_CONFIG`), so `providerAccounts.create` refuses a bad account before it is stored.

## Credentials

| Account                | `credentials` | `assumeRoleArn` | Signs as                                                |
| ---------------------- | ------------- | --------------- | ------------------------------------------------------- |
| platform (root tenant) | set           | –               | the static key                                          |
| platform               | –             | –               | the host's ambient identity                             |
| platform               | any           | set             | AssumeRole from one of the above                        |
| tenant                 | set           | –               | the static key                                          |
| tenant                 | set           | set             | AssumeRole from the static key                          |
| tenant                 | –             | set             | AssumeRole from the platform identity                   |
| tenant                 | –             | –               | refused (`INVALID_CONFIG`, reason `ambientCredentials`) |
| any                    | –             | – (`webIdentityRoleArn` set) | AssumeRoleWithWebIdentity with the account's workload identity |

Ambient credentials are the control plane's own identity, so only platform accounts may use them (ruling F1).

Every AssumeRole sends the ExternalId `<externalIdPrefix>:<providerAccountId>` (`better-compute:pa_…` by default). The platform assigns it; there is no config field for it, so a tenant naming another tenant's role gets `AccessDenied` from STS. A tenant role in a `platformAccounts` account is refused when the account is stored. Before the first EC2 call the provider checks, once, that the role is not in the platform identity's own account and that the assumed identity is the role's account (`ACCESS_DENIED`, reasons `platform-account-role` and `assumed-identity-mismatch`).

To onboard a tenant's AWS account:

1. Pick the role's name and create the provider account with `assumeRoleArn` set to its ARN (`arn:aws:iam::<tenant account>:role/<name>`). Storing the account makes no AWS call, so the role need not exist yet; the call returns the account's id (`pa_…`).
2. Create that role in the tenant's account with the permissions policy from `better-compute aws iam-policy` (narrow it with `--region`, `--account` and `--discover-tag`; with a customer-managed `kmsKeyId`, add `--kms-key <key ARN>` for the EBS grants on that key, through EC2 only). Root-volume replacement (reinstall) also names its new task, volume, snapshot and image, which the policy allows for that action alone; the instance itself still needs `better-compute:instance`. The KMS and reinstall resource lists follow the AWS documentation and are confirmed by the live suite.
3. Give it the trust policy from `better-compute aws trust-policy --platform-principal <the control plane's role ARN> --external-id better-compute:<the id from step 1>`.
4. The account's first EC2 call (its first reconcile) assumes the role and runs the identity checks above; it fails with `ACCESS_DENIED` until the role and its trust policy exist.

`providerAccounts.get` shows what the tenant still has to set up as the account's `onboarding`: `mode`
(`assume-role`, `web-identity`, `access-key` or `ambient`), and for a role the `externalId` and, when the host
passes `awsProvider({ platformPrincipalArn })`, the principal to trust. That option is display only and never
derived (reading the host's identity would be a network call on every read); a value that is not an IAM role or
user ARN fails `awsProvider` (`INVALID_CONFIG`, `platformPrincipalArn`), and without it tenants see the ExternalId
only and must get the principal from the operator. A keyless (`web-identity`) account shows the `subject` and
`audience` its role trusts and, when the host configures `pki.workloadIssuer`, the `issuer` URL that
`aws onboarding-template --issuer` takes. `better-compute aws onboarding-template
--account <pa_…> --platform-principal <arn>` renders steps 2 and 3 as one CloudFormation template (the role, its
trust and the ABAC policy; the same `--region`, `--instance-profile`, `--kms-key` and `--discover-tag` flags).

### Keyless accounts (workload identity federation)

As with provider-gcp's `federationAudience`, a tenant's AWS account can sign in with no key and without the
platform's own AWS identity: set `webIdentityRoleArn`. vps fixes the account's subject,
`compute-account:<tenantId>/aws/<name>`; the provider mints a token for it from the host's workload issuer
(`ComputeOptions.pki.workloadIssuer`, audience `sts.amazonaws.com`) and exchanges it, unsigned, with
`AssumeRoleWithWebIdentity`. Without an issuer the account is `INVALID_CONFIG` (`noWorkloadIssuer`); with
`credentials` or `assumeRoleArn` too, `webIdentityExclusive`; a tenant role in a `platformAccounts` account,
`platform-account-role`.

Before such an account is stored, `checkAccount` proves the role trusts exactly that subject: the account's own
subject must be accepted (`federationRefused`) as the role's account (`assumed-identity-mismatch`); then a
stranger's probe (another tenant, the same name) and a sibling's (this tenant, another name) must be refused by the
trust condition, `AccessDenied` (`federationTrustsAnySubject` if accepted); and it must read EC2 (`ec2Access`). A
probe answered with any other STS error, such as `InvalidIdentityToken` when STS cannot fetch the issuer's keys, is
`UNAVAILABLE` (`federationProbeInconclusive`), never a pass. That, throttling, 5xx and timeouts (`checkTimeoutMs`,
default 10 s) store nothing and a retry runs the check again.

`better-compute aws onboarding-template --issuer <issuer URL> --tenant <tenantId> --name <account name>` renders
the IAM OIDC provider for the issuer (client id `sts.amazonaws.com`; `--oidc-provider-arn` reuses one) and the role
trusting exactly that subject, with the ABAC policy.

### Workload roles

Instances of a hosted pool can assume an IAM role with no static keys. The pool turns workload identity on
(`policy.workloadIdentity: true`) and lists the roles its instances may name in `policy.workloadRoles.aws` (ARN
globs); an instance names one as `instances.create` `workloadIdentity.awsRoleArn`. vps sends it to the host as
`InstanceSpec.awsRole` while the pool allows it; bcd exchanges the instance's workload token (audience
`sts.amazonaws.com`, subject `t:<tenantId>:instance:<id>`, from the gateway's workload broker, which must list
that audience) for the role's credentials and serves them on the guest's AWS-compatible metadata paths.
`better-compute aws workload-role --tenant <tenantId> --issuer <issuer URL> [--role-name <name>] [--policy-arn <arn>]`
renders the OIDC provider and the role, trusting `aud` `sts.amazonaws.com`, `sub` like `t:<tenantId>:instance:*`
and the session tag `bc-role` equal to the role itself (`aws:RequestTag/bc-role` = its ARN without a path, with
`sts:TagSession` allowed; the `RoleTag` output shows the value).

The workload broker mints a token for `sts.amazonaws.com` (requested, or the issuer's default audience) only for
an instance that names a role its pool still allows (refusal `audience`, reason `aws-role-not-allowed`), decided
before anything is signed, and tags it with that role (`https://aws.amazon.com/tags` `principal_tags.bc-role`).
So a token minted for one workload role assumes no other role of the tenant, even when the guest fetches it
itself from `/latest/identity-token`. A role you write by hand needs the same trust: without the tag condition it
accepts any of the tenant's STS tokens. A role name with a comma cannot be a tag value; the broker refuses such a
role (`aws-role-untaggable`) and `aws workload-role` refuses the name.

When a pool's workload settings change, `pools.update` recomputes the specs of the hosts running its role-bearing
instances at once. Credentials bcd already obtained stay valid until they expire (at most an hour; bcd's cache
renews 5 minutes before expiry).

IAM Roles Anywhere for bcd nodes outside AWS (plan question AQ9) is deferred, as the plan's default: workloads get
AWS credentials only through this web identity exchange.

The commands ship with this package (the CLI never imports providers). Add them to your configuration:

```ts
import {
  awsIamPolicyCommand,
  awsOnboardingTemplateCommand,
  awsTrustPolicyCommand,
  awsWorkloadRoleCommand,
} from '@better-compute/provider-aws';
export const commands = [
  awsIamPolicyCommand(),
  awsTrustPolicyCommand(),
  awsOnboardingTemplateCommand(),
  awsWorkloadRoleCommand(),
];
```

## Tags and the guard

Every instance and root volume better-compute creates (and, on a tenant network, its primary network interface) is tagged `better-compute:managed=true` and `better-compute:instance=<instance id>`, plus `Name` and the instance's labels as `better-compute:<key>` (the ownership tags win). `delete` needs `better-compute:managed=true`; `power` and `reinstall` need `better-compute:instance` (`INVALID_STATE`, reasons `not-managed` and `not-claimed`). The policy from `aws iam-policy` makes AWS enforce the same rules on its side (ABAC): `TerminateInstances` only on instances tagged `better-compute:managed=true`, power and reinstall only on instances tagged `better-compute:instance`, and tag edits after launch only of those two keys (a request must name them, so a `DeleteTags` of every tag is refused). Attach is what writes the ownership tags on an existing instance, so the role can make any instance it may tag deletable: ABAC stops a stray terminate of an untagged instance, not a buggy attach. `--discover-tag key=value` (the account's `discoverTag`) limits attach tag edits, and so everything destructive outside better-compute's own launches, to instances carrying that tag.

## Offers and ids

An offer id is `<zone>/<instanceType>`, as in `us-east-1a/p5.48xlarge`. `listOffers` lists the on-demand types offered in the account's zones, skipping bare metal, with vCPUs, memory and GPUs (NVIDIA H100, H200, B200, A100, L4, L40S, A10G and T4 by name; others are `other`). Every offer carries `arch`. Capacity reservation (`@cr-…`) and Spot (`:spot`) offers are described under [Capacity markets](#capacity-markets). Instance types are cached for a day, offerings and zone ids for an hour. A machine id is the instance id `i-…`; its labels carry `topology.aws/zone-id`.

## Images

An image is an `ami-…` id, a `resolve:ssm:<parameter>` that EC2 resolves at launch, or an alias expanded for the instance type's architecture (Graviton gets arm64):

| Alias              | Public SSM parameter                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------- |
| `ubuntu-24.04`     | `/aws/service/canonical/ubuntu/server/24.04/stable/current/{amd64,arm64}/hvm/ebs-gp3/ami-id`          |
| `ubuntu-22.04`     | `/aws/service/canonical/ubuntu/server/22.04/stable/current/{amd64,arm64}/hvm/ebs-gp2/ami-id`          |
| `al2023`           | `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-{x86_64,arm64}`                       |
| `dlami-gpu`        | `/aws/service/deeplearning/ami/{x86_64,arm64}/base-oss-nvidia-driver-gpu-ubuntu-22.04/latest/ami-id`  |
| `eks-al2023-<k8s>` | `/aws/service/eks/optimized-ami/<k8s>/amazon-linux-2023/{x86_64,arm64}/standard/recommended/image_id` |

For an alias the root device name is known; for a raw `ami-…` it is read with `DescribeImages` (cached a day, with the verdict below). A raw `ami-…` comes from the tenant, and EC2 launches any image the account can see: its own private golden images, and images other accounts shared with it. So a raw AMI is refused (`INVALID_INPUT`, reason `image`, at `create` and `reinstall`) unless it is public, owned by `amazon` or `aws-marketplace`, or owned by an account in the host's `imageOwners`. A raw `resolve:ssm:` image must name a public `/aws/service/` parameter, or one under the host's `ssmImagePrefixes` (`/my/team/`): the image comes from the tenant and EC2 reads the parameter as the account, so other private parameters are refused (`INVALID_INPUT`, reason `image`). A private prefix also needs `ssm:GetParameters` on it in the role's policy: `aws iam-policy` grants `/aws/service/*`, and `--ssm-prefix /my/team/,/other/` adds the host's prefixes. For a raw `resolve:ssm:` parameter the root device cannot be known without reading SSM, so the root volume mapping is left out: the volume then has the AMI's size and type, and is encrypted only if the account encrypts EBS by default. The provider logs this once per image.

## Hardened defaults

- IMDSv2 only (`HttpTokens=required`), hop limit `metadataHopLimit`, instance metadata tags off.
- The root EBS volume is encrypted (the account default key, or `kmsKeyId`) and deleted with the instance.
- An instance-initiated shutdown stops the instance rather than terminating it.

## User data

EC2 takes at most 16 384 bytes of user data. With SSH keys, the user data is a MIME multipart: a `text/cloud-config` part with `ssh_authorized_keys` and the payload. Over 16 384 bytes it is gzipped; still over, `create` refuses it (`INVALID_INPUT`, reason `user-data-too-large`). The packing is byte-for-byte deterministic (the gzip header's time and OS bytes are fixed and the MIME boundary derives from the content), because EC2 refuses a retried `RunInstances` whose parameters differ.

## Creates, reads and deletes

`create` is one `RunInstances` with a `ClientToken` derived from the instance id, so a retried create returns the same instance and a retry with different parameters is `CONFLICT`. It does not wait. EC2 is eventually consistent right after a launch: `get` looks the instance up by id, then by its client token, and reports `pending` for up to `consistencyWindowMs` (2 minutes) so vps never marks a new instance lost. An instance EC2 terminates for capacity or volume limits after accepting it surfaces through `get` as `CAPACITY_UNAVAILABLE` or `QUOTA_EXCEEDED`, which ends the create. `delete` reads the same way (by id, then client token). An instance this client launched inside the window that neither read shows yet is still terminated (RunInstances tagged it managed), and a `TerminateInstances` that does not find it is `UNAVAILABLE` (reason `eventual-consistency`, retried), never success. Otherwise `delete` of a missing, terminating or terminated instance succeeds; termination protection is `INVALID_STATE` (reason `termination-protected`).

`power` maps `on` to `StartInstances`, `graceful-off` and `off` to `StopInstances` (`off` with `Force`), `reset`, `cycle` and `graceful-restart` to `RebootInstances`, and `nmi` to `SendDiagnosticInterrupt`. EC2 refuses a start while an instance is stopping and a stop or reboot while it is pending; `power` reports those states (and an `IncorrectInstanceState` from a state change between its read and its call) as `UNAVAILABLE` (reason `transitional-state`), which the reconciler retries, rather than `INVALID_STATE`, which would fail the instance. `reinstall` replaces the root volume (`CreateReplaceRootVolumeTask`) and does not block. That call takes only an AMI id (`resolve:ssm:` is a launch-time syntax), so an alias or `resolve:ssm:` image is first read with one SSM `GetParameters` as the account (a parameter that does not exist or does not hold an AMI id is `INVALID_INPUT`, reason `image`). Its `ClientToken` covers the instance id, the image and the current root volume id: a retry while the task runs is the same task, and the same reinstall after the volume was replaced is a new one.

## Capacity markets

- **Reservations.** `listReservations` reads On-Demand Capacity Reservations and Capacity Blocks for ML (`DescribeCapacityReservations`): an ODCR is reservation `cr-…`, a block `cb:cr-…`. `active` is `ready`; `scheduled`, `payment-pending`, `assessing` and `delayed` are `scheduled`; `pending` is `creating`; gone and unknown states are left out, and so are reservations create cannot launch into (not Linux/UNIX, dedicated tenancy, or outside the account's zones). A reservation another account shares through RAM is `shared`, its zone resolved from the zone id. Ready reservations are offered as `<zone>/<type>@<cr-id>` with their free slots as `count` (market `reserved` or `capacity-block`), and vps admits creates against them (`claimReservationSlot`). `create` on such an offer reads the reservation first (it must be active and hold that type in that zone), targets it, and adds `MarketType=capacity-block` for a block. Machines report `market` and `reservation`.
- **Spot.** With `spot`, every on-demand offer has a `:spot` twin. A Spot create is a one-time request that terminates on interruption (a shutdown from inside terminates it too). A reclaimed Spot Instance reads as `deleted` with `interruption { kind: 'spot', at, action }`.
- **Quotas.** With `quotas`, offers carry the EC2 vCPU quota headroom of their family as a machine `count` (`GetServiceQuota`; usage is the vCPUs of pending and running instances, Spot against the Spot quota), and an offer with none left is not available. Cached 5 minutes; an unreadable quota leaves `count` unset.
- **Prices.** `pricing: 'on-demand'` reads one region-wide Price List `GetProducts` (Linux, shared tenancy, no pre-installed software), cached a day; `'all'` adds `DescribeSpotPriceHistory` for Spot offers, cached 10 minutes. A failed read leaves prices unset and never fails `listOffers`. GovCloud (`aws-us-gov`) has no Price List API: `on-demand` is refused there (INVALID_CONFIG) and `all` prices Spot offers only.
- **Buying.** `listReservationOfferings` (a read) lists the ODCRs the account could create now and the Capacity Blocks on sale. `purchaseReservation` spends money: it is refused unless `allowPurchases` and the account is a platform account, a Capacity Block is bought only while it is on sale at no more than its listed price (the offering id carries both), and a retry with the same key returns what the first attempt bought (the reservation's `better-compute:purchase` tag, and an ODCR's `ClientToken`). `PurchaseCapacityBlock` has no `ClientToken` and EC2's reads lag, so after an attempt that may have bought (vps passes `uncertainSince`) a retry also looks for the block by type, zone, count, start and creation time, and buys again only once `purchasePropagationMs` (15 min) passed with nothing in sight. Without `allowPurchases` the client has no `purchaseReservation` at all. vps's `providerAccounts.purchaseReservation` is root-only, needs `confirm: true`, and buys exactly once.
- **Policy.** `aws iam-policy` always grants the reservation, offering and Spot price reads, the vCPU quota reads and launches into reservations (any owner's ARN, so RAM-shared ODCRs work with `--account`); `--spot`, `--pricing` and `--allow-purchases` add Spot launches, the Price List and buying (only tagged `better-compute:managed=true`).

The vCPU quota codes beyond standard, G/VT and P (and their Spot twins) are marked _verify_ in `src/markets/quotas.ts`, as are the resource types `PurchaseCapacityBlock` authorizes against.

## Discovery and attach

`discover` yields every instance that is not terminated (only those tagged `discoverTag`, when set). `claim` writes `better-compute:instance` (and `better-compute:managed` when deletion is handed over) and re-reads: EC2 tags have no compare-and-swap, so a re-read naming another instance is a lost race (`CONFLICT`). Tag reads lag behind writes too: a re-read that does not show the tag (or `managed`) yet is `UNAVAILABLE` (reason `tag-propagation`, retried), and so are a `get` right after a claim that does not see the ownership tag yet (vps would take a missing label as lost ownership) and a `delete` right after a managed claim that does not see `managed` yet, within `consistencyWindowMs` of the claim by the same client. The vps unique index on the external id referees between control planes. `release` removes the tags only when they name the instance. Deleting an attached instance detaches it by default and leaves it running.

## Networks

`AwsCompute.networks` implements tenant networks (`ProviderNetworks`, AWS phase A2) with `subnetScope: 'zone'` and `denyRules: 'network-wide'`; `zoneRegion` maps `us-east-1a` and Local Zones to their region. Everything it makes is tagged `better-compute:managed=true` and `better-compute:network=<network>` and found again by tag:

- `ensureNetwork`: a VPC (the spec's `cidr`, default `10.64.0.0/16`, private /16 to /28; or an `ipamPoolId` allocation), DNS support and hostnames, an internet gateway, and the network's own route table (its `0.0.0.0/0` route to the gateway) and network ACL (allow-all at rule 32766, so deny entries come first), both created tagged with an idempotency token. AWS's main route table and default ACL are never edited.
- `ensureSubnet`: needs a zone of the account; a range outside the VPC gets its /16 (or itself) associated first; `MapPublicIpOnLaunch` follows `associatePublicIp`; the subnet is put on the network's route table and ACL (`AssociateRouteTable`, `ReplaceNetworkAclAssociation`) before it is `ready`, and one someone put on another route table is `error`, never moved; `privateGoogleAccess` adds S3 and DynamoDB gateway endpoints on the network's route table (no idempotency token, so one deleted by hand is made again; AWS refuses a second one for a service on the table) and tags the subnet `better-compute:private-access=true`: `deleteSubnet` of the last such subnet of the VPC removes the endpoints. In an adopted VPC a subnet must fall inside the VPC's ranges and cannot ask for private service access (`error`): an adopted VPC is never changed. A subnet that exists with another range or zone, or a range held by a subnet better-compute did not make, is `error`.
- `ensureFirewall`: allows go to `bc-net-<network>` (no targets) or to the group named after each target tag, with one `better-compute:firewall:<name>` tag per rule that wants a security group rule; the set is diffed and revoked by `SecurityGroupRuleId`, and a rule better-compute did not make is only tagged and untagged. Denies become entries on the network's ACL numbered `100 + priority/10` (shifted past taken ones, `INVALID_INPUT` at 32766), each owned through the ACL tag `better-compute:deny:<direction>:<n>`, written before the entry. A targeted deny, a deny on an adopted VPC, and destinations on ingress (or sources on egress) are `error`.
- `setTags`: the network's group and one group per tag on the primary interface, other groups kept; the instance must carry `better-compute:instance` naming it. Tags are `bc-…` but never `bc-net-…` (a network group's name), and the interface limit (`securityGroupsPerInterface`, default 5) is checked before any group is made (`QUOTA_EXCEEDED`). A tag group nothing uses any more (no interface has it, no firewall rule targets it) is deleted by a later `ensureNetwork`, `ensureFirewall` or `setTags` of its VPC, adopted VPCs included: at most one sweep per VPC every 10 minutes, and only after two sweeps a consistency window apart both saw it unused. `create` on a network launches in the network's subnet in the offer's zone (`INVALID_INPUT`, reason `subnet-zone`, otherwise) with those groups.
- An adopted network is a VPC id, or `default`: the account's default VPC in the region (`isDefault`), which vps adopts as the shared default network; an account without one is `error`. Neither is ever changed or deleted.
- Deletes go endpoints, subnets, security groups, gateway, the network's route table and ACL, VPC; `DependencyViolation` is `pending`, and so is an endpoint `DeleteVpcEndpoints` lists as unsuccessful.
- Not yet: NAT gateways for private subnets (the plan's optional `natGateway`), and telling the tenant the range an IPAM pool allocated (choose subnet ranges inside the pool's). With an `ipamPoolId`, the lost-CreateVpc check reads the region's VPCs by tag, since the range is not known up front. A VPC without the network tag is never deleted.

`aws iam-policy --phases A1,A2` adds the network statements (`networksIamStatements`): creates must carry `aws:RequestTag/better-compute:managed=true`, changes and deletes need the tag on the resource, rule and ACL tag edits are limited to their keys, and group swaps need `better-compute:instance` on the instance (or the primary interface: RunInstances tags it, and setTags tags a claimed multi-interface machine's with that key only). No statement grants `better-compute:managed` or `better-compute:network` on an existing resource, so a resource-tag condition cannot be met by tagging: routes, ACL entries and subnet associations change only on route tables, ACLs and subnets created managed (which is why a network has its own table and ACL instead of AWS's untagged main ones), deny-owner tags go only on a managed ACL, route tables, ACLs and endpoints go only into a managed VPC and an endpoint only onto a managed table, and a route may only name a managed internet gateway. The one self-grant left is the interface ownership tag, as with A1's attach: the role may put `better-compute:instance` on any network interface it may tag, which unlocks that interface's security groups. `--discover-tag key=value` limits it to interfaces carrying the discovery tag (tag the interfaces of machines you attach, not only the instances). (verify) whether `ReplaceNetworkAclAssociation` authorizes against the new ACL only (not the one the subnet leaves). (verify) whether `ec2:CreateAction` covers rule tags on `AuthorizeSecurityGroup*` and which resources `CreateVpcEndpoint` names, against the live suite.

## EBS volumes

`ProviderImpl.volumes` is EBS behind the generic provider volumes contract (AWS phase A5); vps drives it with the `providerVolumes` and `providerSnapshots` groups. Every call reads EBS, starts at most one operation and returns where it stands (`pending`, `updating`, `deleting`); the reconciler calls again.

- **Ownership.** A volume is tagged `Name`, `better-compute:managed=true` and `better-compute:volume=<name>` (the name vps derives), plus its labels as `better-compute:<key>`; a snapshot carries `better-compute:snapshot=<name>` instead. Attach, detach, resize, snapshot and delete refuse a volume without both ownership tags (`INVALID_STATE`, reason `not-managed`), and a restore or `deleteSnapshot` a snapshot without them: a public or shared snapshot is someone else's data. Snapshots are read with `Owner=self`, so another account's snapshot reads as missing whatever tags it carries (a restore from it is `INVALID_INPUT`, reason `snapshot`).
- **Create.** `ensureVolume` finds the volume by its name tag, else calls `CreateVolume` with `ClientToken` = sha256(`volume:<name>`), so a lost answer never makes a second volume; a retry with other parameters (`IdempotentParameterMismatch`) is `UNAVAILABLE` (reason `not-visible-yet`) until EBS shows the first. A name whose only volume is deleting or deleted without this client having deleted it (an operator, a cleanup script) is state `error` (`outputs.reason` `deleted-outside`), also when EC2 answers the old `ClientToken` with that deleted volume: never pending for ever, never an empty volume in its place. Volumes are always encrypted, with the account's `kmsKeyId` or the account's default EBS key; a spec cannot name another key. The zone is `spec.zone`, else the zone `spec.region` names (vps keeps AWS volumes per zone), else the account's only zone; a bare region on an account with several zones is `INVALID_INPUT` (reason `zone-required`), never a silent first zone. A volume's `region` output is that zone (as is `zone`), the place vps names it by; a snapshot's `region` is the account region. Types are `gp3` (the default), `gp2`, `io2`, `io1`, `st1`, `sc1` and `standard` (`volumes.types`), with each type's minimum size; `iops` only for gp3, io1 and io2, `throughputMiBps` only for gp3. Shared volumes (EFS, phase A10) and formatted filesystems are `UNSUPPORTED`: the guest formats a raw volume (a restore ignores `filesystem`: it keeps the snapshot's). `findVolume(name, region)` reads the volume of a name without ever creating one (vps asks it for a delete whose create answer was lost): undefined when there is none or it is gone, and in a zone only that zone's.
- **Reads by id.** EC2 reads are eventually consistent: a volume or snapshot another control-plane process (a restart, another replica) just made can read `NotFound` by id. One miss never ends its life: `getVolume` and `getSnapshot` report `pending`, `deleteVolume` and `deleteSnapshot` report `deleting` (nothing is deleted yet, nothing settles as gone), and attach, resize and snapshot are `UNAVAILABLE` (reason `volume-not-visible`, retried) until a by-id read finds it or it has been missing for the whole `consistencyWindowMs` (2 minutes) since this process first missed it; then it is gone (undefined, `deleted`, `NOT_FOUND`). A volume or snapshot this process deleted, or saw deleted, is gone at once.
- **Attach.** Only to an instance carrying `better-compute:instance` (the instance named, when vps names one; else `INVALID_STATE`, reason `not-instance`) in the volume's zone (else `INVALID_INPUT`, reason `zone-mismatch`, before any write). A volume attached elsewhere is `CONFLICT`. An instance EC2 does not show yet (vps attaches right after `RunInstances` answered) is `UNAVAILABLE` (reason `instance-not-visible`, retried) until it shows, or `NOT_FOUND` (reason `machine`) once it has been missing for the whole consistency window; a terminated instance still reads terminated for a while (`INVALID_STATE`, reason `instance-state`). A volume being created or an instance between states waits (`pending`). The device is the next free `/dev/sd[f-p]` (`/dev/xvdX` counts as the same name; none free is `QUOTA_EXCEEDED`, reason `devices`). The client remembers the devices it gave for the consistency window, so two attaches to one new instance in one pass never pick one device while the attachment reads lag; EC2 refusing a device another writer took (a re-read shows it, or EC2 says the attachment point is in use) is `UNAVAILABLE` (reason `device-race`), and the retry skips that device. Outputs: `attachedTo`, `attachDevice` (the `/dev/sdX` EC2 was given), `serial` (the volume id without the dash, which Nitro guests see as the NVMe serial) and `device`, `/dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<serial>`. `detachVolume` never touches a volume attached to another machine. A detach right after this client's own attach, before the by-id read shows any attachment, reports `deleting` and detaches once the attachment shows (for at most the consistency window), never `deleted` while the volume attaches. With `{ force: true }` it sends `DetachVolume` with `Force` (for a guest that never releases the volume; unflushed writes may be lost), also on a detach already stuck in `detaching`, once per attachment, then waits.
- **Resize.** `ModifyVolume`, grow only (`INVALID_INPUT`, reason `shrink`). EBS takes one modification per volume every six hours, counted from the start of the last one: a resize inside that window, or while a modification to another size runs, is `RATE_LIMITED` (reason `cooldown`) with `retryAfterMs`; EBS's own refusals map the same way. A resize reports `updating` while EBS modifies the volume, and `ready` once EBS reports the new size.
- **Snapshots.** `snapshotVolume` finds the snapshot by its name tag, else calls `CreateSnapshot` (which takes no client token, so the client remembers what it created for the consistency window). A control-plane restart inside the tag-read lag can still take a second snapshot of one name: the next `snapshotVolume` keeps the oldest and deletes the others, and `deleteSnapshot` also deletes the other snapshots of its name, so none is orphaned. Restores use only completed snapshots of this deployment and at least the snapshot's size. `deleteSnapshot` of a snapshot an AMI uses is `INVALID_STATE` (reason `in-use`).
- **Policy.** `aws iam-policy` grants the EBS actions tag-scoped: creates only when they tag the new volume or snapshot managed, every change only on a managed volume that also carries its `better-compute:volume` name (never a root volume, which RunInstances tags managed too: two `Deny` statements refuse a `RunInstances`, and the `CreateTags` it makes, that would put `better-compute:volume` or `better-compute:snapshot` on a volume), restores and snapshot deletes only on managed snapshots carrying `better-compute:snapshot` (with `--account`, only that account's: `ec2:Owner`), attach and detach only on an instance carrying `better-compute:instance` (`iamPolicy({ volumes: false })` leaves them out). With a customer-managed `kmsKeyId`, `--kms-key` adds the grants EBS needs.
- **AWS Backup.** Tag-based backup plans can select `better-compute:managed=true` volumes (or one of their label tags). Snapshots AWS Backup takes are not better-compute's: they carry no `better-compute:snapshot` tag and cannot be restored through vps.

## Managed Kubernetes (EKS)

The provider implements `ProviderImpl.kubernetes` on Amazon EKS, so [`@better-compute/kubernetes`](../kubernetes) (`kubernetesClusters`, `kubernetesNodePools`, short-lived kubeconfigs) works on an AWS account as it does on GKE. Clusters are regional: the location is the account's `region`. The account needs `eksClusterRoleArn`, `eksNodeRoleArn` and, unless a cluster names its subnets, `eksSubnetIds`.

| Field               | Meaning                                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| `eksClusterRoleArn` | The IAM role new clusters run as.                                                                         |
| `eksNodeRoleArn`    | The node IAM role of managed node groups and EKS Auto Mode nodes.                                         |
| `eksSubnetIds`      | Default subnets of new clusters (two or more, in two or more zones); node groups use the cluster subnets. |
| `eksNodeInstanceProfile` | The instance profile of EC2 machines that join an EKS cluster (`policy.kubernetes.eks`); its role holds the `EC2_LINUX` access entry. Only those launches get it, and they get nothing else. |

- **Clusters.** `standard` is a cluster whose nodes are managed node groups; `autopilot` is EKS Auto Mode (EKS runs the compute, block storage and load balancing; there are no node pools). Every cluster authenticates through access entries only (`authenticationMode: API`): there is no `aws-auth` ConfigMap, and the creator (the account's own principal) gets the cluster-admin access entry. The release channel maps to EKS's support policy (`extended` to `EXTENDED`, the others to `STANDARD`; EKS has no rapid, regular or stable channels and upgrades only when `version` asks). In place, one update at a time: the support policy, the version (one minor per `UpdateClusterVersion`, as EKS upgrades; never down) and the authorized networks (`publicAccessCidrs`; empty means `0.0.0.0/0`). better-compute mints credentials through the public endpoint, so authorized networks that leave out the better-compute host make `credentials` fail (as on GKE); the driver does not add that host for you. The mode, VPC, subnets and private nodes are immutable (`INVALID_STATE`); with `privateNodes` no subnet may have `MapPublicIpOnLaunch`. A network's `subnet` may list several subnet ids, comma-separated. Deleting a cluster deletes its node groups first. Clusters and node groups carry `better-compute:managed=true`.
- **Node groups.** Counts are per zone, as on GKE: a node group's sizes are the pool's times the zones of its subnets (all of the cluster's, or those in `zones`). AL2023 AMIs follow the instance type: NVIDIA for GPU types (with the taint `nvidia.com/gpu=:NoSchedule`, as GKE's GPU pools have), arm64 for Graviton, Neuron for Inferentia and Trainium (with the taint `aws.amazon.com/neuron=:NoSchedule`). A GPU pool, or any pool of a GPU family (`p*`, `g*`, `gr*`), whose instance type cannot be read (no `ec2:DescribeInstanceTypes`) is refused (`INVALID_STATE`, reason `instanceTypeUnknown`) rather than made with the CPU AMI. Unlike GKE, EKS does not install the NVIDIA device plugin: the AL2023 NVIDIA AMI ships the drivers only, so `nvidia.com/gpu` is advertised once bcd's device plugin or the tenant's runs on the group. `spot` is `capacityType: SPOT`. `accelerators` must match the type, since EKS attaches none (`nvidia-l4` x 1 on `g6.xlarge`). `diskType` is refused: managed node groups without a launch template use the AMI's. With `autoscaling` the bounds are the group's min and max size and a cluster autoscaler in the cluster owns the desired size. Only the size and the bounds change in place. After the control plane is upgraded, `ensureNodePool` upgrades the group (`UpdateNodegroupVersion`) one minor at a time until it runs the cluster's minor, as GKE upgrades node pools after their control plane.
- **Credentials.** The account principal reaches a cluster's API with an `eksToken` (aws-core: a presigned STS `GetCallerIdentity` signed with the `x-k8s-aws-id` header) through its access entry, which the driver creates with `AmazonEKSClusterAdminPolicy` at cluster scope on a cluster another principal made (the IAM policy allows that only on managed clusters unless the account adopts clusters). Each subject gets a service account in `bc-access` bound to the built-in `view` or `cluster-admin` ClusterRole, or for `edit` to `better-compute:edit`, and a TokenRequest token for the requested lifetime. `better-compute:edit` is `view` plus the built-in edit's writes without `impersonate` on service accounts and without `serviceaccounts/token`: the built-in edit would let an edit subject act as any service account of `bc-access`, an admin subject's included. Before the first token the driver also writes the ValidatingAdmissionPolicy `better-compute-access-guard`, which refuses every create, update, delete and connect (exec, attach, port-forward) in `bc-access` and `kube-system` by a `bc-access` subject that cannot escalate ClusterRoles (all but cluster-admin), so pods, token secrets and exec there cannot borrow another service account. A cluster without that API (before Kubernetes 1.30) gets no credentials (`INVALID_STATE`). Service accounts of other namespaces stay reachable to edit subjects, as Kubernetes' edit is designed. Reads are not admission: like Kubernetes' edit, `better-compute:edit` reads Secrets in every namespace, `kube-system` and `bc-access` included (on EKS, add-on webhook TLS keys and any legacy service-account-token Secret of a privileged service account, which leads to cluster-admin). Grant `edit` only to subjects trusted with those; binding the secrets read per namespace is open. Nothing is stored and no token is logged. A cluster that authenticates through the ConfigMap only is `INVALID_STATE`.
- **Versions** come from `DescribeClusterVersions`: the `rapid`, `regular` and `stable` channels list the versions in standard support, and `extended` adds those in extended support.
- **Discovery.** `kubernetes.listClusters` lists every cluster of the region, with the nodeadm settings of the ready ones (`policy.kubernetes.eks`), so EC2 machines can join an EKS cluster through `k8s-join` mode `eks`. The vps method `providerAccounts.clusters` (`compute:providers:read` on the account) returns that list. A provider pool whose policy names one (`policy.kubernetes.eks`, with `platformOperated` on a platform site) launches every machine of the pool owner (a tenant the pool is offered to would get root on a cluster node, so its launches fail closed) with nodeadm's `NodeConfig` as the first part of its user data, the SSH keys and the tenant's user data as further parts of the same multipart; use an `eks-al2023-<k8s>` image. Those launches, and only those, carry the account's `eksNodeInstanceProfile`, whose role has the cluster's `EC2_LINUX` access entry (without it they fail closed, `INVALID_CONFIG`). Never give that entry to the role of `instanceProfile`: every machine of the account gets it, including those of pools offered to other tenants, whose root could then register a Node in the cluster.

`aws iam-policy --eks-cluster-role <arn> --eks-node-role <arn>` adds the EKS statements: reads; `CreateCluster` and `CreateNodegroup` only when they tag `better-compute:managed=true`; updates and deletes only of resources tagged so; every write (and `eks:TagResource`, which tag-on-create needs) only on clusters named `bc-k-*` and their node groups and access entries, the names the kubernetes module uses, so the role cannot tag a cluster it did not create as managed and then delete it; an access entry only for the caller's own principal (`eks:principalArn` equal to `${aws:PrincipalArn}`), only on clusters tagged `better-compute:managed=true` (the driver tags the entries it creates the same way), with only the cluster-admin access policy at cluster scope (`--eks-adopt-clusters` drops the tag condition and the name scope of the own access entry only, for credentials on clusters better-compute did not create; it never extends updates or deletes); `iam:PassRole` of the two roles to EKS; and the EKS service-linked roles. `--eks-node-instance-profile <arn>` adds `iam:PassRole` of that profile's role to EC2. Host options: `endpoints.eks` (emulators, VPC endpoints), `platformRoleArn` (the host's ambient role ARN with its path, for the access entry of platform accounts on ambient credentials: a session ARN drops the path) and `kubeTransport` (the transport to a cluster's API; by default `node:https` trusting only the cluster's CA).

### Hosted mode and nodeadm

[`@better-compute/provider-kubernetes`](../provider-kubernetes) runs bcd as a DaemonSet in an existing EKS cluster: select a node group with `nodeSelector: { 'eks.amazonaws.com/nodegroup': '<name>' }` and tolerate `nvidia.com/gpu` `NoSchedule` on GPU node groups. Machines of a provider pool join an EKS cluster instead through `policy.kubernetes.eks` (`k8s-join` mode `eks`): provision's `eksUserData` puts nodeadm's `NodeConfig` (`node.eks.aws/v1alpha1`) into the user data of an AL2023 EKS AMI (alias `eks-al2023-<k8s>`), and the node authenticates as the role of the account's `eksNodeInstanceProfile`, which needs an `EC2_LINUX` access entry on the cluster.

## Events

`pollEvents` is the account's event intake (A4, AD12), read by vps's `vps.provider-events` worker. With `eventQueueUrl`, it long-polls the queue (`ReceiveMessage`, at most 10 messages, `WaitTimeSeconds` at most 10) and maps EventBridge envelopes:

| `detail-type`                                                     | Event                                                     |
| ----------------------------------------------------------------- | --------------------------------------------------------- |
| `EC2 Instance State-change Notification`                          | `machine-changed`                                         |
| `EC2 Spot Instance Interruption Warning`                          | `interruption-warning`, deadline = event time + 2 minutes |
| `EC2 Instance Rebalance Recommendation`                           | `rebalance-recommended`                                   |
| `EC2 Capacity Reservation Instance Interruption Warning`          | `interruption-warning`, deadline = `instance-termination-time` |
| `AWS Health Event` (service `EC2`, `scheduledChange`, naming instances) | `maintenance-scheduled` per instance, deadline = `startTime`, `healthEvent` = the ARN's unique tail |
| `AWS Health Event` (service `EC2`, another category, naming instances) | `health` per instance                                   |
| `AWS Health Event` naming Capacity Reservations (ODCR underutilization) | `reservation-changed` per reservation                  |
| `Capacity Block Delivered`, `Capacity Block Expiration Warning` and other Capacity Reservation, Capacity Block and ODCR types | `reservation-changed`                     |
| `AWS API Call via CloudTrail` (succeeded EC2 instance calls)      | `api-call` per instance                                   |
| `GuardDuty Finding` (when `aws.guardduty` is allowed)             | `health`                                                  |

An envelope counts only when its `account` is the account's verified AWS id, its `region` the account's region and its `source` allowed. Everything else (and anything malformed) is dropped, with counts logged and no message content, and deleted with the batch, so a forged message is read once and never loops. Messages are deleted (`DeleteMessageBatch`) only when vps calls the batch's `ack()`, after its transaction commits; a queue in another AWS account than the identity is `INVALID_CONFIG`. Events only wake reconcilers early: polling stays the source of truth, so a forged event can at worst cause a harmless re-read. The Capacity Block detail types are the ones the EC2 user guide documents (pinned in the tests); the Ec2Events rule also passes the `Capacity Block`, `Capacity Reservation`, `EC2 Capacity Reservation`, `EC2 ODCR` and `EC2 Capacity Block` prefixes, as broad as the mapper, for types not documented yet.

Without a queue, `pollEvents` reads scheduled events with `DescribeInstanceStatus` at most every 5 minutes and reports each as `maintenance-scheduled`; the event id carries its status, so a completed or canceled event is new. The scan includes stopped instances (`IncludeAllInstances`: instance-stop and instance-retirement stop the instance before EC2 marks the event completed), and a complete scan is authoritative: an event the previous scan listed as scheduled and this one does not list at all (rescheduled under a new id, or aged out) is reported as completed. The previous set lives in the process, so an event that vanishes while the control plane restarts is not completed this way.

`better-compute aws event-rules --queue-name <name> --account <id>` prints the CloudFormation stack to deploy in the account: the queue and its dead-letter queue (SSE-SQS, 14-day retention), the EventBridge rules (`--api-calls` adds CloudTrail EC2 calls, `--guardduty` GuardDuty findings), and a queue policy that lets only `events.amazonaws.com` send, only from those rule ARNs in the account, only over TLS, and denies `sqs:SendMessage` to every other sender (a same-account role with `sqs:SendMessage` on `*` included: its forged body could otherwise carry the right account, region and source). Its `QueueUrl` output is `eventQueueUrl`. `aws iam-policy` includes `ec2:DescribeInstanceStatus`, and `--event-queue <name>` adds `sqs:ReceiveMessage` and `sqs:DeleteMessage` on the queue. Add `awsEventRulesCommand()` to the CLI configuration next to the policy commands.

## Costs, prices and governance

Costs (A11) are opt-in, because Cost Explorer charges per request, and read in the commercial partition (`aws`) only (an aws-cn or GovCloud account with `costs` is refused at create: GovCloud has no Cost Explorer, its costs are read from the linked commercial account): an account with `costs: 'region'` (only its own region, for several regional accounts on one AWS account) or `costs: 'account'` (every region) has `costs`, which the `vps.costs` worker reads into `provider_costs`. It is `GetCostAndUsage`, daily, in three queries per window: regular usage by the `better-compute:instance` tag and usage type, regular usage without that tag by `better-compute:tenant` (a tag provider-aws never writes: only resources an operator tags with it are attributed to a tenant this way), and everything else (tax, credits, fees, Savings Plan negation) by record type and service, as `costType`. Every query is filtered to the caller's own linked account, so a payer role never reads its member accounts. In `region` scope it is also filtered to the account's region and the Local Zone groups its `zones` name (`us-west-2-lax-1a` adds `us-west-2-lax-1`, the REGION Cost Explorer reports Local Zone usage under); those rows carry the parent region. Two provider accounts on one AWS account that read the same scope (both `account`, one `account` and one `region`, or both `region` in one region) would ingest every row twice: in one process the second is refused (`INVALID_CONFIG`, reason `costs-overlap`) until the first stops reading for two days. Readers in other processes are not seen, so keep one reader per scope. The current UTC day is never read (it is incomplete) and a day read is kept 24 hours (`costsCacheMs`), so the 6-hourly pass costs one read per day. Each finished day is read on two passes a day apart, so the vps window must hold two full days before today: `vps({ costs: { lookbackDays } })` of 3 or more (the default). A shorter window reaching today is refused (`INVALID_CONFIG`, reason `costs-window`, recorded as the pass's error) rather than read as no rows. Cost Explorer groups only by **active cost allocation tags**: activate `better-compute:instance`, `better-compute:tenant`, `better-compute:pool` and `better-compute:managed` in the payer account (`better-compute aws cost-allocation-tags --activate --yes`, or the Billing console), or nothing is attributed to instances and an `aws budget-template` budget tracks nothing. provider-aws writes `better-compute:managed` and `better-compute:instance` on the instances and volumes it creates (and `better-compute:instance` on those it claims); so costs are attributed by instance, and by `better-compute:tenant` only where an operator tagged a resource with it. Activation applies from then on, not to earlier costs. `awsBilling` tells vps that instance hours are compute and EBS volumes and public IPv4 addresses are metered, so those rows are never passed through, and leak detection compares a daily row's billed hours with the instance's running intervals.

`listPrices` reads the AWS Price List (`pricing:GetProducts`; Linux, shared tenancy, on demand) for the regions asked, the account's region by default, each kept 24 hours. It exists in the `aws` partition only, the one the Price List serves. Instance prices are split per family into a vCPU and a GiB price (a GiB weighs 0.074 of a vCPU) that compose back to the family's prices exactly; a GPU type's vCPUs and memory take the region's cheapest general-purpose family and the rest per GPU is the GPU price. EBS capacity is per GiB-hour (730 hours a month) and an in-use public IPv4 address per hour. There are no Spot list prices.

`aws iam-policy --costs --prices` adds `ce:GetCostAndUsage` and `pricing:GetProducts` (neither takes resource ARNs). The governance commands run as the operator's own AWS identity, whose policy `aws governance-policy` prints (the reads always, `organizations:DescribeOrganization` among them; `--activate-tags`, `--quota-requests` and `--spend` add ce:UpdateCostAllocationTagsStatus, servicequotas:RequestServiceQuotaIncrease on EC2 quotas, and ce:GetCostAndUsage for the spend guard): `aws organization-accounts --role <name> --region <r> --zones <a,b> [--parent ou-…]` prints FleetConfig provider accounts for an organization's ACTIVE accounts (it only renders; the management account, from `organizations:DescribeOrganization`, is left out unless `--include-management`, and so is an account whose state AWS does not give; `--exclude` takes 12-digit ids); `aws quotas` prints the EC2 instance vCPU quotas and `aws quota-request --quota-code L-… --value <n> --yes` asks for more (without `--yes` it only prints); `aws tag-policy [--enforce]` renders an Organizations tag policy for the better-compute keys; `aws budget-template --amount <n> --email <a>` renders an `AWS::Budgets::Budget` CloudFormation template over everything tagged `better-compute:managed=true` (it refuses `--tenant` and `--pool`: provider-aws does not write those tags, so such a budget would never see an instance's spend). `awsMonthToDateCost` and `assertAwsSpendBelow` are the live suite's spend guard; they compare gross spend (credits and refunds left out), so an account on promotional credits still trips it. An answer they cannot read (no days, a day without an amount or currency they can parse) refuses the run (`PROVIDER_ERROR`, reason `spend-unreadable`) and is never counted as $0 spent; spend in a currency other than USD is `QUOTA_EXCEEDED`.

## ML fabric

Phase A10 (`src/placement.ts`, `src/topology.ts`, `src/filesystems.ts`):

- **Placement groups.** A create's `placement` (`{ group, strategy: 'cluster' | 'spread' | 'partition', partition? }`) sets `Placement.GroupName` (and `PartitionNumber`). The group is read with `DescribePlacementGroups` and made when absent with `CreatePlacementGroup`, tagged `better-compute:managed=true` (partition groups get 7 partitions); a group made or read is trusted for an hour. A `Duplicate` answer is read again, and a group EC2 does not show yet is `UNAVAILABLE` (`placement-group-propagating`), never launched into blind. A group better-compute did not make is `CONFLICT` (`placement-group-foreign`): it is never adopted. Another strategy is `CONFLICT` (`placement-strategy`), a deleting group `UNAVAILABLE` (`placement-group-deleting`), and a placement with a reservation offer (`@cr-…`) `INVALID_INPUT` (`placement-reservation`).
- **EFA.** With `efa: 'auto'`, a type whose `NetworkInfo` reports EFA launches with one `InterfaceType=efa` interface per network card, up to `MaximumEfaInterfaces`: card 0 as device 0, every other card as device 1, and no public address when there is more than one interface (EC2 refuses it), even with `associatePublicIp: true`: the provider warns once per type (`efa-public-ip`), so reach such machines over their private addresses or attach an Elastic IP yourself. EFA needs explicit interfaces, so a launch without a subnet is `INVALID_CONFIG` (`efa-subnet`) rather than a machine without its fabric. EFA traffic also needs the security group to allow all traffic from itself: with `efa: 'auto'`, `ensureNetwork` gives the network's group (`bc-net-<network>`, on every interface of its machines) an all-traffic ingress and egress rule naming the group itself, tagged `better-compute:efa` and no firewall key, so firewall changes never revoke it; with `efa: 'off'` the next `ensureNetwork` revokes the rules it made. Every machine of an EFA network can then reach every other one on any port. A launch on `subnetId` and `securityGroupIds` (no network) needs that rule in those groups already. (verify) whether the newer `efa-only` interface type should take the secondary cards on p5.
- **Topology.** `get`, `list` and `discover` of a running machine of an EFA family read `DescribeInstanceTopology` (once an hour per machine; `list` and `discover` ask for up to 100 machines in one read) and label it `topology.aws/network-node-1..N`, top to bottom, so every path shows the same labels. A malformed answer is no topology; a failed read warns once, leaves the labels out and is asked again after a minute (after the hour when the account may not read topology: `ACCESS_DENIED`, `UNAUTHENTICATED`, `UNSUPPORTED`); a tag never poses as one of these labels.
- **Neuron.** `NeuronInfo` devices are the machine's `gpus`: Trainium `TRN1`, Trainium2 `TRN2`, Inferentia `INF1`, Inferentia2 `INF2` (an unknown name is `other`), so flavors and `gpuModel` queries treat them like GPUs. (verify) bcd's inventory model strings for `/dev/neuron*`.
- **Graviton.** Offers carry `arch`, image aliases resolve the arm64 build on arm64 types, and an AMI whose `DescribeImages` architecture the type cannot run is `INVALID_INPUT` (`image-arch`) before `RunInstances`.
- **Shared filesystems.** `filesystems` (`ProviderFilesystems`, kinds `nfs` and `lustre`; sub-plan `docs/superpowers/plans/2026-11-05-aws-a10-shared-filesystems.md`). `nfs` is Amazon EFS: `CreationToken` = the filesystem name, general purpose, elastic throughput, always encrypted (`kmsKeyId` when set), and one mount target per zone in the network's subnet there (the first by name; a zone that gains a subnet gets one on the next ensure). `lustre` is FSx for Lustre in one zone (`zone`, default the account's first): `SCRATCH_2`, or `PERSISTENT_2` at 125 MB/s/TiB with `deployment: 'persistent'`; 1200 GiB or a multiple of 2400 GiB, refused before any call otherwise (`filesystem-size`). Both sit behind the filesystem's own group `bc-fs:<name>`, which allows NFS (2049) or Lustre (988, 1018-1023) from the network's group only, and Lustre also from itself; its rules carry `better-compute:filesystem` and no firewall key. The group names the network's group, so the network is not deleted before its filesystems. Only networks better-compute made take filesystems (an adopted VPC is `error`), and a file system without `better-compute:managed=true` is never adopted or deleted (`INVALID_STATE`, `filesystem-foreign`). `deleteFilesystem` deletes the mount targets, then the file system (persistent Lustre skips the final backup), then the group. The ready state's `mount` (`nfs4` `<fs>.efs.<region>.amazonaws.com:/`, or `lustre` `<dns>@tcp:/<mountName>`) is what a create's `mounts` takes: they are checked against those shapes, a plain absolute path outside the system directories, and plain options (`INVALID_INPUT`, `mount`), and packed as a `text/x-shellscript` part before the tenant's part (client install, an fstab line with `nofail`, `mount`). It is a shell part because cloud-config parts merge with replace, so a tenant `runcmd` would drop it. (verify) The Ubuntu Lustre client needs the FSx apt repository.
- **Capacity Block proposals.** vps's `vps.purchase-proposals` worker proposes a Capacity Block 48 hours before a `pending` capacity reservation of a provider pool on a platform account starts: `listReservationOfferings` for whole machines of the pool's GPU flavor covering the reservation (block lengths of whole days up to 14 days, whole weeks up to 182), the covering block that starts latest. Root reads them with `providerAccounts.purchaseProposals` and buys one with `purchaseReservation` (confirmed, `allowPurchases`); nothing is bought on its own. Instances on the vps filesystems group (`instances.create` `filesystems`) get the mounts above.

`aws iam-policy --phases A1,A10` adds `MlFabricRead` (`DescribePlacementGroups`, `DescribeInstanceTopology`), `CreatePlacementGroup` only with `aws:RequestTag/better-compute:managed=true` (and the tag on create), and `RunInstances` on `placement-group/*` only when the group carries that tag. For filesystems it adds `FilesystemRead` (EFS and FSx describes), `FilesystemCreate` (EFS and FSx creates only with `aws:RequestTag/better-compute:managed=true`), tag-on-create only (`elasticfilesystem:CreateAction`, `fsx:CreateAction`), `FilesystemManageOwned` (mount targets and deletes only on file systems carrying that tag), `FilesystemEc2Read` (`DescribeSubnets`, `DescribeNetworkInterfaces`, `DescribeSecurityGroups` on `*`: EC2 describes have no resource-level permissions), `FilesystemMountTargetInterfaces` (`ec2:CreateNetworkInterface` and `DeleteNetworkInterface` on the account's subnets, security groups and interfaces in the region, which EFS requires of the caller for a mount target; EFS does not set `aws:CalledVia` and its interfaces carry no tag of ours, so this cannot be narrowed further), and `FilesystemServiceRoles` (`iam:CreateServiceLinkedRole` for the EFS and FSx service-linked roles, which an account's first create makes). Their groups and rules come from A2, so filesystems need `--phases A2,A10`. (verify) `fsx:CreateAction` and the mount target statements against the live suite.
