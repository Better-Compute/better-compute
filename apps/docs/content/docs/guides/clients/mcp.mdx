`@better-compute/mcp` turns the compute API into [Model Context Protocol](https://modelcontextprotocol.io) tools, so
an AI agent can find GPU capacity, reserve and release GPUs, create, stop, start and delete VPS instances, look at a
node and run a diagnostic. There are no tools for [sandboxes](/docs/guides/vps/sandboxes) yet; an agent calls the
`sandboxes` API directly. It is built for
the v0.3 goal "an agent reserves via MCP with human confirmation, retrying with the same key", and the end-to-end
test `tests/mcp-e2e-confirmation.test.ts` runs exactly that against a real server and an embedded Better IAM.

The design has one rule: **every tool calls the compute API as the caller.** A tool forwards the agent's own
`Authorization` header, so compute and Better IAM make the real decision on each call, and a tool can never do more
than the agent's credential allows. The server holds no credential of its own.

## How it fits

```mermaid
sequenceDiagram
  participant A as Agent (MCP client)
  participant G as Better IAM gate
  participant M as createComputeMcp
  participant C as compute API
  participant I as Better IAM
  A->>G: POST tools/call reserve_gpus (Bearer agent token)
  G->>I: authenticate; compute:pools:read on the pool?
  G->>M: forwarded request, caller
  M->>M: validate arguments against the tool's schema
  M->>C: reservations.create (same Bearer token)
  C->>I: decide compute:reservations:create on the draft
  C-->>M: reservation, or CONFIRMATION_REQUIRED
  M-->>A: tool result (structuredContent)
```

The server is a small, stateless Streamable HTTP endpoint that speaks JSON-RPC 2.0 for `initialize`, `ping`,
`tools/list` and `tools/call`, and accepts notifications. It has no MCP SDK dependency; its only runtime dependency
is `@better-compute/client`. `@better-iam/mcp`, which provides the gate, is an optional peer.

<Callout type="info" title="Mounted when you ask for it">
  `serve` and `dev` mount the endpoint when the configuration's host sets `host.mcp` (below); nothing is mounted
  otherwise. You can also host the handler yourself in any runtime with the Fetch API, with Better IAM embedded in
  the same process or reached over HTTP ([remote IAM](#remote-iam)).
</Callout>

## Mount it with serve

`computeMcpEndpoint({ compute, gate, delegations?, ...options })` builds the endpoint for a control plane in the same
process: the gate first, then the tools, each calling `compute.handler` in-process with the caller's own
`Authorization` header, so compute decides every call exactly as it would over HTTP. With `delegations` (Better IAM's
delegations API) the tools wait inside the call for a person to approve a held-back action. Hand its `handler` to the
host:

```ts title="better-compute.config.ts"
import { createMcpGate } from '@better-iam/mcp';
import { defineHost } from 'better-compute/cli';
import { computeMcpEndpoint, gateTools } from 'better-compute/mcp';

export const host = defineHost(({ compute }) => ({
  mcp: {
    path: '/mcp', // the default
    handler: computeMcpEndpoint({
      compute,
      gate: createMcpGate({ iam, tenantId: platformTenantId, tools: gateTools(), unlisted: 'deny' }),
      delegations: iam.api.delegations,
    }).handler,
  },
}));
```

`serve` and `dev` then answer `POST`, `GET` and `DELETE` on the path, and `GET
/.well-known/oauth-protected-resource{path}` for the gate's RFC 9728 metadata. A path that is not absolute, or a
missing handler, is `INVALID_CONFIG`. The gate is required. Give it a fixed `tenantId` (the organization that runs the
endpoint), or choose one per caller deliberately: deciding in each caller's own tenant would let any organization
grant itself access. The compose audit test mounts it through a real `serve`: no token is 401, and an administrator
lists the tools.

## Mount the endpoint yourself

```ts title="mcp.ts"
import { createMcpGate } from '@better-iam/mcp';
import { createComputeMcp, gateTools, iamConfirmations } from 'better-compute/mcp';
import { iam } from './iam';

const mcp = createComputeMcp({
  baseURL: 'https://compute.example.com',
  // Optional: wait inside the tool call for the person to approve (see below).
  confirmations: iamConfirmations(iam.api.delegations),
});

const gate = createMcpGate({ iam, tenantId, tools: gateTools(), unlisted: 'deny' });

export default {
  fetch: (request: Request) => gate(request, (forwarded, caller) => mcp.handler(forwarded, caller)),
};
```

With `baseURL`, each request gets a fresh compute client that forwards the caller's `Authorization` header and a
request id. The gate authenticates the caller, applies the visibility rules below, and hands the handler the
caller's `tenantId`, which the tools act in.

### Remote IAM

When Better IAM runs in another process, give the gate `remoteMcpIam()` instead of a `betterIam()` instance (v0.4).
It wraps a `createIamClient<BetterIam>()` from `@better-iam/client` and answers the gate's calls over Better IAM's
HTTP API, each with the caller's own credential (only identity headers are forwarded), so every decision is still
made and audited as the caller:

| Gate call | Better IAM API |
| --- | --- |
| authenticate | `sts.getCallerIdentity` |
| authorize, authorizeMany | `authorize`, `authorizeMany` |
| confirmations | the caller's delegation: `delegations.get` and `delegations.requestConfirmation` |

```ts
import { createIamClient } from '@better-iam/client';
import type { BetterIam } from '@better-iam/server';
import { remoteMcpIam } from 'better-compute/mcp';

const gate = createMcpGate({
  iam: remoteMcpIam(createIamClient<BetterIam>({ baseURL: 'https://iam.example.com' })),
  tenantId,
  tools: gateTools(),
  unlisted: 'deny',
});
```

`iamConfirmations()` reads confirmations through the server API's shape (`getConfirmation(credential, input)`), so a
remote host that wants tools to wait for approval passes an equivalent reader over its IAM client.
`tests/mcp-e2e-confirmation.test.ts` runs the whole confirmation flow through both the embedded and the remote gate,
including refusing another organization's owner.

`createComputeMcp()` returns the `tools`, `listTools()` (the `tools/list` entries) and `callTool(name, args, request,
caller?)` besides `handler`, so you can run a tool without the JSON-RPC wrapper, for example from your own agent
framework.

## The tools

| Tool | Calls | Gate rule | Hints |
| --- | --- | --- | --- |
| `list_pools` | `pools.list` | any authenticated caller | read-only |
| `capacity_summary` | `capacity.summary`, or `capacity.byPool` with `poolId` | any authenticated caller | read-only |
| `preview_reservation` | `capacity.preview` | `compute:pools:read` on the pool | read-only |
| `reserve_gpus` | `reservations.create` (`binding: 'hold'`) | `compute:pools:read` on the pool | idempotent |
| `release_reservation` | `reservations.release` | any authenticated caller | destructive, idempotent |
| `list_reservations` | `reservations.list`: the caller's own by default, `scope: 'all'`, filters `state` and `poolId`, `limit` 1 to 200, `cursor` | any authenticated caller | read-only |
| `get_reservation` | `reservations.get` | any authenticated caller | read-only |
| `extend_reservation` | `reservations.extend` by a duration, confirmation-aware | any authenticated caller | idempotent |
| `node_status` | `nodes.get` | `compute:nodes:read` on the node | read-only |
| `run_diagnostic` | `commands.run` with `diag.nvml` | `compute:nodes:read` on the node | idempotent |
| `create_instance` | `instances.create` | `compute:pools:read` on the pool | idempotent |
| `list_instances` | `instances.list`: the caller's own by default, `scope: 'all'`, filter `poolId`, `limit` 1 to 200, `cursor` | any authenticated caller | read-only |
| `get_instance` | `instances.get` | any authenticated caller | read-only |
| `start_instance` | `instances.start` | any authenticated caller | idempotent |
| `stop_instance` | `instances.stop` | any authenticated caller | destructive, idempotent |
| `delete_instance` | `instances.delete` | any authenticated caller | destructive, idempotent |
| `exec_command` (with `execCommand: true`) | `commands.run`: `inventory.refresh`, `logs.collect` or `node.reboot` | `compute:nodes:read` on the node | destructive |
| `fleet_export` (with `fleet: true`) | `fleet.export` | `compute:fleet:admin` on the fleet | read-only |
| `fleet_plan` (with `fleet: true`) | `fleet.plan` | `compute:fleet:admin` on the fleet | read-only |

The GPU tools share one argument shape: `poolId`, `gpus` (1 to 64 whole GPUs), `duration` (such as `30m`, `8h`,
`3d`), and optionally `gpuModel` (`H100`), `gpuProduct` (`H100-SXM5-80GB`), `nvlink` (all GPUs in one NVLink
domain) and `selector` (up to 32 `{ key, op, values }` expressions with `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`,
`Gte`, `Lt` or `Lte`). The tool turns them into one device request of class `gpu`. `reserve_gpus` also takes an
`idempotencyKey` and `waitSeconds` (0 to 30, default 20), which it sends as `wait: { timeoutMs }`, so on a pool-lease
pool the call returns once the reservation is placed or the wait runs out; see
[waiting for placement](/docs/guides/capacity/reservations#waiting-for-placement).

`create_instance` takes `poolId`, `flavor` and `imageId`, and optionally `sshKeys`, an `idempotencyKey` and
`waitSeconds` (0 to 30, default 20), which it sends as `wait: { timeoutMs }`: the call returns once the instance is running or has
failed, or the wait runs out, so the agent does not have to poll `get_instance`; see
[waiting for the instance](/docs/guides/vps/instances#waiting-for-the-instance).

The instance tools take one `instanceId` (`inst_…`), except `list_instances`. They pass it to compute as is, with the
caller's tenant: `stop_instance` is a graceful shutdown that keeps the disk and addresses, `start_instance` runs a
stopped instance again, and `delete_instance` removes the instance and its disk for good. Unlike `create_instance`,
they do not turn `CONFIRMATION_REQUIRED` into a result; it comes back as a tool error.

Every argument is checked against the tool's JSON Schema before anything is called: ids must match their prefix
(`pool_…`, `node_…`, `rsv_…`, `inst_…`), and unknown arguments are refused. A bad argument is a tool error `INVALID_INPUT`
with the path of the first problem.

**Fleet tools plan but never apply.** `fleet_plan` returns the changes and the `planHash`, with the list of calls
replaced by `callCount`. There is deliberately no apply tool: a person reviews the plan and runs
`better-compute fleet apply FILE --plan-hash HASH`. Pass `fleet: true` to both `createComputeMcp` and `gateTools`.

## The gate checks visibility only

`gateTools()` returns the rules for `@better-iam/mcp`'s `createMcpGate({ tools, unlisted: 'deny' })`. They are
deliberately light:

- A tool that names a pool is visible to a caller with `compute:pools:read` on `compute-pool/{poolId}`; one that
  names a node needs `compute:nodes:read` on `compute-node/{nodeId}`.
- `list_pools`, `capacity_summary`, the reservation tools (`release_reservation`, `list_reservations`,
  `get_reservation`, `extend_reservation`) and the instance tools (`list_instances`, `get_instance`,
  `start_instance`, `stop_instance`, `delete_instance`) are open to any authenticated caller, because the compute API
  filters and decides every call anyway, on the reservation or instance itself (`OwnReservations`, `BoundedExtend`,
  a delegation's confirm list).
- The fleet tools need `compute:fleet:admin` on `compute-fleet/global`, which only resolves in the root tenant.

The gate never checks the action a tool performs, such as `compute:reservations:create`. That decision happens once,
in compute, on the reservation draft with its full attributes. Actions a delegation holds back for confirmation are
never gate actions, so a person is never asked twice about two different resources for one request. Pass
`typePrefix` to `gateTools` if your deployment uses a resource type prefix other than `compute-`.

## Results and errors

A tool result carries the compute response twice: as pretty-printed JSON text in `content`, and as
`structuredContent` (an object; other values are wrapped as `{ result }`). `reserve_gpus` answers
`{ idempotencyKey, reservation }` and `create_instance` `{ idempotencyKey, instance }`, so the model always has the key
to retry with.

A compute error becomes a tool error with `isError: true`, the text `CODE: message`, and
`structuredContent.error` holding `code`, `message`, and `retryAfterMs` and `details` when compute sent them. Any
other failure is reported as `INTERNAL_ERROR` with a generic message, never internals. JSON-RPC problems use the
standard codes: `-32700` for unparsable JSON (HTTP 400) or a non-JSON content type (HTTP 415), `-32600` for an
invalid request or a batch (HTTP 400) or a body over `maxBodyBytes` (HTTP 413), `-32601` for an unknown method and
`-32602` for a missing `params.name`. Methods other than POST get 405. Notifications get 202 with no body.

## Delegated confirmation

An agent usually acts through a Better IAM **delegation**: a person lets the agent use some of their permissions,
and can list actions that the person must approve each time. When the agent calls one of those,
compute answers `CONFIRMATION_REQUIRED` and Better IAM opens a confirmation request. See
[delegated confirmation](/docs/guides/iam/delegated-confirmation) for the whole mechanism.

`reserve_gpus`, `extend_reservation` and `create_instance` turn that error into a normal result the model can act
on (`extend_reservation` answers `{ idempotencyKey, extension }` once it goes through):

```json title="reserve_gpus, waiting for a person"
{
  "status": "confirmation-required",
  "confirmationId": "cnf_…",
  "idempotencyKey": "mcp-3f9c0a…",
  "message": "A person must approve this action. Once they have, call the tool again with the same idempotencyKey."
}
```

The model calls the tool again with the same arguments and that `idempotencyKey` once the person has approved. The
retry reaches the same reservation draft, Better IAM finds the approval, and the reservation is placed. The default
server instructions tell the model to do exactly this.

**Waiting inside the call.** With `confirmations`, the tool polls instead of returning at once: it asks for the
confirmation's state every `intervalMs` (default 2 s) for up to `timeoutMs` (default 25 s). On `approved` it
retries once with the same key and returns the result; on `denied` or `expired` it returns
`{ status: 'confirmation-denied' | 'confirmation-expired', confirmationId, idempotencyKey }`; on a timeout it returns
`confirmation-required` as above.

`iamConfirmations(iam.api.delegations, { timeoutMs?, intervalMs?, now? })` builds that poller per request from
Better IAM's `delegations.getConfirmation`, called with the caller's own bearer token in the caller's tenant, so an
agent only ever sees its own requests. It maps `rejected` to `denied`, and a `pending` request past its `expiresAt`
to `expired`. Without a bearer token or a tenant it returns nothing and the tool answers `confirmation-required`.

<Callout type="warn" title="Stop on a rejection">
  A retry after the person rejected is decided again, denied again, and opens a new confirmation request. Tell your
  agent to stop on `confirmation-denied`, and to start over with a new request (and key) after
  `confirmation-expired`.
</Callout>

## Limits worth knowing

- `exec_command` is off unless you pass `execCommand: true`, and even then it only runs `inventory.refresh`,
  `logs.collect` and `node.reboot`. `node.reboot` restarts the machine.
- `run_diagnostic` runs `diag.nvml` only. It returns the queued command; the result arrives when the node finishes,
  and `node_status` or the command's own methods show it.
- `reserve_gpus` always books with `binding: 'hold'`; whole-node leases, spot, gangs and calendar starts are not
  exposed as tool arguments.
- `release_reservation`, `stop_instance` and `delete_instance` are marked destructive: many MCP hosts ask the user
  before calling such a tool.
- The server is stateless, with JSON responses only: it does not open SSE streams or send server notifications, and
  `tools.listChanged` is `false`. It negotiates protocol versions `2025-06-18`, `2025-03-26` and `2024-11-05`,
  answering with the newest when the client asks for another.
