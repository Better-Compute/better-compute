A VM is not much use until you know its address. Better Compute keeps networking deliberately small: an address
plan per hosted pool, whatever the runtime or the provider reports, and, on provider accounts that support them,
[tenant networks](#tenant-networks) the provider builds. Software-defined networking of its own beyond bridges, VLANs
and IPAM is a non-goal for v1, as is live migration.

Where an instance's addresses come from depends on its pool:

| Pool                        | Addresses                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Hosted (`vps-host`)         | One IPv4 lease from the pool's range, taken at placement, plus any addresses the host's runtime reports.          |
| Hosted, no range configured | Only what the runtime reports.                                                                                     |
| Provider (`provider`)       | What the provider reports for the machine, replaced on every poll.                                                 |

## Give a hosted pool a range

Pool IPAM is one IPv4 range per hosted pool. You configure it with `setIpPool`, a function exported by
`@better-compute/vps`. There is no API method, CLI command or FleetConfig field for it in this release, so run it
from your own setup code against the compute database:

```ts title="setup-ipam.ts"
import { setIpPool } from '@better-compute/vps';

const range = await compute.context.sql.transaction((tx) =>
  setIpPool(tx, { poolId: 'pool_01jz…', cidr: '10.0.0.0/24', gateway: '10.0.0.1' }),
);
// → { poolId: 'pool_01jz…', cidr: '10.0.0.0/24', gateway: '10.0.0.1',
//     firstHost: '10.0.0.2', lastHost: '10.0.0.254' }
```

    dns: { type: 'string[]', description: "DNS servers for the guests (ip_pools.dns, migration vps/0019_ip_pool_dns; 387c22f). Empty: guests keep their image's resolvers.", default: '[]' },

/>

`firstHost` and `lastHost` must both lie inside `cidr`, with `firstHost` not after `lastHost`. Anything else,
including a malformed address, is `INVALID_INPUT` naming the pool. Because the default `firstHost` is the address after
the gateway, set it explicitly when the gateway sits at the end of the network (`10.0.0.254` in a `/24`).

Calling `setIpPool` again for the same pool replaces the range. Existing leases are kept as they are, even if they now
fall outside it.

## How leases work

A hosted instance takes its lease in the same transaction that places it, right after capacity claims its resources on
a host (see [instances](/docs/guides/vps/instances)):

- The lease is the lowest free address from `firstHost` to `lastHost`, skipping the gateway.
- An instance holds at most one lease. Placing an instance that already holds one returns the same address.
- `(pool, address)` is the primary key of `ip_leases`, so two instances can never hold the same address. Concurrent
  placements that race for one address retry, up to 8 times, on the next free one.
- When the range is exhausted, placement fails with `CAPACITY_UNAVAILABLE` ("Pool … has no free IP address"). In
  `instances.create` the whole transaction rolls back, host claims included, and the caller gets the error. When the
  reconciler places an instance later (after a host loss), the instance moves to `error` with an `Unschedulable`
  condition.
- A pool without a range leases nothing, and placement succeeds without an address.

The lease is returned when the instance is deleted. After a host loss with `recreateOnHostLoss`, the instance returns
its lease with its allocation and takes a new one, again the lowest free address, when it is placed on another host.

For example, with `cidr: '10.0.0.0/29'` and `gateway: '10.0.0.1'`, the range is `10.0.0.2` to `10.0.0.6`: five
instances get `.2` to `.6` in order, and a sixth create fails with `CAPACITY_UNAVAILABLE` until one of them is deleted.

Operators can see the plan and the leases in the database:

```sql
SELECT cidr, host(gateway) AS gateway, host(first_host) AS first, host(last_host) AS last
  FROM ip_pools WHERE pool_id = $1;

SELECT host(address) AS address, instance_id
  FROM ip_leases WHERE pool_id = $1 ORDER BY address;
```

The v0.3 acceptance run (`tests/vps-churn.test.ts`) checks that after 200 instances churn on 3 hosts there is exactly
one lease per placed instance, none leaked and none shared.

## Addresses on an instance

`Instance.addresses` starts with the lease, if any. After that:

- **Hosted pools.** Addresses in the host's `StatusReport.instances` (from the guest agent or DHCP leases, CIDR form
  on the wire) are added to the list. Reports only add; the lease stays first.
- **Provider pools.** Each poll replaces the list with the machine's addresses. Hetzner Cloud reports the public IPv4
  address, the public IPv6 network as Hetzner gives it (a `/64`), and private network addresses. Proxmox VE reports
  the guest agent's addresses while the VM runs, without loopback and link-local ones, and nothing without an agent.
  Proxmox clones are configured with `ipconfig0=ip=dhcp`, so the guest takes its address from your cluster network's
  DHCP.

## What reaches the host

A hosted instance's network reaches its host in `InstanceSpec.nics`, in the `instances` section of the
<Term id="nodespec">NodeSpec</Term>. vps sends one NIC per instance:

| Field | Value |
| --- | --- |
| `network` | The host bridge: `br0`, or `vps({ hostNetwork })` |
| `mac` | A stable locally administered MAC: `02` followed by the first 10 hex digits of the SHA-256 of the instance id |
| `addresses` | The IPAM lease in CIDR form (the address with the range's prefix length), or none without a lease |
| `gateway` | The range's gateway, for a NIC with a lease (387c22f) |
| `nameservers` | The range's `dns`, for a NIC with a lease, when it has any (387c22f) |

**The guest's network configuration.** Since 0791fc9 bcd writes a cloud-init `network-config` (version 2) into the
NoCloud seed of `libvirt-kvm` and `cloud-hypervisor` guests when a NIC has static configuration: each such NIC matched
by its MAC, its addresses static, a default route (`0.0.0.0/0`, or `::/0` for an IPv6 gateway) through its gateway, and
its nameservers. A NIC without addresses keeps DHCP, and with no static NIC at all bcd writes no `network-config`, so
the image's own fallback (DHCP on the first NIC) stays. bcd parses every value and quotes it again, so a malformed
lease fails the seed rather than adding YAML to it. A bcx runtime plugin gets each NIC's gateway and nameservers in its
spec.

The NodeSpec encoder keeps NIC order, since it is the guest's interface order. The spec also carries the instance's
`allocationId`, which the host names when it fetches the user data. The FakeDaemon's fake hypervisor creates a tap
per NIC. On a host build with `virsh`, bcd's `libvirt-kvm` runtime (362317c) attaches each NIC as a virtio device on
the named bridge with the spec's MAC, on a tap named `runtime.TapName`, so bcd's nftables rules for the NIC exist
before the tap does. bcd's `cloud-hypervisor` runtime (2598f0a) creates a persistent tap of the same name
(`ip tuntap add`), puts it on the named bridge and brings it up before the VMM starts, then gives it to the VM with
the spec's MAC (933c51b). A guest reboot reopens that same tap, a tap that cannot be attached means the VM does not
start, a NIC without a network is refused, and the taps are deleted when the VM stops or is destroyed. Both have been
tested against fake tools only, not on a real host. A VPS profile can already declare `network: { mode: 'bridge', ipam: 'pool' }`
(see [steps and profiles](/docs/extending/steps-and-profiles)), but `vps()` does not read profiles.

### bcd's nftables tables

Every instance tap is named `bc<10 hex digits>n<nic>` (`runtime.TapName`), and bcd owns three nftables tables, which
it replaces together in one transaction before any domain starts:

| Table | Holds |
| --- | --- |
| `bridge bcd_instances` | The per-tap rules: anti-spoofing (the NIC's MAC and addresses), the `private` and `none` network policies, sandboxes' SSH-from-the-host-only rule, and the drops every tap gets (DHCP server replies, router advertisements and redirects, the host's own addresses). See [sandbox networks](/docs/guides/vps/sandboxes#network) |
| `inet bcd_taps` | A backstop (933c51b): `iifname "bc*" drop` on the input and forward hooks, and `oifname "bc*" drop` on forward and (since b12c217) output. Frames of a tap that is on its bridge reach these hooks as the bridge's, so only a tap off its bridge, which the bridge table cannot see, is dropped here. With no instance NIC on the host the table is deleted and not loaded again |
| `arp bcd_taps` | The same backstop for ARP, which the inet hooks never see (b12c217): `iifname "bc*" drop` on input and `oifname "bc*" drop` on output. Present exactly when `inet bcd_taps` is |

A NIC on a bridge whose name starts with `bc` would match every tap rule, so it fails its instance. bcd's 5-second
check counts the rules of all three tables against what it loaded, and under
[privilege separation](/docs/daemon#privilege-separation) the root helper accepts a ruleset that names these tables
and no other.

## Tenant networks

On a provider pool whose provider supports networks (Google Compute Engine and DigitalOcean), a tenant builds its own private networks
through [networks](/docs/reference/api/networks) and [firewallRules](/docs/reference/api/firewall-rules), and the
provider runs them: a VPC per network, subnets in it, and firewall rules. The calls record what the tenant wants and
return at once; the `vps.networks` reconciler converges the provider.

```ts
const network = await compute.api.networks.create(
  { token },
  { tenantId, poolId, name: 'prod', idempotencyKey: 'net-prod' },
);
await compute.api.networks.addSubnet(
  { token },
  { tenantId, networkId: network.id, name: 'app', region: 'us-central1', cidr: '10.10.0.0/24' },
);
// Once the network has been ready once, instances can be created on it.
const vm = await compute.api.instances.create(
  { token },
  { tenantId, poolId, flavor, imageId, sshKeys, networkId: network.id, idempotencyKey: 'vm-1' },
);
await compute.api.firewallRules.create(
  { token },
  {
    tenantId,
    networkId: network.id,
    name: 'ssh',
    direction: 'ingress',
    rules: [{ protocol: 'tcp', ports: ['22'] }],
    sources: ['0.0.0.0/0'],
    targets: { instanceIds: [vm.id] },
  },
);
```

- **Whose it is.** A network is its tenant's (`compute-network`, a child of `compute-tenant`, decided on
  `compute:networks:*`), on a provider pool the tenant owns or is offered. Another tenant's network is `NOT_FOUND`
  in your tenant, and naming another tenant is `ACCESS_DENIED` before any decision. A rule targets only the tenant's
  own instances on that network, and `instances.create` takes only the tenant's own `networkId`: another tenant's
  is `INVALID_INPUT`, worded as for one that does not exist. The platform (root callers) may act on any tenant's
  networks. See [platform-issued compute](/docs/guides/vps/providers#platform-issued-compute).
- **Names.** A network's name is unique among the tenant's networks that are not deleted; a deleted network's name
  is free again. A retried create with the same `idempotencyKey` returns the same network for the same caller.
  At the provider every resource is named `bc-` and its lower-cased id, and each instance's machine carries the tag
  `bc-` and 16 hex digits of the sha256 of its instance id, which rules that name instances target.
- **States.** A network's `state` (`pending`, `ready`, `deleting`, `deleted`, `error`) covers the VPC and its
  subnets; each subnet and each rule has its own. A rule the provider refuses is `error` on the rule without taking
  the network out of `ready`. The reconciler publishes `network.*` events and re-applies drift every five minutes.
- **Tags.** The reconciler applies rules first, then tags the instances that own their machine (an attached one once
  claimed, never one that lost its machine); a tag set after its rule still matches. Tags set within the last hour
  are skipped, so a large network is tagged over several runs, and a tag removed by hand comes back within the hour.
- **Instances.** `instances.create` with `networkId` (and `subnetId`, or the network's only subnet in the offer's
  region) needs a network that has been provisioned (it reached `ready` once; one back in `pending` because a subnet
  or rule was added still takes instances), is not being deleted, and a `ready` subnet. A network not provisioned
  yet, or a subnet not ready yet, is `INVALID_STATE`, so retry. Attached machines keep their network and are linked to
  the tenant network their NIC is on.
- **Deletion.** `networks.delete` and `removeSubnet` are `INVALID_STATE` while instances are on them. The reconciler
  deletes rules, then subnets, then the VPC. A provider account with a network that is not deleted cannot be deleted.
- **Shared project quotas (Google Compute Engine).** All tenants' networks on one provider account live in that account's single project, so
  they share its quotas for VPC networks, subnetworks and firewall rules: what one tenant creates, the others on the
  account cannot. vps caps each tenant at 10 networks that are not deleted, and each network at 16 subnets and 100
  firewall rules (`QUOTA_EXCEEDED`, the cap in `details.limit`). Size the project's quotas for the tenants you offer
  the pool to, or give a tenant that needs more its own account (with its own key) and project.

### On DigitalOcean

DigitalOcean has no network object and no firewall priorities, so the
[DigitalOcean provider](/docs/guides/vps/providers#digitalocean) maps the same calls onto its VPCs, Cloud Firewalls and
tags. The tenant-facing behaviour above holds; these are the differences.

- **Subnet regions.** A DigitalOcean account has no zones, so a subnet's region must be one of the account's `regions`
  (vps reads `regions` as well as the zones of Google Compute Engine accounts). Any other region is `INVALID_INPUT`.
- **Provider-side names.** The provider names things by the provider-side names vps hands it (`bc-` and the lower-cased id of the
  network, subnet or rule), not by the tenant's display names. Below, "the network" and "the subnet" are those names.
- **A VPC per subnet.** DigitalOcean VPCs are regional, so each subnet is a VPC of its own, named by its provider-side
  name (`bc-<id>`), with the subnet's range and the description `bc:network=<network>` (the network's provider-side
  name). The range is an RFC 1918 IPv4 CIDR from /16 to /28 and
  may not overlap another VPC of the account. A VPC of that name that exists with another range, region or network is
  `INVALID_STATE` (`subnetDrift`). Deleting a subnet whose VPC still has members stays `pending` until they are gone.
- **The base firewall.** A network is its base firewall `bc-base-<net16>` (`net16` is 16 hex digits of the sha256 of
  the network's provider-side name). It targets the tag `bc-net-<net16>`, which every instance created on the network carries from its
  first boot, and has no inbound rule and an allow-all outbound rule: the "deny ingress, allow egress" of any other
  provider. The network is `ready` once that firewall exists.
- **A rule is a Cloud Firewall** named `<rule>.n<net16>.p<priority>`. DigitalOcean firewalls carry neither a network
  nor a priority, so the name does. A rule with no targets applies to the network's member tag; the tags a rule
  targets replace that. A firewall is applied in the background: the rule is `pending` until DigitalOcean reports it
  applied, and `error` (applied again on the next run) if it failed.
- **Priorities are refused when they can't be kept.** DigitalOcean applies every firewall that matches an instance, and
  a deny always wins, so a ruleset in which an allow has a lower priority number than an overlapping deny of the same
  network and direction can't be expressed. The provider checks each allow it applies against the denies DigitalOcean
  already holds; a deny is never checked and always applies. So in whichever order vps reconciles the pair, the deny
  is applied and the allow ends in `error` with `UNSUPPORTED` (reason `firewallPriority`) on its own reconcile: the
  ruleset is enforced more strictly than written, never more loosely. An allow that was applied before the deny
  arrived stays applied but is no longer updated; the deny wins at DigitalOcean for the traffic they share, so it
  opens nothing. Read the allow's error message, then fix or remove the inversion. Addresses on the wrong side of a rule
  (destinations on an ingress rule) and an `mtu` other than 1500 are `UNSUPPORTED` too.
- **An attached instance outside the network's VPCs.** DigitalOcean denies what no firewall allows. An attached
  Droplet that a rule targets, but that sits outside the network's VPCs, is covered by that rule's firewall alone,
  which allows only what the rule says, so it loses egress.
- **Only its own names are touched.** The provider replaces and deletes only firewalls whose names have exactly the
  shape above and VPCs whose description names a network. A `bc-r1.prod` firewall or a VPC made by hand is left alone.

What is not there at all: IPv6 ranges, more than one range or lease per instance, and an API to manage ranges. Tunnels
give you exec, SSH and single-port TCP access without routing to the instance network; see [tunnels](/docs/guides/access/tunnels).
