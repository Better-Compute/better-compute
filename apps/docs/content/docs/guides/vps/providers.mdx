A provider pool runs its instances on someone else's infrastructure: a public cloud, or a hypervisor cluster you
operate but do not want to run bcd on. Better Compute splits this the way it splits every extension point: **code
registers kinds, data configures instances**.

- A <Term id="provider">provider</Term> is code: a `defineProvider()` definition such as `hetzner-cloud`, passed to
  `vps({ providers })`.
- A <Term id="provider-account">provider account</Term> is data: a row naming a provider, with a config validated by
  that provider's manifest. Its credentials are secret references, never values.
- A pool of class `provider` points at one account. Its instances are created, polled, powered and deleted through the
  account's client by the `vps.instances` reconciler (see [instances](/docs/guides/vps/instances)).

```ts title="compute.ts"
import { vps } from 'better-compute/vps';
import { hetznerCloud } from '@better-compute/provider-hetzner';
import { proxmoxProvider } from '@better-compute/provider-proxmox';
import { gcp } from '@better-compute/provider-gcp';

vps({ providers: [hetznerCloud, proxmoxProvider({ writeSnippet }), gcp] });
```

The provider packages are on npm like the rest of Better Compute, but sit outside the `better-compute` umbrella:
install them by their own names (`npm install @better-compute/provider-hetzner @better-compute/provider-proxmox @better-compute/provider-gcp`).

## Provider accounts

### Credentials first

An account config never holds a credential. Fields declared with `field.secret()` accept only a `SecretRef`:
`secret://…`, `vault://…` or `env://…`. On top of the manifest, vps refuses any string field whose name ends in
`token`, `secret`, `password` or `key` that is not a reference, at any depth, with `INVALID_INPUT`.

Store the value first. [secrets.put](/docs/reference/api/secrets#put) (`compute:secrets:manage`) writes it to the
configured secret store and answers with its reference; nothing ever reads it back through the API:

```ts
const { ref } = await compute.api.secrets.put(
  { token },
  {
    tenantId: 'root',
    name: 'hcloud-token',
    value: process.env.HCLOUD_TOKEN!,
    idempotencyKey: 'hcloud-token-1',
  },
);
// ref: 'secret://root/sec_…'
```

References are resolved when a client needs them, through `vps({ secrets })` if you passed a resolver, otherwise the
server's secret broker, which routes each reference to the store serving its scheme. The default store, pki's
local-sealed store, serves `secret://` only. An `env://` or `vault://` reference resolves only if you configure a
`SecretStore` for that scheme in `betterCompute({ secrets })` (the list replaces the default) or pass your own
resolver to `vps()`.

### Whose references an account may name

An account's references are scoped to its tenant, for every provider. An account of the root (platform) tenant may
name any `secret://`, `vault://` or `env://` reference. An account of any other tenant may name only
`secret://<its tenant>/…`, the secrets that tenant put with `secrets.put`, and the `vault://` paths you allow it:

```ts
vps({
  providers: [hetznerCloud, gcp],
  // An entry ending in / allows every path under it; any other entry allows that one path.
  tenantVaultPaths: { org_acme: ['kv/tenants/acme/'] },
});
```

`env://` stays the platform's: it reads the control plane's own environment. A tenant's account naming `env://`,
a `vault://` path it is not allowed, the platform's secrets or another tenant's would run on credentials that are
not the tenant's, so `providerAccounts.create` and `update` refuse it with `INVALID_CONFIG` (`details.path` names the
field, `details.reason` is `secretRefScope`). The rule holds again when a client resolves the account's references:
an account stored before it, or written around the API, fails that call with `ACCESS_DENIED` and nothing is read.
A tenant's references reach the store with the tenant as the resolve context (`resolve(ref, { tenantId })`): the
local-sealed store then serves only a secret stored for that tenant, and a `SecretStore` of your own for `vault://`
gets the same context to check against. The root tenant is the deployment's `rootTenantId`, given to
`betterCompute()` or named by the IAM port (`bridge.embedded(iam, { rootTenantId })`): modules see it either way.

### A pool on the account

```ts
const pool = await compute.api.pools.create(
  { token },
  { tenantId: 'root', siteId, class: 'provider', providerAccountId: account.id },
);
// agent is 'none': a provider pool's machines are reached through the provider
```

A provider pool needs `providerAccountId`, and its `agent` must be `none`. Only provider pools take an account.

## Discovery and attach

A provider that can list every machine of an account (`discover`, Google Compute Engine today) lets you hand a VM that
already runs to a customer tenant without recreating it.

- **The `vps.discovery` worker** lists each such account every `vps({ discovery: { every } })` (default `5m`) into
  `provider_machines`, and publishes `provider.machine.discovered`, `changed` and `gone`. It never changes a machine.
  [machines](/docs/reference/api/provider-accounts#machines) reads what it saw, and
  [discover](/docs/reference/api/provider-accounts#discover) runs a pass now (`wait: true` holds the answer for at
  most 30 s).
- **[instances.attach](/docs/reference/api/instances#attach)** turns a free machine into an instance of a tenant's
  provider pool backed by the same account. The instance is owned by `ownerIdentityId`, takes the machine's own shape
  as its flavor, and is charged to the tenant's quota. Only the platform attaches from accounts its own tenant does
  not own. The reconciler then writes the ownership label (`claim`) and adopts the machine as it is, running or
  stopped.
- **The tenant controls it** like any instance: `get`, `list`, `start`, `stop`, `reboot` and `delete`.
  `onDelete: 'detach'` (the default) removes the label and leaves the machine running; `'delete'` deletes it.
  [instances.detach](/docs/reference/api/instances#detach) always detaches.
- **Ownership is re-checked on every read.** A machine whose label is gone or names another instance fails its
  instance with `OwnershipLost` (`AttachConflict` when the first claim was refused). vps never powers, deletes or
  relabels it again, and deleting the instance finishes as a detach without a provider call. An instance whose
  machine id a live instance already holds fails with `DuplicateMachine` instead of retrying.
- **Networks.** An attached machine keeps its network. When its NIC is on one of the tenant's
  [networks](/docs/guides/vps/networking#tenant-networks) on the same account, the instance is linked to it; a
  network being deleted refuses the attach with `INVALID_STATE`.
- **Auto-attach** is opt-in (owners: see below). With `vps({ discovery: { autoAttach: { ownerIdentityId } } })`, a free machine labelled
  `better-compute-tenant=<tenant>` and `better-compute-pool=<pool>` is attached to that pool after each pass
  (`onDelete: 'detach'`), owned by the identity in its `better-compute-owner` label or else `ownerIdentityId`.

## Provider reservations

A provider that can list capacity reservations (`listReservations`, Google Compute Engine today) has them detected and
offered as capacity that tenants create instances on.

- **The `vps.reservations` worker** asks each such account every `vps({ reservations: { every } })` (default `5m`)
  and publishes `provider.reservation.detected`, `changed`, `ready` and `gone`.
  [reservations](/docs/reference/api/provider-accounts#reservations) lists them with `free` (`total - inUse - pending`)
  and `pending` (creates admitted that the last scan may not have counted). `free` can be one pass behind the
  provider.
- **[bindReservation](/docs/reference/api/provider-accounts#bindreservation)** makes a `ready` reservation a flavor
  (default name `rsv-<name>`) of a provider pool of the account. A `scheduled` (future) reservation is listed and
  evented, and `provider.reservation.ready` fires when it is fulfilled, but it can be bound only once it is ready,
  because the provider fulfils it under a new id.
- **Admission.** `instances.create` on a bound flavor takes a free slot under a lock on the reservation, so concurrent
  creates never over-commit it; with none free it is `CAPACITY_UNAVAILABLE` with the counts in `details`. The provider
  stays the final referee: a create it refuses fails the instance with `ProvisionFailed`, and the slot is free again.
- **[unbindReservation](/docs/reference/api/provider-accounts#unbindreservation)** removes the binding. The flavor is
  deleted, or archived while instances use it; the worker does the same when a bound reservation goes away.

## Platform-issued compute

The root (platform) tenant adds compute once and issues it to customer tenants, which then use and control what they
were given. The account, its credentials, the pool and its quotas stay the platform's.

1. **A root account.** The root tenant creates the provider account (`providerAccounts.create` in its own
   tenant). A root account may use the host's own credentials (ruling F1); a tenant's own account must name its key.
2. **A root pool, offered.** A `class: 'provider'` pool on that account (`pools.create`), flavors on it
   (`flavors.create`, or `providerAccounts.bindReservation` for a reservation), offered to each customer with a
   quota (`pools.offer`, `quotas.set`).
3. **Issue.** Attach a VM that already runs (`instances.attach` with the customer's `tenantId` and an
   `ownerIdentityId` of theirs; discovery lists the account's VMs), or create a new one (`instances.create` with
   the customer's `tenantId` and `ownerIdentityId`). The instance is the customer's: it shows in the owner's
   default `scope: 'mine'` list, owner-conditioned policies (`resource.ownerId`) apply to them, and it is
   charged to the customer's quota.
4. **The customer uses it.** With grants in its own tenant the customer lists, reads, starts, stops, reboots and
   deletes it (an attached VM's `onDelete: 'detach'` hands it back running), creates instances of its own on the
   offered pool (a reservation-backed flavor included), and builds
   [networks](/docs/guides/vps/networking#tenant-networks), subnets and firewall rules on it.

| Who                                                                           | Can                                                                                                                                                           | Cannot                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Root (root realm, root administrator, user session with MFA: `ROOT_OVERRIDE`) | Everything above, in any tenant, decided in the tenant that holds the resource                                                                                | Bypass state rules (an account still in use is `INVALID_STATE`)                                                                                                                                                                                                                                                                                                                                    |
| A customer tenant, with grants in its own tenant                              | `instances:*` on its instances, `networks:*` on its networks, its own provider accounts (with their own key), pools on those, attach and reservations on them | Read or change a root account (`get`, `offers`, `machines`, `discover`, `reservations`, `bindReservation`, `unbindReservation`, `bootstrap`, `update`, `delete`); build a pool on an account that is not its own; attach from a root account; change the root pool, its offers or flavors; set quotas; make anyone but itself the owner of an instance (`ownerIdentityId` on `create` or `attach`) |
| Another customer tenant                                                       | The same, for its own resources                                                                                                                               | See or act on the first tenant's instances, networks and rules; target them in its rules; put instances on its networks                                                                                                                                                                                                                                                                            |

IAM is the first gate: a tenant's grants are decided in its own tenant, on resources compute projects there. Compute
then holds these rules itself, so a tenant holding `compute:*` in its own tenant still cannot use them to reach
root-level resources or another tenant's:

- Naming another tenant's `tenantId`, the root tenant's included, is `ACCESS_DENIED` by the envelope before any IAM
  decision or database read. `quotas.set` is decided on the fleet, in the root tenant.
- Handlers read by `(id, tenantId)`: a root account, the management of the root pool (`pools.update`, `offer`,
  `unoffer`, `archive`, flavors) and another tenant's instances or networks are `NOT_FOUND` in the caller's own
  tenant.
- A provider pool runs only on an account of its own (owner) tenant: `pools.create` refuses another tenant's
  account as `NOT_FOUND`, worded as for an unknown one, and vps uses a pool's account only when the pool's owner
  owns it (instance creates and the provider reconciler, flavors, networks, reservation bindings). A pool offered to
  other tenants keeps working for them; they are not shown its `providerAccountId`.
- `instances.attach` from an account the caller's tenant does not own is the platform's only (`ACCESS_DENIED`).
  Only a root caller acting in another tenant makes anyone but itself the owner (`ownerIdentityId` on `create` and
  `attach`); when the IAM port can say (`IamPort.isMember`: the embedded better-iam bridge), the owner must be an
  active identity of that tenant (`INVALID_INPUT` otherwise). Ports without it check the id's shape only.
- A firewall rule's targets and an instance's `networkId` must be the tenant's own. Another tenant's are
  `INVALID_INPUT`, worded as for ones that do not exist.
- `providerAccounts.machines` on a tenant's own account does not name the instance or tenant holding a machine
  when that is another tenant (its pool was offered to it); the platform sees both.
- Label-driven auto-attach takes the `better-compute-owner` label only on a platform account, and only for an active
  member of the labelled tenant when the IAM port can say (else `autoAttachError` `AUTO_ATTACH_OWNER_REFUSED`, not
  attached). On a tenant's own account the label is the tenant's to write, so it is ignored: the configured
  `ownerIdentityId` gets the instance and `AUTO_ATTACH_OWNER_IGNORED` is recorded (with a
  `provider.machine.changed` event).
- A tenant's account names only its own secret references and never the host's ambient cloud credentials (see
  [Whose references an account may name](#whose-references-an-account-may-name) and the
  [Google Compute Engine](#google-compute-engine) section).

Not covered here: what a tenant may do in its own GCP project through its own key, and the platform's own operators,
who act with `ROOT_OVERRIDE` everywhere.

The IAM actions split the same way. Root-only by policy: `compute:providers:*` on root accounts,
`compute:instances:attach` from root accounts, `compute:quotas:manage`, and `compute:pools:share` and
`compute:flavors:manage` on root pools. Tenant-grantable: `compute:instances:*` (`attach` only from the tenant's
own accounts), `compute:networks:*` (on `compute-network`, a child of `compute-tenant` with `providerAccountId`,
`poolId` and `projectId` attributes) and `compute:providers:*` on the tenant's own accounts. An operator role
that controls what it was issued:

## Billing

The root tenant bills its customers for what it issues to them on its provider accounts: compute meters the VMs,
reservation slots, networks, disks and addresses, and Better IAM prices and invoices them. The whole model, prices
and budgets are in [Billing and usage](/docs/guides/iam/billing-and-usage); this is what a provider pool adds.

- **Billing modes.** A provider pool's `policy.billing.mode` is `metered` (vCPU, memory, GPU and per-VM lines, plus
  disks and public addresses), `platform-fee` (one `vm.managed.hours` line per running VM) or `none`. Root-owned
  pools default to `metered`; a pool on a tenant's own cloud account defaults to `platform-fee`, so a tenant is never
  charged compute it already pays its provider for. Only the platform sets the mode
  ([`pools.create`](/docs/reference/api/pools#create), `pools.update`).
- **What a VM records.** Usage comes from the instance's observed `running` and `stopped` spans, written with the
  lifecycle change: billing starts at the first observed `running` and ends at the observed stop, detach or delete,
  and a `lost` span is not billed. A stopped VM still bills its disks. A flavor with a root-set `billing.meter`
  (`flavor.<name>.hours`) bills one whole-shape line instead of the composed ones.
- **Attach.** [`instances.attach`](/docs/reference/api/instances#attach) takes `billing: 'metered' | 'none'`. Only
  the platform may write a VM off with `none`; a lent VM bills its tenant from its first observed `running` after
  the attach, never before.
- **Reservations.** A VM admitted against a bound reservation bills the `vm.reserved.*` meters. Root can commit
  slots of a reservation to one tenant for a term with
  [`reservationGrants.create`](/docs/reference/api/reservation-grants#create): the tenant pays
  `vm.grant.slot.hours` for every committed slot, used or not, gets priority on them, and its VMs inside the grant
  record no compute meters. While a grant is live, `unbindReservation` and `delete` on the account are
  `INVALID_STATE`.
- **Provider costs.** The `vps.costs` worker reads what the provider billed (Compute Engine: the BigQuery billing
  export named by `billingExport`) and attributes each row to a tenant by the `better-compute-instance` and
  `better-compute-tenant` labels. `billing.passThrough` rules on a root account bill costs compute does not meter
  itself, such as egress, at cost times a multiplier on a `reported` meter; the SKUs compute meters are refused as
  patterns and never passed through. Root reads its margin per tenant, pool, account or meter with
  `billing.margins`, and `billing.leak` flags a VM the provider billed for more hours than compute metered.
- **Budgets.** `instances.attach` (when billed) and `networks.create` (on a `metered` pool) are budget-checked like
  `instances.create`, against the target tenant's budgets when root issues into it. An offer with
  `onBudgetExceeded: 'suspend'` stops the tenant's running VMs in the pool and refuses its new work once its budget
  is spent.
- **Estimates.** Each item of `flavors.list` on a provider pool carries the hourly `estimate` for the caller's
  tenant, and `instances.estimate` answers it before a create.

## The provider contract

`defineProvider` checks a definition's shape up front and returns it frozen with `extension: 'provider'`. Every
refusal is `INVALID_CONFIG` with `details.path`:

```ts title="acme-cloud.ts"
import { ComputeError, field, manifest } from '@better-compute/core';
import { defineProvider } from '@better-compute/vps';

export const acmeCloud = defineProvider({
  id: 'acme-cloud', // lower-case letters, digits, hyphens
  version: '1.0.0',
  provides: ['vps'], // 'metal', 'vps' or both
  config: manifest({
    token: field.secret().describe('API token'),
    location: field.option(['fra', 'ams']).default('fra'),
  }),
  capabilities: ['power'],
  create: (config, context) => acmeClient(config, context), // returns a ProviderImpl
});
```

`create(config, context)` receives the validated config (secret fields still as references) and a
`ProviderContext` of `{ clock, secrets, log }`. Resolve the token with `context.secrets.resolve(config.token)` when
you call the API, not once up front.

The client is a `ProviderImpl`:

| Method                                             | Contract                                                                                                                                                                                                                                                          |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `listOffers(query)`                                | Offers matching the query; an impossible query returns `[]`.                                                                                                                                                                                                      |
| `create({ offerId, image, userData, name }, call)` | Idempotent by `call.idempotencyKey` (vps passes the instance id): a retried create returns the same machine.                                                                                                                                                      |
| `get(id, call)`                                    | The machine, or `undefined` when it does not exist.                                                                                                                                                                                                               |
| `delete(id, call)`                                 | A machine that is already gone counts as deleted: `NOT_FOUND` is success.                                                                                                                                                                                         |
| `power?(id, action, call)`                         | `on`, `off`, `graceful-off`, `reset`, `graceful-restart`, `cycle`, `nmi`. vps uses `on` and `graceful-off`; without `power`, a stop or start is `UNSUPPORTED` and fails the instance.                                                                             |
| `reinstall?`, `rescue?`, `list?`, `bootstrap?`     | Optional. `bootstrap` delivers a single-use join token to machines that will run bcd, and never through user data.                                                                                                                                                |
| `costs?(window, call)`                             | Optional ([billing](#billing)). The account's billed cost rows whose usage started in `[from, to)`, as `ProviderCostRecord`s in integer micros, each with a `sourceRowId` that stays the same when the provider re-exports the row. Read outside any transaction. |
| `listPrices?(query, call)`                         | Optional. The provider's list prices for `billing.proposePrices`, before any margin.                                                                                                                                                                              |

A machine is an `ExternalMachine`: `{ id, name?, state, offerId?, region?, addresses }`, with `state` one of
`pending`, `running`, `stopped`, `rescue`, `deleting`, `deleted`, `error` or `unknown`. Each call gets a
`CallContext` with `idempotencyKey`, an abort `signal`, `clock`, `secrets` and `log`.

A provider whose clients read costs also declares, on its definition, which of its SKUs compute meters itself:
`billing: { computeSku?, meteredSku? }`, two pure matchers over a cost row's `service`, `sku` and
`skuDescription`. `computeSku` (vCPU, memory, GPU, instance) is what leak detection counts; neither kind is ever
passed through, and a pass-through rule whose pattern either matches is refused. Pass-through rules are accepted
only for providers that declare them.

Throw `ComputeError`s. The reconciler records any failure as a `ProviderError` condition; `UNSUPPORTED`,
`INVALID_STATE` and `INVALID_CONFIG` fail the instance, and `CAPACITY_UNAVAILABLE` or `QUOTA_EXCEEDED` from `create`, or
from `get` before the machine has run, fail it with a `ProvisionFailed` condition instead; everything else (use
`PROVIDER_ERROR` and `RATE_LIMITED`) is retried. User data from vps carries only the tenant's SSH keys or the tenant's own cloud-init, so a provider never has
to filter secrets out of it. [Providers](/docs/extending/providers) walks through writing one end to end.

## Conformance

`providerConformanceCases()` from `@better-compute/vps` turns the contract into cases you run with `runConformance`
from `@better-compute/core/conformance`, in any test runner, against a live account, a recording or an emulator:

```ts title="acme-cloud.test.ts"
import { runConformance } from '@better-compute/core/conformance';
import { providerConformanceCases } from '@better-compute/vps';

const report = await runConformance(providerConformanceCases(), () => ({
  provider: acmeCloud,
  config: { token: 'env://ACME_TOKEN' },
  offerId: 'small', // an offer create accepts
  image: 'ubuntu-24.04', // an image create accepts
  context: { secrets, clock },
  prefix: `ci-${runId}`, // concurrent runs never share idempotency keys
}));
expect(report.failed).toEqual([]);
```

The cases check that the definition builds a client with the four required methods; that `listOffers` returns
well-formed offers including the subject's and nothing for `minVcpu: 1_000_000`; that a retried `create` names the
same machine; that `get` follows it, `delete` removes it and a second `delete` fails only with `NOT_FOUND`; and that
`power`, when offered, stops and starts it. Set `powerObservable: false` for providers that can act on power but not
report it. Every case cleans up the machines it made.

## Hetzner Cloud

`@better-compute/provider-hetzner` exports `hetznerCloud` (id `hetzner-cloud`, `provides: ['vps']`, capabilities
`power`, `reinstall`, `list`). Servers become the instances of provider pools.

- **Idempotent create.** The Hetzner API has no idempotency keys, so every server carries the labels
  `better-compute.io/managed=true` and `better-compute.io/idempotency-key=<key>`. `create` looks the key up first; if a
  concurrent create wins the unique server name, it returns the winner.
- **Names** are hostname-safe: `inst_01…` becomes `inst-01…`, at most 63 characters.
- **Offers** come from `/server_types` and `/datacenters`, following pagination: gross hourly prices in EUR for the
  account's location (or the queried `region`), `available` from that location's datacenters, deprecated types
  skipped. GPU and metal queries return nothing.
- **Power:** `on` is `poweron`, `off` is `poweroff`, `graceful-off` is `shutdown`, `reset` and `cycle` are `reset`,
  `graceful-restart` is `reboot`; `nmi` is `UNSUPPORTED`. `reinstall` is `rebuild`. `list` yields only managed
  servers.
- **Errors:** a 404 is absent (`get` answers `undefined`, `delete` and `power` throw `NOT_FOUND`); a 429 is
  `RATE_LIMITED` with `retryAfterMs` from `RateLimit-Reset`; anything else is `PROVIDER_ERROR` with
  `details: { status, code }`, and an unreachable API is `PROVIDER_ERROR` too.

`hetznerCloudProvider({ fetch, endpoint, labelKey })` builds the same provider with another transport, endpoint
(default `https://api.hetzner.cloud/v1`) or label key. `tests/provider-hetzner.test.ts` passes an in-memory emulator
of the servers, server types, datacenters and actions endpoints as `fetch`, and runs the conformance cases plus the
Hetzner specifics against it; the same hook can record or replay real traffic.

The package also exports `hetznerRobot` (`provides: ['metal']`), which claims existing Hetzner Robot dedicated
servers and bootstraps them into bcd hosts. That is platform hardware, not tenant VMs: see
[bare metal](/docs/guides/bare-metal). `providerAccounts.bootstrap` drives it for a `vps-host` or `metal-host` pool;
see [bootstrapping machines](/docs/extending/providers#bootstrapping-machines).

The image is a template's VMID or name. The token needs `VM.Clone` on the templates, plus `VM.Allocate`,
`VM.Config.*`, `VM.PowerMgmt`, `VM.Audit` and `Datastore.AllocateSpace` where VMs are created, and `Sys.Audit` for the
node headroom that offers report.

- **Idempotent create.** A key hashes (SHA-256) to a VMID slot in the account's range, and the clone records the key
  in its description. A slot held under another key probes the next one, up to 64. Retried and concurrent creates
  meet on one VMID, where PVE lets exactly one clone through; a clone interrupted before configuration is finished by
  the next create. No free slot is `CAPACITY_UNAVAILABLE`.
- **Configuration.** After cloning, create sets cores, memory and `ipconfig0=ip=dhcp`, grows the boot disk for sized
  offers (never shrinks it), tags the VM `better-compute` last and starts it. It reports `pending` until `get` sees it
  running.
- **Shared clusters.** `delete` and `power` act only on VMs tagged `better-compute` and refuse others with
  `ACCESS_DENIED`; `list` yields only tagged VMs; templates are never machines.
- **Tasks.** Clone, stop, delete and power wait for their task; a failed task is `PROVIDER_ERROR`. `taskPollMs`
  (default 1 s) and `taskTimeoutMs` (default 10 min) tune the wait.
- **Addresses** come from the QEMU guest agent while the VM runs; without an agent the list is empty.
- **Offers** are the configured sizes, `available` when an online node (or the pinned `node`) has the CPUs and free
  memory.
- **Power:** `on`, `off`, `graceful-off`, `reset`, `graceful-restart`, and `cycle` as stop then start; `nmi` is
  `UNSUPPORTED`. `reinstall` destroys the VM and clones the new template into the same VMID, keeping its key, name,
  size, disk size and cloud-init volume.

<Callout type="warn" title="Proxmox needs writeSnippet under vps">
  The PVE API cannot upload cloud-init snippets, so without `proxmoxProvider({writeSnippet})` a
  create refuses any user data beyond an empty `#cloud-config` with `UNSUPPORTED`. vps always
  renders at least a hostname into user data, so an account used by vps needs `writeSnippet`;
  otherwise every instance ends in `error`.
</Callout>

```ts
import { proxmoxProvider } from '@better-compute/provider-proxmox';

export const proxmox = proxmoxProvider({
  // Write the snippet where the cluster reads it (SFTP, a shared mount), and return its volume id.
  writeSnippet: async (name, content, call) => {
    await snippets.write(name, content); // your transport
    return `local:snippets/${name}`;
  },
  // Self-signed cluster: a fetch bound to a dispatcher that pins the cluster CA.
  fetch: pinnedFetch,
});
```

The account's service account needs `roles/compute.instanceAdmin.v1` (instances, labels, tags and consuming
reservations; on the owner and consumer projects for shared reservations), `roles/compute.networkAdmin` (networks
and subnets), `roles/compute.securityAdmin` (firewalls) and `roles/compute.viewer` (discovery, reservations and
future reservations), plus `roles/iam.serviceAccountTokenCreator` on the target when `impersonate` is set.

- **Billing.** Disks are reported with their types, so attached VMs bill their real disks. With `billingExport`,
  the account's client reads costs (`costs`) from the detailed BigQuery export, and `listPrices` reads the Cloud
  Billing Catalog for `billing.proposePrices`. The export has to be turned on by hand in the Cloud Console, and the
  service account needs `roles/bigquery.dataViewer` on the export dataset and `roles/bigquery.jobUser` on its
  project; the account's project needs the Cloud Billing API for list prices. The provider-gcp README has the setup.
  Compute Engine's core, RAM, GPU and instance SKUs, persistent disk and Hyperdisk capacity, local SSD and external
  IP charges are the ones compute meters itself, so they are never passed through.

- **Ids.** A VM is `zone/name`, named `bc-` and the lower-cased instance id. An offer is `zone/machineType`, or
  `zone/machineType@reservation` for capacity a reservation holds, which create consumes by name.
- **Idempotent create.** GCE's `requestId` is a UUIDv5 of the idempotency key. create does not wait for the insert;
  the reconciler polls `get`, which answers for a VM GCE does not show yet from its insert operation: `pending` while
  the operation runs, its error once it failed.
- **Failed creates end.** A stockout (`ZONE_RESOURCE_POOL_EXHAUSTED`, mapped to `CAPACITY_UNAVAILABLE`) or a quota
  error, at once or after GCE accepted the insert, moves the instance to `error` with `ProvisionFailed` and publishes
  `instance.failed`. It is not retried, keeps its quota until it is deleted, and deletes without a VM.
- **Ownership labels.** create labels the VM `better-compute-managed=true` and `better-compute-instance=<id>`. Attach
  writes `better-compute-instance` only, and `better-compute-managed` just before an `onDelete: 'delete'` deletion.
  `delete` acts only on managed VMs and `power` only on VMs carrying the instance label.
- **Power:** `on` is start, `off` and `graceful-off` stop, `reset` and `cycle` reset, and `graceful-restart` is a
  stop (waited for, at most 20 s) then a start; `nmi` is `UNSUPPORTED`.
- **Credentials.** A key is exchanged for tokens at the OAuth endpoint and cached until a minute before expiry;
  without one the host's own identity is used: `gcpProvider({ tokenSource })` (a workload-identity client), else the
  metadata server. That identity is the control plane's, so only an account of the root (platform) tenant may rely on
  it: a tenant's account must name its own key in `credentials` or sign in keyless with `federationAudience` (see
  [keyless GCP accounts](#keyless-gcp-accounts)); `impersonate` alone is not enough, and without either
  `providerAccounts.create` and `update` refuse the account with `INVALID_CONFIG`. A `tokenSource` never overrides an account's
  `credentials`. The key must be the tenant's own (`secret://<tenant>/…`, see
  [above](#whose-references-an-account-may-name)). Tokens are never logged.
- **Pinned token endpoint.** The key JSON is the tenant's, and the control plane POSTs the signed JWT to its
  `token_uri`. So `token_uri` must be absent (the default), `https://oauth2.googleapis.com/token`, or its older alias
  `https://accounts.google.com/o/oauth2/token`, compared exactly; any other value, such as an address inside the
  platform's network, is `INVALID_CONFIG` (`details.reason` `tokenUri`) on the first call that needs a token, and
  nothing is fetched.
- **Errors** map to `ComputeError` codes (`NOT_FOUND`, `CONFLICT`, `RATE_LIMITED` with `retryAfterMs`,
  `QUOTA_EXCEEDED`, `ACCESS_DENIED`, `INVALID_INPUT`, `UNAVAILABLE`), with `details: { provider: 'gcp', status, reason }`.

### Keyless GCP accounts

A tenant need not hand over a service-account key. With `federationAudience`, the control plane signs in to the
tenant's own project through [workload identity federation](https://cloud.google.com/iam/docs/workload-identity-federation):
Better Compute is the OIDC issuer (`pki.workloadIssuer`, served at `{basePath}/workload/.well-known/openid-configuration`
and `{basePath}/workload/jwks.json`), and the tenant's workload identity pool provider trusts it. The host must run a
workload issuer; without one an account naming `federationAudience` is `INVALID_CONFIG` (`details.reason`
`noWorkloadIssuer`). An account names either `credentials` or `federationAudience`, never both
(`credentialsAndFederation`).

Every account has exactly one subject, `compute-account:<tenantId>/<provider>/<name>`, which vps alone builds. The
tenant's pool provider must trust that subject and no other: a broader condition, such as one matching every subject
that starts with `compute-account:`, would let one account, or one tenant, act as another. `providerAccounts.create`
and `update` check this before the account is stored (see the errors below).

1. **Ask for the setup.** Call `providerAccounts.federationSetup` with the `provider` and the `name` you will give
   `create`. It calls no provider and stores nothing, and answers with the exact values to use:

   ```ts
   const setup = await compute.api.providerAccounts.federationSetup(
     { token },
     { tenantId: 'org_acme', provider: 'gcp', name: 'gcp-main' },
   );
   // → {
   //   issuer: 'https://compute.example.com/api/compute/workload',
   //   jwksUri: 'https://compute.example.com/api/compute/workload/jwks.json',
   //   subject: 'compute-account:org_acme/gcp/gcp-main',
   //   attributeCondition: 'assertion.sub == "compute-account:org_acme/gcp/gcp-main"',
   //   allowedAudienceHint: 'https://iam.googleapis.com/projects/<PROJECT_NUMBER>/locations/global/workloadIdentityPools/<POOL>/providers/<PROVIDER>',
   // }
   ```

   An unknown `provider` is `INVALID_INPUT`, as in `create`; a host with no workload issuer is `INVALID_CONFIG`
   (`details.reason` `noWorkloadIssuer`). Give `create` the same `provider` and `name`: the subject is derived from
   them, so another name is another subject.

2. **Create a workload identity pool** in the tenant's project:

   ```sh
   gcloud iam workload-identity-pools create my-pool \
     --project=my-project \
     --location=global \
     --display-name="Better Compute"
   ```

3. **Create an OIDC provider** in the pool that trusts the `issuer`, maps the subject, and admits exactly the
   `attributeCondition` from step 1:

   ```sh
   gcloud iam workload-identity-pools providers create-oidc my-provider \
     --project=my-project \
     --location=global \
     --workload-identity-pool=my-pool \
     --issuer-uri=https://compute.example.com/api/compute/workload \
     --attribute-mapping=google.subject=assertion.sub \
     --attribute-condition='assertion.sub == "compute-account:org_acme/gcp/gcp-main"'
   ```

   Google fetches the issuer's discovery document and keys itself, so the issuer URL must be reachable from the
   internet. For an issuer Google cannot reach, download the keys from `jwksUri` (`curl -o jwks.json <jwksUri>`) and
   add `--jwk-json-path=jwks.json` to the command. Uploaded keys are a copy, and Google accepts no token signed by a
   key it was not given. The operator announces a rotation ahead of time and publishes the next key in `jwks.json`
   beside the current one before it signs anything: as soon as `jwks.json` lists a key your upload lacks, download
   it again and update the provider (`gcloud iam workload-identity-pools providers update-oidc` with
   `--jwk-json-path=jwks.json`) within the announced window. Uploading only after the issuer has switched keys leaves the account unable to
   authenticate until you do. The provider's default allowed audience is its resource name as an `https://` URL, the
   `allowedAudienceHint` with your project number, pool and provider filled in, and the control plane signs for it.

4. **Grant access to the account's principal**, which is the subject in the pool:
   `principal://iam.googleapis.com/projects/<n>/locations/global/workloadIdentityPools/<pool>/subject/<subject>`.
   Either let it impersonate a service account that holds the compute roles listed above:

   ```sh
   gcloud iam service-accounts add-iam-policy-binding vms@my-project.iam.gserviceaccount.com \
     --project=my-project \
     --role=roles/iam.workloadIdentityUser \
     --member="principal://iam.googleapis.com/projects/123456789012/locations/global/workloadIdentityPools/my-pool/subject/compute-account:org_acme/gcp/gcp-main"
   ```

   or grant the compute roles to that principal directly (`gcloud projects add-iam-policy-binding` with the same
   `--member`).

5. **Create the account** with `federationAudience` (and `impersonate`, for the service account of step 4):

   ```ts
   await compute.api.providerAccounts.create(
     { token },
     {
       tenantId: 'org_acme',
       provider: 'gcp',
       name: 'gcp-main',
       config: {
         projectId: 'my-project',
         zones: ['us-central1-a'],
         federationAudience:
           '//iam.googleapis.com/projects/123456789012/locations/global/workloadIdentityPools/my-pool/providers/my-provider',
         impersonate: 'vms@my-project.iam.gserviceaccount.com',
       },
     },
   );
   ```

   The audience here starts with `//`, not `https://`. Two accounts cannot name the same `federationAudience`
   (`CONFLICT`): a pool provider belongs to one account, in any tenant.

`create` and `update` check the account before storing it, with no transaction open and a 10 second limit on each
call. They sign probe tokens for a subject of another tenant and for another account of the same tenant, and the
pool provider must refuse both; then they exchange the account's own token, impersonate if asked, and read the
project. Each `INVALID_CONFIG` below carries `details.reason`, and nothing is stored:

| `details.reason`             | Meaning                                                                                                                                | What the tenant does                                                                                                                                                                                                                            |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `federationTrustsAnySubject` | The pool provider accepted a probe (`details.probe` is `stranger` or `sibling`): its condition is broader than this account's subject. | Set the provider's `--attribute-condition` to exactly the `attributeCondition` from `federationSetup` (`gcloud iam workload-identity-pools providers update-oidc`).                                                                             |
| `federationRefused`          | Google STS refused the account's own token (`details.stsError`). The message quotes the condition, `assertion.sub == "<subject>"`.     | Check that the provider's `--issuer-uri` is the `issuer`, that the attribute mapping is `google.subject=assertion.sub`, that the condition matches the subject exactly (so the same `name`), and that `federationAudience` names that provider. |
| `impersonationRefused`       | The federated identity may not impersonate `impersonate`. The message names the principal.                                             | Grant that principal `roles/iam.workloadIdentityUser` on the service account.                                                                                                                                                                   |
| `projectAccess`              | The final identity cannot read the project (`compute.projects.get`), or the project id is wrong, or the Compute Engine API is off.     | Grant it `roles/compute.viewer` and the roles above, check `projectId`, and enable the API (`details.activationUrl` when Google gave one).                                                                                                      |

A throttled or unreachable Google (`RATE_LIMITED`, `UNAVAILABLE`) also stores nothing: retry with the same
`idempotencyKey`. Only a 400, 401 or 403 from Google counts as a refusal, so a malformed or throttled reply can never
pass as "refused". No token is logged. Check the gcloud commands above against your gcloud version.

`tests/provider-gcp.test.ts` runs the conformance cases and the GCE specifics against an in-memory emulator passed as
`fetch`, and `tests/gcp-end-to-end.test.ts` runs the provider and the emulator through vps.
