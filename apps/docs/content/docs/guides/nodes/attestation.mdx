A join token proves that someone with access to your API wanted a machine to join. That is enough for a server
you install by hand, but not for a machine that PXE-boots on its own, a cloud VM, or a server whose certificate
expired over a long weekend. An <Term id="attestor">attestor</Term> answers the question for one kind of
evidence: is this machine allowed to join, and as which node?

Each attestor is a `@better-compute/core` `AttestorVerifier` that runs inside JoinService's join transaction.
`JoinRequest.attestor` names it (empty means `join-token`), `JoinRequest.attestation` carries its evidence, and a
sealed token, when the request has one, is opened and handed over as `evidence.token`. Every refusal reaches the
agent as the same `ACCESS_DENIED`; the reason goes only to the `onRefusal` hook and the `security.join.refused`
event (see [joining](/docs/guides/nodes/joining)).

## The attestors

| Attestor | Phase | Roles | Evidence | Proves | Joins as |
| --- | --- | --- | --- | --- | --- |
| `join-token` | v0.1 | `node`, `site` | a sealed `node` or `site` token | the holder of a live token for this pool or site | a new node, or a reclaim with `allowReclaim` |
| `x509pop` | v0.2 | `node`, `site` | its last certificate chain and a proof by that key | the machine still holds the key of a recent certificate | the same node, in place |
| `provisioned` | v0.2 | `node` | a sealed single-use `provisioned` token and a product UUID claim | the OS a deploy or provider bootstrap installed | the target node re-keyed, or a new node |
| `discovery` | v0.2 | `ramdisk` | a sealed single-use `discovery` token and a signed discovery assertion | the ramdisk the site's boot server just booted | a ramdisk identity of at most 2 hours |
| `cloud-iid` | v0.3 | `node` (configurable) | a provider-signed instance identity | the cloud instance your provider account created | whatever `resolve` answers |
| `tpm` | v0.5 | `node` (configurable) | TPM endorsement and attestation keys, then an activated credential and a quote | the TPM holding that endorsement key | the node bound to that key |

Only `join-token` is built into the server. You add the others, and one with id `join-token` replaces the
built-in:

```ts title="compute.ts"
import { betterCompute, pkiJoinCrypto } from 'better-compute/server';
import {
  discoveryAttestor,
  provisionedAttestor,
  x509popAttestor,
} from 'better-compute/pki';
import {
  discoveryWorkflowNodeResolver,
  provisionedTargetResolver,
} from 'better-compute/provision';

// `bundle`: the PKI bundle `better-compute pki init` wrote, loaded with importPkiBundle(text, { secret }).
export const compute = betterCompute({
  // database, secret, baseURL, iam, modules, …
  pki: {
    nodeCa: bundle.nodeCa,
    join: pkiJoinCrypto({
      trustDomain: bundle.trustDomain,
      nodeCa: bundle.nodeCa,
      signingKey: bundle.joinSigning,
      encryptionKey: bundle.joinEncryption.privateKey,
    }),
  },
  attestors: [
    x509popAttestor(),
    provisionedAttestor({ resolveTarget: provisionedTargetResolver() }),
    discoveryAttestor({
      resolveWorkflowNode: discoveryWorkflowNodeResolver(),
      approval: 'unknown-machines',
    }),
  ],
});
```

The attestors from `@better-compute/pki` also take `onRefusal(refusal)`, called with
`{ attestor, reason, tokenId?, nodeId?, tenantId? }` for your own audit or metrics.

## join-token

The v0.1 attestor, described in [joining](/docs/guides/nodes/joining). It locks the `join_tokens` row, checks
the secret in constant time, revocation, expiry at `compute_now()`, the remaining uses and the role (`node`
tokens admit `node`, `site` tokens admit `site`), and consumes one use. JoinService enforces the token's
`expect` binding and reclaim flag for every token-based attestor, not only this one.

## x509pop

A node's certificate lasts 24 hours. A machine that was powered off or cut off longer than that comes back with
an expired certificate, and renewal refuses expired certificates. `x509pop` lets it re-join as itself: it
presents its last certificate chain and a proof by the certificate's key, bound to its new CSR.

The evidence is UTF-8 JSON:

```json title="JoinRequest.attestation"
{
  "v": 1,
  "nodeId": "node_…",
  "chain": ["<base64url DER leaf>", "<base64url DER issuer>"],
  "clientTime": 1790000000000,
  "sig": "<base64url r‖s>"
}
```

`sig` is an ES256 signature under purpose `x509pop` over the CSR's SHA-256, the node id and the client time, so
neither a Renew proof nor an earlier `x509pop` proof can be replayed as one. The attestor refuses unless:

- the leaf is byte for byte a `node_certs` row of that node, of its current identity generation, and not revoked;
- the node is not `retired`, and the certificate's role is the requested one (`node` or `site`; a lessee's
  `node-tenant` certificate re-joins as `node` and JoinService restores the restriction);
- the certificate expired at most `graceMs` ago (7 days by default);
- `clientTime` is within `windowMs` (60 seconds) of database time, and the proof was not used before
  (`replayCache`, in memory by default, 10,000 entries).

The result names the node, so JoinService reclaims it in place: it raises the identity generation, revokes every
older certificate and keeps the node's state. A revoked certificate never re-joins; neither does one from before
`nodes.revokeIdentity`. Agents build the evidence with `createX509popEvidence` (or `x509popProducer` for
`FakeDaemon`). bcd does not produce this evidence yet: it joins with `join-token` only and answers no attestor
challenge, so a bcd node whose certificate expired offline cannot re-join this way yet.

## provisioned

When Better Compute deploys an operating system, the deploy renders a single-use `provisioned` token into the
machine's user data (the provisioning engine's `userdata.render` step). The installed system joins with it.
The attestor requires:

- a token of role `provisioned` with exactly one use left (`not-single-use` otherwise);
- a product UUID in the machine's claims (`no-product-uuid`);
- a binding to one machine: the token's `expect.productUuid`, or a target the host resolves (`unbound`).

`resolveTarget(tx, token)` answers with the node the token was minted for and its expected product UUID.
`provisionedTargetResolver()` from `@better-compute/provision` finds the running workflow whose `userdata.render`
step minted the token, and reads the product UUID from that node's newest inventory. With a target node, the
join re-keys that node in place and keeps its provisioning state; a UUID that differs is
`product-uuid-mismatch`. Without one, the machine joins as a new node, which is what a provider bootstrap such as
Hetzner Robot's installimage does.

## discovery

During commissioning, a bare-metal server PXE-boots a platform ramdisk before anything is installed on it. The
ramdisk has no identity of its own, so two parties vouch for it: the iPXE script carries a single-use
`discovery` token bound to the MAC, and the site's boot server signs a statement that it just served that MAC.

The evidence is the sealed token plus a serialized `SignedDiscoveryAssertion` (`bettercompute.site.v1`). The
assertion names the site, the vouching site agent's node id, the boot lease epoch it held, the MAC, and
optionally the IP, product UUID and workflow id, with `issued_at` and `not_after`. The attestor checks:

- the token: role `discovery`, one use left, issued for the assertion's site, and its `expect.mac` (when set)
  equal to the asserted MAC;
- the signer: a `site` node of that site, not retired, currently holding the `site:<id>:boot` lease at exactly the
  asserted epoch, so a fenced boot server can no longer vouch; the signature (purpose `discovery-assertion`) must
  verify against its unexpired certificate;
- freshness: the assertion is valid until the earlier of its `not_after` and 15 minutes after `issued_at`
  (`maxAgeMs`);
- the machine: its claimed MACs include the asserted MAC, and its product UUID matches when the assertion names
  one.

Each signed assertion admits one join (`assertion-reused` otherwise), and the token is spent. The resulting
certificate is a `ramdisk` certificate of at most 2 hours (`certTtlSeconds` may shorten it) that allows only the
commissioning command kinds, `discoveryAllowedKinds` by default: `inventory.refresh`, `logs.collect`, `diag.*`,
`disk.wipe`, `deploy.*` and `boot.kexec`, which are exactly the registered kinds whose roles include `ramdisk`
(`tests/pki-attestors.test.ts` checks the two agree). Pass `allowedKinds` to change the list.

| Option | Default | Effect |
| --- | --- | --- |
| `resolveWorkflowNode(tx, workflowId)` | none | A known machine re-commissions as its node (`discoveryWorkflowNodeResolver()` answers for running workflows). Without it every discovery creates a node. |
| `approval` | `'never'` | `'unknown-machines'` defers machines no workflow names; `'always'` defers every one. |
| `hardwareKey(claims)` | none | The trusted hardware key requests are keyed on; without one they key on site and MAC. |
| `pendingTtlSeconds` | 86,400 | How long a pending request waits for a decision. |
| `retryAfterSeconds` | 30 | When the ramdisk retries a deferred join. |

### Both halves in bcd

bcd produces this evidence on both sides. `bcd site` signs one assertion for every iPXE script its boot server
renders, while it holds the boot lease: the site id, its own node id, the lease epoch, the MAC, the IP (from iPXE's
query, else the connection), the product UUID (from iPXE, else the boot entry), the workflow, `issued_at` in server
time, and a `not_after` of at most 15 minutes and never past the boot entry's, signed by its node key under purpose
`discovery-assertion`. It fetches the machine's discovery token with a `SecretRequest` bound to the workflow and puts
both on the ramdisk's kernel command line (`bc.token`, `bc.assertion`). `bcd ramdisk` reads them back, seals the
token to the pinned JoinService key and sends `Join` with attestor `discovery`, role `ramdisk`, the serialized
`SignedDiscoveryAssertion` as the attestation, and its hardware claims (MACs, product UUID). A deferral is retried
with the same CSR. The Go tests check the assertion's fields and signature, and the TypeScript vectors pin the
signing input, but no test yet joins a real `bcd ramdisk` through this attestor. See
[the boot server](/docs/guides/bare-metal/sites#the-boot-server-in-bcd-site) and
[the ramdisk](/docs/daemon/install#the-ramdisk).

## cloud-iid

A cloud VM that your provider account created can prove it with the identity document its cloud signs, so it
needs no token at all. `cloudIidAttestor({ providers, resolve, roles? })` verifies the document with one of its
providers, then asks `resolve(tx, identity, { role, claims })` where the instance joins. `resolve` returns an
attestation result (tenant, pool, site, and `nodeId` for a known machine) or `undefined` to refuse
(`unknown-instance`), for example for an instance in an account you do not manage.

```json title="JoinRequest.attestation"
{ "provider": "gcp", "document": "<identity token JWT>" }
```

| Provider | Verifies | Bound to the CSR |
| --- | --- | --- |
| `gcpInstanceIdentity({ audience, fetch or jwks, projects?, maxAgeMs? })` | A Compute Engine identity token with `format=full`, signed by Google (RS256 or ES256, JWKS cached an hour). `projects` limits the accepted project ids. | Yes: the agent requests audience `cloudIidAudience(audience, sha256(csr))`, that is `<audience>#<base64url hash>`. |
| `awsInstanceIdentity({ certificates, maxAgeMs?, accounts? })` | The EC2 identity document and its `signature`, checked with the region's AWS certificate, which you supply (`'*'` covers regions not listed). `accounts` limits the account ids. | No: accepted only within `maxAgeMs` (30 minutes) of the instance's `pendingTime`. |
| `oidcInstanceIdentity({ id, issuers, jwks, audience, identity })` | Any issuer that signs JWTs into a JWKS; `identity(claims)` maps the claims to account and instance. | Yes, through the audience. |

Identity tokens older than `maxAgeMs` (10 minutes by default for OIDC and GCP) are refused. Whatever the
provider, each (provider, account, instance) admits exactly one join, ever (`instance-reused`): an AWS document
is readable by any process on the VM, and even a bound token must not mint a second node. A known instance that
lost its certificate re-joins with `x509pop`.

## tpm

`tpm` (v0.5) ties a node to its TPM's endorsement key (EK), an identity that survives a reinstall or a disk swap.
It follows the go-attestation enrollment flow as a two-round join.

1. **Challenge.** The agent sends its EK (public area and manufacturer certificate) and an attestation key (AK).
   The attestor checks the EK certificate chains to one of `ekRoots` and that the AK has attestation-key
   attributes, then answers with a `MakeCredential` challenge plus an opaque state sealed under `challengeKey`
   (AES-256-GCM, bound to the CSR, at most 5 minutes). It writes no row, so any `api` replica can finish the join.
2. **Answer.** Only the TPM holding that EK, with that AK loaded, can activate the credential. The agent returns
   the secret and a quote of its PCRs whose `extraData` is `sha256(secret ‖ sha256(csr))`. The attestor checks
   the secret, the quote signature, the nonce, that the PCR values match the quote's digest, and your
   `pcrPolicy`.

It then decides where the machine joins, keyed by the SHA-256 of the EK: the node that key is already bound to
(a reclaim), else your `resolve` allow-list (for example a vendor's delivery manifest), else operator
`enrollment` through [join requests](/docs/guides/nodes/joining). JoinService binds the EK to the node
(`node_bindings`): a later join proving it reclaims that node, and it can never admit another one
(`bound-elsewhere`).

| Option | Meaning |
| --- | --- |
| `challengeKey` | 32 bytes shared by every `api` replica; seals the challenge state. Required. |
| `ekRoots` | Manufacturer EK CA certificates (PEM or DER). |
| `allowUncertifiedEk` | Accept an EK without a certificate (swtpm, labs). Never in production. |
| `pcrSelection` | PCRs the quote must cover; default the SHA-256 bank, PCRs 0 to 7. |
| `pcrPolicy(pcrs)` | Returns a refusal reason, or `undefined` to accept. |
| `resolve(tx, identity, { role })` | Where an unbound EK joins, or `undefined`. |
| `enrollment` | `{ tenantId, siteId, poolId?, pendingTtlSeconds?, retryAfterSeconds? }`: defer unknown EKs for approval. |
| `challengeTtlMs` | Challenge lifetime, at most 5 minutes. |

### bcd with its TPM

`tpmProducer(SoftwareTpm)` is the agent side in TypeScript tests. bcd has its own, `internal/tpm` (f61b32d): a pure-Go
TPM 2.0 client over the kernel resource manager (`/dev/tpmrm0`, Linux only) that derives the default RSA-2048 EK and a
restricted P-256 AK and builds this attestor's `{ ek, ak }` evidence and its round-2 answer (the
`ActivateCredential` secret and a quote with `extraData = sha256(secret || sha256(csr))`), with a software TPM,
`tpmsim`, for tests. Since 8545688 `bcd join --attestor tpm` uses it:

```bash
bcd join --config /etc/bcd/config.toml --attestor tpm
```

- **The TPM is the credential.** No token is read or sent: `BCD_JOIN_TOKEN` is dropped from the environment, and
  `--token-file` with `--attestor tpm` is a usage error. Where the machine joins is the attestor's decision (the
  bound node, `resolve` or `enrollment` above).
- **Which TPM.** A host build opens `/dev/tpmrm0`; a fakehw build keeps a software TPM in
  `<data_dir>/fakehw-tpm.json`, the same EK on every join of that machine.
- **The rounds.** `agent.Join` sends the evidence, answers up to 3 challenge rounds for the same CSR, and waits out
  a pending approval (`enrollment`) before a fresh challenge round. A machine that already joined answers
  `already joined as <node>` without touching the TPM.
- **The install script.** [`daemon install-script --attestor tpm`](/docs/daemon/install#generate-the-script)
  (a006d9f) writes a script that reads no token, fails early without `/dev/tpmrm0`, and runs
  `bcd join --config /etc/bcd/config.toml --attestor tpm < /dev/null` before (re)starting the units, so the same
  script installs and upgrades.

The node key is still a file under the data directory, not a TPM key. Since 965c14d `internal/tpm` has the pieces
for one, not yet used by `bcd join` or the session: `NodeKey`, an unrestricted, non-exportable P-256 signing key
derived as a primary of the owner hierarchy from a 32-byte per-key unique (nothing is stored in the TPM; anyone
with owner auth, root on the node, can derive and use it too), usable as a Go `crypto.Signer` for CSRs, TLS and node
statements, and `CertifyNodeKey`, which has the AK certify that key (`TPM2_Certify`) over qualifying data.

What is tested, and with what TPM:

| Test | TPM | What it proves |
| --- | --- | --- |
| `TestTSContract` (`daemon/internal/tpm`) | `tpmsim` fixture, with a manufacturer EK certificate in NV (b973e05) | bcd's round-1 evidence is still byte for byte the fixture's, including the EK certificate bcd reads from NV index `0x01C00002` (`tpm.EKCertIndex`) and sends as `ekCert`, and the challenge `tpmAttestor` made for it activates and quotes through bcd's client (TypeScript to Go) |

| `tests/e2e/bcd-tpm.test.ts` (`BCD_E2E=1`, WSL or Linux; db9bd46) | `tpmsim` in a fakehw bcd | a real `bcd join --attestor tpm` with no token against the dev stack's JoinService: two rounds, the SHA-256 PCR bank 0 to 7 reaching `resolve`, the node in the resolved pool and bound to `sha256(EK)` in `node_bindings`; with its identity removed (a reinstall) the same TPM joins as the same node; `bcd node` on that identity is adopted |

`scripts/daemon-tpm-fixture.mjs` regenerates the fixtures in `daemon/internal/tpm/testdata` after a deliberate change
of either side, so a format change fails a test rather than a machine's join. Since b973e05 the contract runs the
attestor as against a real TPM: `ek-root.der` is a test manufacturer root and `ek-cert.der` the EK certificate it
issued for the sim's EK (made once by the Go test, and kept with `sim.json` when the fixtures are regenerated), and
the attestor verifies that chain through `ekRoots`. The dev-stack e2e (`tests/e2e/bcd-tpm.test.ts`) still uses
`allowUncertifiedEk`, since the software TPM there carries no manufacturer certificate. Every test uses a software TPM: no test
has run against a hardware TPM, a real manufacturer's EK certificate or a real `/dev/tpmrm0`.

## Single-use evidence

Tokens are not the only thing that must not be used twice. `cloud-iid` and `discovery` record what they
accepted in `attestation_uses (attestor, subject, expires_at)` inside the join transaction:

| Attestor | Subject | Kept until |
| --- | --- | --- |
| `cloud-iid` | SHA-256 of provider, account and instance | forever |
| `discovery` | SHA-256 of the signed assertion body | the assertion's expiry |

A second join with the same subject is refused. `pruneAttestationUses(tx, { batch? })` from
`@better-compute/postgres` deletes expired rows, 5,000 per call by default; see
[retention](/docs/operations/retention). Single-use tokens (`provisioned`, `discovery`) must have exactly one
use left, so a token minted for several machines is never accepted as a machine credential.

## Two-round joins

Some attestors cannot decide in one request: `tpm` must challenge the TPM, and `discovery` or `tpm` may wait for
an operator. Such an attestor returns an `AttestationDeferral` instead of a result:

```ts
interface AttestationDeferral {
  deferred: 'approval' | 'challenge';
  requestId?: string; // approval: the join request
  retryAfterSeconds?: number; // approval: default 30
  challenge?: Uint8Array; // challenge: attestor-specific bytes
  notAfter?: Date; // challenge: answers after this are refused
}
```

JoinService then commits the transaction (so the attestor's own rows, such as a pending join request, persist),
issues nothing and spends nothing, and answers with a signed `JoinResponseBody` whose `deferral` holds either
`JoinPending{ request_id, retry_after_seconds }` or `JoinChallenge{ attestor, payload, not_after }`. The node id
and chain are empty, and `csr_sha256` still binds the answer to the request. The agent re-sends `Join` with the
**same CSR**: after the wait, or with its answer to the challenge in `attestation`. Attestors therefore consume
tokens and record uses only on the final round.

On the agent side, `openJoinResponse` reads a response as joined, pending or challenge, and `verifyJoinResponse`
refuses a deferral. `runAgentJoin` in `@better-compute/testing` is the reference retry loop.

## Requiring an attestor

By default a pool takes a machine whichever attestor admitted it. Since 1516728 a pool can require hardware
attestation with `policy.joinAttestors`, the ids of the attestors that may admit a machine into it:

```ts title="tpm-pool.ts"
const pool = await client.pools.get({ tenantId: 'root', poolId: 'pool_01k…' });
await client.pools.update({
  tenantId: 'root',
  poolId: pool.id,
  // The policy is replaced as a whole, so keep the rest of it.
  policy: { ...pool.policy, joinAttestors: ['tpm'] }, // or ['tpm', 'x509pop'], or ['join-token', 'tpm'] to keep tokens
});
```

- **Where it is checked.** JoinService checks it in the transaction that resolves the pool, before any reclaim or
  insert. A join or a reclaim admitted by an attestor that is not listed is refused with `ACCESS_DENIED`, reason
  `pool-attestor`. A token join is `join-token`, so a pool that lists only `tpm` refuses tokens, and a token reclaim
  of a TPM-bound machine (`allowReclaim` with the same trusted hardware key) is refused while its TPM still reclaims
  it.
- **Who sees the refusal.** The attestor has already verified the machine, so the refusal is attributed to the pool's
  owner: `security.join.refused` with the attestor and reason `join:pool-attestor`, and the token or node id when
  known.
- **Validation.** `pools.create` and `pools.update` refuse (`INVALID_INPUT`) a value that is not an array of 1 to 16
  ids of attestors this control plane runs: `join-token` and every attestor registered in `attestors` or by a module
  or plugin.
- **Moving nodes.** No API moves a node between pools. A node gets its pool at join, where the check runs, or at
  `metal.enroll`, whose machine gets its identity only through JoinService.

Tested by `tests/server-join-pool-attestors.test.ts`.

## Choosing an attestor

| Situation | Use |
| --- | --- |
| A server you install by hand or with configuration management | `join-token`, with `expect` when the firmware reports placeholder identifiers |
| A node whose certificate expired while it was offline | `x509pop` |
| The OS a Better Compute deploy or a provider bootstrap installed | `provisioned` |
| A ramdisk during bare-metal commissioning | `discovery`, with `approval` if unexpected machines should wait for a person |
| A VM your provider account created | `cloud-iid` |
| Hardware identity that must survive reinstalls, on TPM 2.0 machines | `tpm` (v0.5), with `bcd join --attestor tpm`; add `policy.joinAttestors: ['tpm']` to refuse every other way in |

To write your own attestor, see [attestors](/docs/extending/attestors).
