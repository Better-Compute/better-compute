## Setup

### init

Write a starter configuration file

```sh
better-compute init [--config better-compute.config.ts]
```

init writes a starter better-compute.config.ts (or the JavaScript form when --config names a .mjs or .js file): a configuration factory that uses PGlite in a local .better-compute-pglite directory for development and PostgreSQL when BETTER_COMPUTE_DATABASE_URL is set, reads the secret and base URL from the environment, shows where better-iam plugs in, and exports an empty list of project commands. It never overwrites an existing file.

| Flag            | Description                                               | Default                    | Environment |
| --------------- | --------------------------------------------------------- | -------------------------- | ----------- |
| `--config PATH` | Where to write the configuration (.ts, .mts, .js or .mjs) | `better-compute.config.ts` |             |

```sh
better-compute init
better-compute init --config better-compute.config.mjs
```

### migrate

Create or upgrade the database schema and apply module migrations

```sh
better-compute migrate [--config PATH]
```

migrate runs compute.initialize(): it checks every method's IAM action against the merged catalog and the normative method table (INVALID_CONFIG on a mismatch), then creates or upgrades the compute schema and applies every module's and plugin's migrations. Run it on every deploy before the application starts; it is idempotent.

| Flag            | Description                                                                      | Default | Environment             |
| --------------- | -------------------------------------------------------------------------------- | ------- | ----------------------- |
| `--config PATH` | Configuration module; default: the nearest better-compute.config.{mjs,js,ts,mts} |         | `BETTER_COMPUTE_CONFIG` |

```sh
better-compute migrate
BETTER_COMPUTE_DATABASE_URL=pglite:./data better-compute migrate
```

### serve

Run the API and the workers in this process

```sh
better-compute serve [--host HOST] [--port PORT] [--roles ROLES] [--no-migrate] [--pki PATH] [--config PATH]
```

serve loads the configuration, migrates (skip with --no-migrate once a deploy step runs better-compute migrate), starts the worker roles (controllers: reconcilers and the command sweeper; scheduler; sinks: outbox dispatch; iam: IAM jobs) under their leases, and serves the API with compute.nodeHandler on --host:--port. Run several processes against one database: leases and shard ownership keep each job single-writer. --roles api serves the API only; --roles controllers,sinks runs a worker with no listener; --roles gateway runs the daemon gateway over mTLS from the configuration's host.gateway (all includes it when configured), with the report hooks of the built-in modules and tunnels when the deployment issues exec tickets. Beside the API the listener answers /healthz, /readyz, /.well-known/better-compute (with --pki, the join keys bcd may fall back to) and the host export's own routes (for example GET /watch and GET /metrics). SIGINT or SIGTERM drains the gateway first, then stops the listener and the workers, releasing their leases.

| Flag            | Description                                                                                            | Default                    | Environment             |
| --------------- | ------------------------------------------------------------------------------------------------------ | -------------------------- | ----------------------- |
| `--host HOST`   | The address to listen on                                                                               | `0.0.0.0`                  | `HOST`                  |
| `--port PORT`   | The port to listen on (0 picks a free one)                                                             | `3000`                     | `PORT`                  |
| `--roles ROLES` | all, or a comma list of api, gateway and controllers, scheduler, sinks, iam                            | `all`                      | `BETTER_COMPUTE_ROLES`  |
| `--no-migrate`  | Do not run migrations first                                                                            |                            |                         |
| `--pki PATH`    | Publish the join keys of this PKI bundle at /.well-known/better-compute (the bcd fallback to its pins) | `.better-compute/pki.json` | `BETTER_COMPUTE_PKI`    |
| `--config PATH` | Configuration module; default: the nearest better-compute.config.{mjs,js,ts,mts}                       |                            | `BETTER_COMPUTE_CONFIG` |

```sh
better-compute serve
better-compute serve --roles api --port 8080
better-compute serve --roles controllers,sinks,iam --no-migrate
better-compute serve --roles gateway,controllers
```

### dev

Run a local development server with no setup

```sh
better-compute dev [--host HOST] [--port PORT] [--data DIR] [--memory] [--sim N] [--sim-variant VARIANT] [--config PATH]
```

dev runs the API and every worker role on 127.0.0.1. With a configuration file (or BETTER_COMPUTE_DATABASE_URL) it uses that deployment; without one it keeps PGlite in --data (default .better-compute/dev-db; --memory for a throwaway database) and a generated deployment secret in .better-compute/dev-secret (owner-only), so repeated runs keep their data. It always migrates first. Without IAM configured only public methods answer; see better-compute iam setup. --sim N adds a gateway on loopback cleartext HTTP/2 (sessions authenticate by a header; local development only) and N simulated machines that join the way bcd does: a join token sealed to throwaway dev JoinService keys, the Join RPC, a Session stream, diag.nvml acceptance and adoption by the real runtime. Without configured IAM, --sim starts an embedded in-memory better-iam and prints its root token; with configured IAM it acts as BETTER_COMPUTE_TOKEN, which must be a root administrator.

### sim

Run the deterministic fleet simulator and check its invariants

```sh
better-compute sim [--seed SEED] [--nodes N] [--duration DURATION] [--settle DURATION] [--chaos LEVEL] [--log PATH]
```

sim runs --nodes FakeDaemons on fake hardware against the in-memory gateway stub for --duration of simulated time, with a steady workload (diagnostics, inventory refreshes, log collection, reboots, GPU bookings) and --chaos faults (none, light, heavy: crashes, reboots, journal loss, partitions, half-open links, resets, stalls, gateway kills), then quiesces for --settle and checks invariants I1 (no double booking), I2 (at-most-once side effects), I5 (every command terminal) and I8 (usage). Nothing reads the wall clock: the same --seed prints the same digest. It exits SIM_INVARIANT_VIOLATED when an invariant fails. Needs @better-compute/testing.

### api

```sh
better-compute api GROUP.METHOD [key=value ...] [--data JSON|@FILE|-] [--list] [--config PATH] [--url URL]
```

api calls any method of the HTTP API (the same routes, envelope and permission checks as POST {basePath}/{group}/{method}) as BETTER_COMPUTE_TOKEN, in process through the configuration or against --url, and prints the result. Plugin methods are plugins.ID.GROUP.METHOD. api --list [GROUP] lists every route with whether it needs a token and the IAM action it is decided on.

### reserve

Reserve GPUs from a pool (reservations.create)

```sh
better-compute reserve --tenant ID --pool ID --gpus N --for DURATION [--selector EXPR] [--model MODEL] [--product PRODUCT] [--nvlink] [--project ID] [--start TIME] [--lease SECONDS] [--key KEY] [--wait SECONDS] [--config PATH] [--url URL]
```

reserve asks for --gpus whole GPUs from --pool for --for, decided by better-iam as compute:reservations:create on the reservation draft and placed by the pool's placer (PLAN.md §3.4, §10.3). --selector takes the shorthand `gpuProduct in (H100-SXM5-80GB), vramGiB >= 80`; --model and --product add a gpuModel or gpuProduct match. It waits up to --wait seconds for the placement and prints the reservation, whose binding lists the booked GPU UUIDs once active. Every run sends a new idempotency key unless --key is given: repeat the command with the same --key to retry safely.

### fleet plan

Show what applying a FleetConfig document would change (fleet.plan)

```sh
better-compute fleet plan FILE --tenant ID [--prune] [--fail-on-drift] [--calls] [--config PATH] [--url URL]
```

fleet plan diffs the document against the tenant's current objects and prints each change: + create, ~ update (with the fields), - delete (only with --prune), and BLOCKED for changes the platform cannot make (a site's region, a pool's class or site, dangling names). It changes nothing. The printed planHash, passed to fleet apply --plan-hash, applies exactly this plan. With --fail-on-drift it exits FLEET_DRIFTED when anything would change, for drift checks in CI; a blocked plan always exits PLAN_BLOCKED.

### pki init
