## Setup

### init

Write a starter configuration file

```sh
better-compute init [--config better-compute.config.ts]
```

init writes a starter better-compute.config.ts (or the JavaScript form when --config names a .mjs or .js file): a configuration factory that uses PGlite in a local .better-compute-pglite directory for development and PostgreSQL when BETTER_COMPUTE_DATABASE_URL is set, reads the secret and base URL from the environment, shows where better-iam plugs in, and exports an empty list of project commands. It never overwrites an existing file.

| --------------- | --------------------------------------------------------- | -------------------------- | ----------- |
| `--config PATH` | Where to write the configuration (.ts, .mts, .js or .mjs) | `better-compute.config.ts` |             |

```sh
better-compute init

```

### migrate

Create or upgrade the database schema and apply module migrations

```sh
better-compute migrate [--config PATH]
```

migrate runs compute.initialize(): it checks every method's IAM action against the merged catalog and the normative method table (INVALID_CONFIG on a mismatch), then creates or upgrades the compute schema and applies every module's and plugin's migrations. Run it on every deploy before the application starts; it is idempotent.

| Flag            | Description                                                                        | Default | Environment             |
| --------------- | ---------------------------------------------------------------------------------- | ------- | ----------------------- |
| `--config PATH` | Configuration module; default: the nearest better-compute.config.\{mjs,js,ts,mts\} |         | `BETTER_COMPUTE_CONFIG` |

```sh
better-compute migrate
BETTER_COMPUTE_DATABASE_URL=pglite:./data better-compute migrate
```

### doctor

Check the database, schema, clock, method registry and IAM wiring

```sh

It only reads. --strict exits non-zero (DOCTOR_FINDINGS) when any error or warning is found.

### serve

Run the API and the workers in this process

```sh
better-compute serve [--host HOST] [--port PORT] [--roles ROLES] [--no-migrate] [--config PATH]
```

serve loads the configuration, migrates (skip with --no-migrate once a deploy step runs better-compute migrate), starts the worker roles (controllers: reconcilers and the command sweeper; scheduler; sinks: outbox dispatch; iam: IAM jobs) under their leases, and serves the API with compute.nodeHandler on --host:--port. Run several processes against one database: leases and shard ownership keep each job single-writer. --roles api serves the API only; --roles controllers,sinks runs a worker with no listener; --roles gateway runs the daemon gateway over mTLS from the configuration's host.gateway (all includes it when configured), with the report hooks of the built-in modules and tunnels when the deployment issues exec tickets. Beside the API the listener answers /healthz, /readyz, /.well-known/better-compute (the server's document, with JoinService's public keys when pki.join publishes them: the fallback bcd checks against its pins) and the host export's own routes (for example GET /watch and GET /metrics). SIGINT or SIGTERM drains the gateway first, then stops the listener and the workers, releasing their leases.

| Flag            | Description                                                                        | Default   | Environment             |
| --------------- | ---------------------------------------------------------------------------------- | --------- | ----------------------- |
| `--host HOST`   | The address to listen on                                                           | `0.0.0.0` | `HOST`                  |
| `--port PORT`   | The port to listen on (0 picks a free one)                                         | `3000`    | `PORT`                  |
| `--roles ROLES` | all, or a comma list of api, gateway and controllers, scheduler, sinks, iam        | `all`     | `BETTER_COMPUTE_ROLES`  |
| `--no-migrate`  | Do not run migrations first                                                        |           |                         |
| `--config PATH` | Configuration module; default: the nearest better-compute.config.\{mjs,js,ts,mts\} |           | `BETTER_COMPUTE_CONFIG` |

```sh
better-compute serve
better-compute serve --roles api --port 8080
better-compute serve --roles controllers,sinks,iam --no-migrate
better-compute serve --roles gateway,controllers
```

### dev

Run a local development server with no setup

```sh
better-compute dev [--host HOST] [--port PORT] [--data DIR] [--memory] [--sim N] [--sim-variant VARIANT] [--config PATH]
```

dev runs the API and every worker role on 127.0.0.1. With a configuration file (or BETTER_COMPUTE_DATABASE_URL) it uses that deployment; without one it keeps PGlite in --data (default .better-compute/dev-db; --memory for a throwaway database) and a generated deployment secret in .better-compute/dev-secret (owner-only), so repeated runs keep their data. It always migrates first. Without IAM configured only public methods answer; see better-compute iam setup. --sim N adds a gateway on loopback cleartext HTTP/2 (sessions authenticate by a header; local development only) and N simulated machines that join the way bcd does: a join token sealed to throwaway dev JoinService keys, the Join RPC, a Session stream, diag.nvml acceptance and adoption by the real runtime. Without configured IAM, --sim starts an embedded in-memory better-iam and prints its root token; with configured IAM it acts as BETTER_COMPUTE_TOKEN, which must be a root administrator.

### sim

Run the deterministic fleet simulator and check its invariants

```sh
better-compute sim [--seed SEED] [--nodes N] [--duration DURATION] [--settle DURATION] [--chaos LEVEL] [--log PATH]
```

sim runs --nodes FakeDaemons on fake hardware against the in-memory gateway stub for --duration of simulated time, with a steady workload (diagnostics, inventory refreshes, log collection, reboots, GPU bookings) and --chaos faults (none, light, heavy: crashes, reboots, journal loss, partitions, half-open links, resets, stalls, gateway kills), then quiesces for --settle and checks invariants I1 (no double booking), I2 (at-most-once side effects), I5 (no allocation released only because its node disconnected) and I8 (usage). Nothing reads the wall clock: the same --seed prints the same digest. It exits SIM_INVARIANT_VIOLATED when an invariant fails. Needs @better-compute/testing.

### support bundle

```sh
better-compute support bundle [--out PATH] [--pki PATH] [--config PATH]
```

support bundle collects what a support request about the control plane needs: the CLI, Node and platform versions; the configuration's shape (database kind, modules, whether IAM, PKI, tunnels and a notifier are configured; never URLs or values); doctor's findings; applied migrations; gateway and worker heartbeats; work-queue, command and IAM-inbox backlogs; and node counts by state. The file is written owner-only. It only reads.

## API

### api

Call any compute API method as the current token

```sh
better-compute api GROUP.METHOD [key=value ...] [--data JSON|@FILE|-] [--list] [--config PATH] [--url URL]
```

api calls any method of the HTTP API (the same routes, envelope and permission checks as POST \{basePath\}/\{group\}/\{method\}) as BETTER_COMPUTE_TOKEN, in process through the configuration or against --url, and prints the result. Public methods (system.version, system.whoami) need no token; system.whoami reports the token when one is set. Plugin methods are plugins.ID.GROUP.METHOD. api --list [GROUP] lists every route with whether it needs a token and the IAM action it is decided on.

### ssh-cert

Get a break-glass SSH certificate for one node, next to your key

```sh
better-compute ssh-cert [COMMAND...] --tenant ID --node ID [--key PATH] [--account NAME] [--minutes N] [--connect HOST] [--ssh PROGRAM] [--config PATH] [--url URL]
```

ssh-cert asks nodes.issueSshCert for a short-lived OpenSSH user certificate for your own public key (--key, default ~/.ssh/id_ed25519.pub, else id_ecdsa.pub) and writes it beside the key as \<key>-cert.pub, where ssh -i \<key> finds it. The certificate is bound to the node (principal \<account>@\<nodeId>): it opens that node only, as --account (default root), for --minutes (default 15, at most 60, and never past your session). It needs compute:nodes:ssh-root and a session verified with MFA. The private key never leaves your machine. Revoke it early with api nodes.revokeSshCert.

### forward

Forward a local port to a port of a running instance

```sh
better-compute forward --tenant ID --instance ID --port PORT [--local-port PORT] [--bind HOST] [--config PATH] [--url URL]
```

forward listens on --bind (default 127.0.0.1) at --local-port (default: the same as --port; 0 picks a free one) and forwards each connection to --port on the instance through its own tcp tunnel (tunnels.open, compute:instances:exec on the instance), like ssh -L. It runs until Ctrl-C. The tunnels run over the server’s WebSocket, so it needs --url (or BETTER_COMPUTE_URL). A connection is re-authorized like any tunnel: revoking your session or the delegation closes it. Binding anything but loopback lets whoever reaches that address use your access; even on loopback, other users of this machine and web pages open in your browser can reach the port, as with ssh -L. At most 16 connections are forwarded at once, and new ones are refused while the server rate-limits your tunnels.

## Capacity

### reserve

Reserve GPUs from a pool (reservations.create)

```sh
better-compute reserve --tenant ID --pool ID --gpus N --for DURATION [--selector EXPR] [--model MODEL] [--product PRODUCT] [--nvlink] [--project ID] [--start TIME] [--lease SECONDS] [--key KEY] [--wait SECONDS] [--config PATH] [--url URL]
```

reserve asks for --gpus whole GPUs from --pool for --for, decided by better-iam as compute:reservations:create on the reservation draft and placed by the pool's placer (PLAN.md §3.4, §10.3). --selector takes the shorthand `gpuProduct in (H100-SXM5-80GB), vramGiB >= 80`; --model and --product add a gpuModel or gpuProduct match. It waits up to --wait seconds for the placement and prints the reservation, whose binding lists the booked GPU UUIDs once active. Every run sends a new idempotency key unless --key is given: repeat the command with the same --key to retry safely.

### sandbox exec

## IAM

### iam setup

Print the example compute policies and create the root billing meters in better-iam

```sh
better-compute iam setup --audience URL [--gpu-model MODEL] [--regions LIST] [--max-gpus N] [--max-hours N] [--feature FLAG] [--meters] [--iam-url URL] [--iam-base-path PATH] [--root-tenant ID] [--gpu-models LIST]
```

iam setup prints the PLAN.md §12.6 example policies, gpu-user and agent-guardrails, for an organization administrator to apply: compute cannot write organization policies. Creating meters calls better-iam at --iam-url as BETTER_IAM_TOKEN, which must be a root credential, through the optional peer @better-iam/client. It sets no prices: pricing is an operator decision (billing.setPrice).

### release sign

Sign a release manifest over a directory's artifacts

```sh
better-compute release sign DIR --product NAME --version SEMVER --sequence N --key PATH [--cosigners PATHS] [--validity-days DAYS] [--out PATH]
```

release sign hashes every file in DIR (not subdirectories; \*.sha256, manifest.json and signature files are skipped), derives each artifact's platform from goreleaser names (\_linux_amd64.), and writes a manifest signed with --key. --sequence must increase with every release of --product: installers and bcd refuse a manifest whose sequence is below the last one they accepted. List the public halves of keys that will cosign later with --cosigners so their signatures count.

| Flag                   | Description                                                                              | Default | Environment |
| ---------------------- | ---------------------------------------------------------------------------------------- | ------- | ----------- |
| `--product NAME`       | e.g. bcd                                                                                 |         |             |
| `--version SEMVER`     | e.g. 1.4.0                                                                               |         |             |
| `--sequence N`         | The rollback counter: higher than every earlier release                                  |         |             |
| `--key PATH`           | The signing key                                                                          |         |             |
| `--cosigners PATHS`    | Comma-separated .pub.pem files of keys that will cosign                                  |         |             |
| `--validity-days DAYS` | How long installers accept the manifest (default 365)                                    |         |             |
| `--out PATH`           | Where to write the manifest (default DIR/manifest.json)                                  |         |             |
| `--format FORMAT`      | Output as json (indented, default), compact (one line), or table                         |         |             |
| `--query PATH`         | Print only part of the result, e.g. protocol.max or findings[].check (strings print raw) |         |             |
