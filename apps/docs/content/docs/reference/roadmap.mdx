Better Compute is built in phases, each defined in PLAN.md §16 by its deliverables, its acceptance criteria and its
exit tests. A phase closes only when its exit tests are green in CI; the benchmark gates are measured on the
reference hardware in `bench/REFERENCE.md` (a gateway host with 8 vCPU and 32 GiB, PostgreSQL 17 on 16 vCPU and
64 GiB NVMe).

The phases were planned in order, but the work did not stay in order: the TypeScript control plane for every phase
up to v0.5 exists in the repository, and the Go daemon covers the v0.1 node agent, while the daemon's later modes and
the pieces that need a PostgreSQL server or real hardware do not exist yet. So no phase after P0 is formally closed
yet. This page tracks each item as:

- **Done**: in the code, with tests, and listed in the changelog.
- **In progress**: partly there. The note says which part is missing.
- **Not started**: nothing in the repository yet.

<Callout type="warn" title="Three things hold every phase open">
- **The Go daemon is not released, and only its node agent runs end to end.** `bcd join`, `bcd node` and
  `bcd status` work and are tested end to end against a real gateway (`tests/e2e/bcd.test.ts`, the fake-hardware
  build in WSL), including a node console tunnel, and the node agent also converges break-glass SSH (`access`).
  `bcd site` and `bcd ramdisk` are written and covered by Go unit tests only. The `instances` converger, instance
  tunnels and the IMDS run end to end only on fakehw builds (`tests/e2e/bcd-vps.test.ts`); the `libvirt-kvm` and
  `cloud-hypervisor` runtimes of host builds (362317c, 2598f0a) are tested against fake tools only. The release
  pipeline exists but no release has been cut. GPUs are read through `nvidia-smi` (cb987e5) with no go-nvml backend.
  Self-update, the WebSocket fallback and `bcd helper` (self-update included) are done and exercised through the
  TypeScript `FakeDaemon`. `bcd sim` runs many real node agents in one process (fakehw builds only).
  One real host has run a host build of bcd (round 6, 2026-10-04): a WSL 2 workstation with a GeForce RTX 5090.
  `tests/e2e/bcd-host-real.test.ts` (`BCD_E2E_REAL=1`) joins it to a dev stack, adopts it, reads its real inventory
  and GPU, exports the GPU's live metrics over OTLP and answers `bcd status` and `bcd doctor`. That bcd ran as an
  ordinary user without `[helper]`, so it binds no GPUs: no real `/etc/cdi` spec, hold slice, passthrough or MIG has
  run yet. See [running bcd on real hardware](/docs/daemon/real-hardware) and
  [what bcd does today](/docs/daemon#what-bcd-does-today).
- **No PostgreSQL server has run the suites.** Local runs use PGlite (PostgreSQL 18 in WebAssembly). Suites that need
  real concurrency skip unless `BETTER_COMPUTE_POSTGRES_URL` is set, and every benchmark number below is from PGlite
  on a development machine, which the gates do not count.
- **The hardware gates (PLAN.md D15) have not run.** They need one NVIDIA box, a self-hosted KVM runner and the
  reference benchmark machines, and rented A100 or H100 capacity before the v0.5 exit.
</Callout>

## CPU, memory and Kubernetes (v1.1)

PLAN.md §3.8 (a760805) designs the complete node daemon for v1.1: compute books a host's CPUs, memory and huge pages
with its GPUs, the node enforces exactly that, bcd applies the host's configuration, and a reservation can hand its
GPUs to a Kubernetes cluster. The principle stays P1: compute decides who gets what, and the node enforces exactly
that and reports it. Most of it is now in the code, on both sides. Every node-side piece is tested against fakes
only (a fake host, a fake root, a fake kubelet, fake VMMs); none has run on a real machine or cluster.
