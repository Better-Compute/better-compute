Better Compute is built in phases, each defined in PLAN.md §16 by its deliverables, its acceptance criteria and its
exit tests. A phase closes only when its exit tests are green in CI; the benchmark gates are measured on the
reference hardware in `bench/REFERENCE.md` (a gateway host with 8 vCPU and 32 GiB, PostgreSQL 17 on 16 vCPU and
64 GiB NVMe).

The phases were planned in order, but the work did not stay in order: the TypeScript control plane for every phase
up to v0.5 exists in the repository, while the pieces that need a Go toolchain, a PostgreSQL server or real hardware
do not. So no phase after P0 is formally closed yet. This page tracks each item as:

- **Done**: in the code, with tests, and listed in the changelog.
- **In progress**: partly there. The note says which part is missing.
- **Not started**: nothing in the repository yet.

<Callout type="warn" title="Three blockers hold every phase open">
- **The Go daemon is not built.** `bcd` is written in `daemon/` but Go is not installed on the build machine, so
  nothing in it has been compiled, released or run on a server. Everything a daemon does is exercised through the
  TypeScript `FakeDaemon`, which speaks the real protocol. See [the daemon](/docs/daemon).
- **No PostgreSQL server has run the suites.** Local runs use PGlite (PostgreSQL 18 in WebAssembly). Suites that need
  real concurrency skip unless `BETTER_COMPUTE_POSTGRES_URL` is set, and every benchmark number below is from PGlite
  on a development machine, which the gates do not count.
- **The hardware gates (PLAN.md D15) have not run.** They need one NVIDIA box, a self-hosted KVM runner and the
  reference benchmark machines, and rented A100 or H100 capacity before the v0.5 exit.
</Callout>

## Sandboxes

Sandboxes are part of the product beside GPU and CPU capacity. Decision D24 (PLAN.md section 17) was taken on
2026-09-24: build a dedicated sandbox API. The work is being planned, so the items below have no phase yet. What
exists and what does not:

| Item | State | Notes |
| --- | --- | --- |
| Isolated VMs as sandboxes | Done in the control plane (v0.3) | A sandbox is a VPS instance: flavors of vCPU, memory, disk and 0 to 16 GPUs, one IAM decision per create, quota, metering, sealed user data, no platform secrets in the guest, exec, SSH and TCP through tunnels. See [sandboxes](/docs/guides/vps/sandboxes) |
| Provider pools running them | Done | Hetzner Cloud and Proxmox VE |
| Hosted runtimes on your own servers | Not started | `libvirt-kvm` and `cloud-hypervisor` inside bcd (v0.3), which needs Go; a Kata runtime plugin via bcx (v0.5) |
| Agents managing sandboxes over MCP | Done | `create_instance`, `list_instances`, `get_instance`, `start_instance`, `stop_instance` and `delete_instance`. See [MCP](/docs/guides/clients/mcp#the-tools) |
| A dedicated sandbox API | Decided (D24), being planned, not built | The shape: a `sandboxes` group layered on `vps()`, with templates (flavor, image and user data), a time-to-live with auto-delete, snapshots and restore through the runtime driver, warm pools of pre-created stopped instances per template, and the microVM runtime (cloud-hypervisor or Kata via bcx) for untrusted code. It would reuse instances' admission, quota, IPAM, tunnels and IMDS, with no new placement or tenancy path. None of it is in the code yet |

## v1.0: Freeze

Not started. It freezes the API and the protocol, guarantees N-2 version skew, adds an external security review
and SLSA level 3 builds, and publishes to npm with provenance once Better IAM is published. Its acceptance: upgrading
from v0.5 disturbs no running allocation, with no open critical or high findings.
