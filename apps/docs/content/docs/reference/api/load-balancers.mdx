Load balancers on a provider account (DigitalOcean regional and global first). Every call records what the tenant wants and returns at once; the `vps.provider-resources` reconciler converges the provider through `ProviderImpl.loadBalancers`. Reading takes `compute:load-balancers:read`, everything else `compute:load-balancers:manage`, on `provider-load-balancer/{id}`. A load balancer books one `loadBalancers` quota on the pool (no quota row grants none) and bills `vps.load-balancer.hours` from `ready` until deleted.

What a load balancer reaches is computed from the tenant's own rows and sent to the provider as explicit machine ids, never a tag, so it never reaches another tenant's machine. A `regional` one targets the tenant's instances in its pool and region (`targets: { pool: true }`) or named instances of the tenant (`targets: { instanceIds }`); a `global` one targets the tenant's regional load balancers (`targets: { loadBalancerIds }`). A regional load balancer is in one VPC and the provider balances only to machines in it: it lives on one subnet of a tenant network (`subnetId`, or the subnet its named instances share) and reaches only instances on that subnet, or, without one, on the account's default network and reaches only instances on no tenant network. An instance counts once it has a machine and until it is being deleted. Deleting an instance updates its load balancers at once; one that gains a machine is added by the periodic pass, within five minutes.

All 5 methods are served by @better-compute/server 0.3.0.

## create

`POST /api/compute/loadBalancers/create`

Makes a load balancer with its `forwarding` rules (1 to 15; an `https` or `http2` entry names a `certificateId` of the tenant on the same account, or an `https` one passes TLS through with `tlsPassthrough`), an optional `healthCheck`, `stickySessions`, `sourceRanges` and `redirectHttpToHttps`, and (global only) the `domains` it serves. It returns `pending`, booking one `loadBalancers`; no room, or no quota row, is `QUOTA_EXCEEDED`. Another tenant's instance is `ACCESS_DENIED`, another region or account `INVALID_INPUT`, named instances on two subnets (or not on `subnetId`) `INVALID_INPUT`, another tenant's subnet `NOT_FOUND`, another tenant's certificate or load balancer `NOT_FOUND`. Named instances are also decided as `compute:instances:update` on each, with the caller's own credential. The provider is asked once the certificates it names are ready. Publishes `providerLoadBalancer.created`, then `providerLoadBalancer.ready` with its `address`, or `providerLoadBalancer.error`.

- **Kind:** mutation
- **Authorization:** `compute:load-balancers:manage` @ `compute-provider-load-balancer`

- **Phase:** v1.0 (registered)
