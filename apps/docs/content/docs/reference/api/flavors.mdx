Flavors are the named instance shapes of a VPS pool: vCPU, memory, disk and GPU count, plus the provider offer a provider pool creates. The pool's owner manages them, and tenants the pool is offered to can list them. An instance keeps the shape it was admitted with, so changing or deleting a flavor never changes a live instance. See [Flavors](/docs/guides/vps/flavors).

All 4 methods are served by @better-compute/server 0.2.1.

## list

`POST /api/compute/flavors/list`

Returns the pool's flavors that are not archived, sorted by name.

The pool must be owned by or offered to the tenant; otherwise the call is `NOT_FOUND`.

**Estimates.** Each item of a provider pool carries `estimate` when the IAM port can quote (`IamPort.quote`): `{ perHourMicros, currency, lines }`, what one hour of the flavor costs the tenant named in the call.

- **How.** The lines are the meters an instance of the flavor would record per hour (the pool's billing mode, the flavor's meter and the shape's vCPUs, memory and GPUs, as `meterLinesFor` computes them), each priced by IAM with the tenant's effective price, so a negotiated price shows. `lines` are `{ meter, quantity, amountMicros }`; a line IAM has no price for has `amountMicros: null`, and then `perHourMicros` is `null` rather than a partial sum. A pool whose billing mode is `none` has no lines and costs `0`.
- **Absent** when the IAM port has no `quote` (see `billing`), when the pool is not a provider pool (hosted pools record usage differently), or when IAM cannot answer: an estimate never fails the list.
- **Currency** is the deployment currency (`vps({ billing: { currency } })`, default `USD`).
- **Before a create:** `instances.estimate` answers the same estimate for one flavor.
- **Freshness.** Estimates are kept five minutes per tenant and pool, so a changed price shows within five minutes.
- **Assumptions.** The estimate is for an on-demand instance of the flavor: Spot, reservation grants and the instance's disks and addresses are not in it. A flavor whose offer is held by a reservation is priced on the `vm.reserved.*` meters.

## create

`POST /api/compute/flavors/create`

Adds a flavor to a `vps-host` or `provider` pool the tenant owns and returns it at version 1.

- `gpus` defaults to 0. A flavor of a provider pool needs `offerId`, the provider offer it creates; without it the call is `INVALID_INPUT`.
- `placement` (hosted pools only; `INVALID_INPUT` on a provider pool) says where the guest lives on its host, and sandbox templates on the flavor inherit it:
  - `hugepages: '2Mi' | '1Gi'` backs guest memory with hugepages. These are booked from the host's hugepage pools instead of its memory, still charged to quota as `memoryGiB`, and never ballooned.
  - `numaAffine` keeps the vCPUs and memory on one NUMA node: the GPUs' node, or otherwise the least-loaded node with room for the memory.
  - `pinned` gives each vCPU a host CPU that no other pinned guest on the host has.
  - A host that cannot honour `numaAffine` or `pinned` still runs the guest, floating, and the instance carries a `PlacementDegraded` condition with the reason (`NoNumaTopology`, `NoNumaNodeFits`, `GpuNumaUnknown`, `NumaMemoryTooSmall` or `NotEnoughFreeCpus`).
  - Resizing to a flavor with a different `placement` is `UNSUPPORTED`.
- In a pool that overcommits memory (`policy.overcommit.memoryGiB` > 1), every guest gets a virtio balloon so the host can reclaim its free memory. The exceptions are hugepage-backed guests and guests with GPUs, whose memory is pinned. This needs no flavor field.
- `billing.meter` (root only) bills instances of the flavor as one line, `flavor.<name>.hours` at one unit per hour, instead of the composed `vm.vcpu`, `vm.memory`, `vm.gpu` and `vm.instance` lines. It must match `^flavor.[a-z0-9.-]{1,56}.hours$` and be at most 64 characters (a meter key's limit), else `INVALID_INPUT`; any other caller who adds, changes or clears one gets `ACCESS_DENIED` before the decision (resending the stored value is allowed), because the meter is defined on the platform's billing tenant. When the IAM port can define meters (`ensureMeters`), the meter is created on the root tenant once IAM has allowed the call, and `billing.syncMeters` and `billing.meters` include every flavor's meter; a port that cannot accepts the flavor and `billing.meters` reports the meter as `missing`. An instance copies the meter into its own flavor snapshot when it is created, so changing the flavor's meter later never changes how a running or stopped instance is billed; a granted or platform-fee instance ignores it.
- `NOT_FOUND` when the tenant does not own the pool; `INVALID_STATE` when the pool is of another class.
- `CONFLICT` when the pool already has a flavor with that name, archived ones included.

## update

`POST /api/compute/flavors/update`

Replaces the shape of the named flavor and increments its version; an archived flavor becomes active again.

The input is the full shape, as for `create`. An omitted `offerId` keeps the stored one, and so does an omitted `billing`; `billing: {}` clears the meter. Setting, changing or clearing a meter is root only (`ACCESS_DENIED` otherwise, before the decision, and nothing is written); a tenant may resend the stored `billing` unchanged. Instances already admitted keep their old shape; only new instances and resizes use the new one. The call is `NOT_FOUND` when the tenant does not own the pool or the flavor does not exist.

## delete

`POST /api/compute/flavors/delete`

Deletes the named flavor, or archives it when any instance, deleted ones included, still references it; returns `deleted` and `archived` to say which.

An archived flavor disappears from `list` and can no longer be used to create or resize instances. `update` makes it active again. The call is `NOT_FOUND` when the tenant does not own the pool or the flavor does not exist.
