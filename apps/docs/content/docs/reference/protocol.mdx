## commands.proto

Package `bettercompute.agent.v1`, `proto/bettercompute/agent/v1/commands.proto`.

Payloads and results of the built-in v0.1 command kinds (PLAN.md §7.3). A Command carries the request in CommandBody.payload (google.protobuf.Any); the CommandUpdate carries the serialized result in `result`. The kind table (lane and flags) lives in @better-compute/protocol (`commandKinds`) and in the daemon's dispatcher; both must agree.

## session.proto

Package `bettercompute.agent.v1`, `proto/bettercompute/agent/v1/session.proto`.

### BatchApproval

k-of-n operator approval of a batch of destructive commands (PLAN.md §13). The scope is a Merkle
tree (RFC 6962 style, SHA-256) with one leaf per (subject, kind, payload), leaves ordered by their
hash (bytewise ascending, duplicates removed):
leaf = H(0x00 ‖ lp(batch_id) ‖ lp(subject) ‖ lp(kind) ‖ lp(payload_sha256)),
node = H(0x01 ‖ left ‖ right),
with lp(x) = uint32_be(len(x)) ‖ x, and an odd node promoted unchanged to the next level.
The subject is what the command acts on, computed by the executing agent from the signed body:

- kinds a node runs on itself (disk.wipe, deploy.image, node.reboot, gpu.reset, boot.kexec…):
  the command's node_id;
- site-relayed BMC kinds (bmc.\*): "bmc:" + \<the executing site agent's node_id> + "/" +
  BmcOperationRequest.address, the BMC acted on. BMC addresses are site-local (10.0.0.5 exists
  at every site), so the site is part of the subject: an approval for site A never admits a
  command at site B;
- site.httpProxy: "node:" + its target_node_id (global ids).
  payload_sha256 is SHA-256 of the command's payload (CommandBody.payload.value), binding the leaf
  to exactly that operation (image, firmware, power action), or EMPTY for "any payload of this kind"
  where the payload is built later (approvers see unbound leaves flagged). The executing agent
  accepts a proof that walks to the root from either the bound leaf (its payload's digest) or the
  unbound one. Daemons run each leaf at most once per batch.
  Signing purpose "batch-approval", parts [batch_id, scope_root, uint32_be(scope_size),
  int64_be(not_after.seconds) ‖ int32_be(not_after.nanos), trust_domain]. The trust domain (the
  deployment's, JoinResponseBody.trust_domain) is supplied by each verifier from its own config, so
  an approval for staging never admits a command in production, even with shared approver keys.

| Field        | Number | Type                               | Description                                                                           |
| ------------ | ------ | ---------------------------------- | ------------------------------------------------------------------------------------- |
| `batch_id`   | 1      | `string`                           |                                                                                       |
| `scope_root` | 2      | `bytes`                            |                                                                                       |
| `scope_size` | 3      | `uint32`                           | Leaves in the tree: what the operators saw and approved ("reimage 412 nodes").        |
| `not_after`  | 4      | `google.protobuf.Timestamp`        | Server time after which the approval no longer admits a command.                      |
| `signatures` | 5      | repeated [`Signature`](#signature) | Approver key signatures (Signature.kid names an approver key); duplicates count once. |

ACKED, RUNNING, SUCCEEDED, FAILED, REJECTED and CANCELLED in CommandUpdate.

pending → dispatched(epoch) → acked → running → succeeded | failed | rejected
pending → expired (CommandSweeper, past not_after); any non-terminal → cancelled

| Value                       | Number | Description                                                                                 |
| --------------------------- | ------ | ------------------------------------------------------------------------------------------- |
| `COMMAND_STATE_UNSPECIFIED` | 0      |                                                                                             |
| `COMMAND_STATE_PENDING`     | 1      | Stored, not yet sent. A BUSY rejection returns a command here with a backoff.               |
| `COMMAND_STATE_DISPATCHED`  | 2      | Sent on the session with the given epoch.                                                   |
| `COMMAND_STATE_ACKED`       | 3      | The daemon journaled it as `accepted` (fsynced before any side effect).                     |
| `COMMAND_STATE_RUNNING`     | 4      | The side effect has started.                                                                |
| `COMMAND_STATE_SUCCEEDED`   | 5      |                                                                                             |
| `COMMAND_STATE_FAILED`      | 6      | Terminal failure; CommandUpdate.error says why (e.g. "interrupted").                        |
| `COMMAND_STATE_REJECTED`    | 7      | Refused before any side effect; CommandUpdate.reject_reason says why.                       |
| `COMMAND_STATE_EXPIRED`     | 8      | Never delivered before not_after (control plane only).                                      |
| `COMMAND_STATE_CANCELLED`   | 9      | Stopped by Cancel between actions. A completed side effect is reported as its real outcome. |

### CommandRejectReason

Why a daemon refused a command before any side effect (PLAN.md §6 "Checks before accepting").

| Value                                    | Number | Description                                                                                                                                                                                |
| ---------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `COMMAND_REJECT_REASON_UNSPECIFIED`      | 0      |                                                                                                                                                                                            |
| `COMMAND_REJECT_REASON_UNSUPPORTED`      | 1      | Unknown kind, or a kind this agent role may not run.                                                                                                                                       |
| `COMMAND_REJECT_REASON_BAD_SIGNATURE`    | 2      | Missing, unknown-kid or invalid signature on a kind that requires one (destructive, v0.2).                                                                                                 |
| `COMMAND_REJECT_REASON_EXPIRED`          | 3      | Past not_after (server time, via the Welcome offset).                                                                                                                                      |
| `COMMAND_REJECT_REASON_STALE_GENERATION` | 4      | min_generation still not applied at not_after.                                                                                                                                             |
| `COMMAND_REJECT_REASON_BUSY`             | 5      | No free credit on the command's lane. NOT terminal: the control plane puts the command back to pending with not_before = compute_now() + backoff (1 s → 30 s).                             |
| `COMMAND_REJECT_REASON_BATCH_UNAPPROVED` | 6      | (v1.0) A destructive command with a batch_id but no valid BatchApproval covering it (too few distinct approver signatures, expired, or an inclusion proof that does not reach scope_root). |
| `COMMAND_REJECT_REASON_UNBATCHED_LIMIT`  | 7      | (v1.0) Over TrustBundle.unbatched_destructive_per_hour.                                                                                                                                    |
