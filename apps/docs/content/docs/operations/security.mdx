Better Compute runs commands as root on your machines, so its security model starts from one question: who can make
a machine do something? The answer is meant to be only the control plane, only after Better IAM allowed the call,
and only in a form the machine can check itself. This page summarizes the model from the security section of PLAN.md, says which parts
are built, and ends with a hardening checklist.

## Trust boundaries

| Boundary | Protected by |
| --- | --- |
| Caller to api | TLS at your load balancer; Better IAM authenticates every caller and decides every call |
| api to Better IAM | In-process (embedded) through the IAM bridge |
| api and workers to gateway | Mutual TLS from the internal CA |
| Gateway to daemon | Mutual TLS from the machine PKI: the node CA for clients, the serving CA for gateways |
| Site agent to BMC | The management VLAN, reachable only from site agents |
| Tenant to tenant | Tenant pre-checks, SQL tenant scoping, the authorization projection |
| Tenant-controlled node to platform | A `node-tenant` certificate that gets no secrets and no destructive platform commands |

## Threat model

| Threat | Mitigation | State |
| --- | --- | --- |
| Cross-tenant access, forged attributes | Tenant pre-check before any database access; SQL tenant scoping; idempotency keys scoped to tenant and identity; attributes only from compute's own projection | Built |
| Stolen join token | Short TTL, `maxUses` (default 1), `expect` binding; tokens stored hashed, revocable, and sealed to JoinService in transit, bound to the CSR | Built |
| Compromised node | `nodeId` only from the certificate's SAN; 24 h certificates with pushed revocation; secrets bound to current work; reports only about its own allocations; its attested results speak only for itself | Built |
| Cloned node identity | A certificate alternating between two machines more than 3 times in 10 minutes is revoked (duplicate-identity quarantine) | Built in the gateway |
| Compromised gateway | Holds no key in its code; commands and NodeSpecs signed; Renew and `JoinResponse` verified end to end; secrets as JWE; results and `AllocationBound` reports signed by the node. It can delay, drop or read frames, not forge intent, identity, results, bindings or secrets | Built, with the [process caveat](#gateway-processes) |
| Compromised api or worker | Admissions still need IAM decisions; worker keys last 24 h; tickets are audited; fleet-wide destructive batches need k-of-n operator approval checked on the machine (the [destructive-batch quorum](/docs/operations/pki#the-destructive-batch-quorum-v10)) | Built except the quorum, which is v1.0 and partial: bcd and the FakeDaemon enforce it and the server stores, approves and holds batches, but the gateway does not attach approvals yet and nothing built in creates batches |
| Compromised driver plugin | Pinned by SHA-256 and executed from the file that was hashed; run under its own unprivileged uid with `no_new_privs`, a seccomp filter (no namespaces, mounts or `io_uring`) and optional cgroup limits; only plugins named `privileged` run as root | Built in bcd (Linux) |
| Replay | Command-id journal, `not_after`, epoch fencing, a server time mark against rewound `Welcome`s, ticket `jti` sets, a Renew replay cache | Built in the control plane, the FakeDaemon and `bcd` (bcd keeps its ticket `jti` set in its journal, so a restart does not forget a spent ticket) |
| Agent overspend | Delegation scope, confirmations, per-agent quotas, budgets, `agents.suspendAll` | Through Better IAM |
| PXE and DHCP spoofing | One lease-holding boot server per site, isolated VLANs, signed images | Partly built (v0.2) |
| Cross-tenant residue on bare metal | BMC-driven teardown: attested erase, DCGM, a firmware baseline check, a new identity generation | Built in `metal` (v0.2, v0.5) |

<Callout type="warn" title="What the real daemon checks today">
  `bcd` is built and tested but not released. It implements the journal, the pinned join and TLS, `JoinResponse`
  verification, signed commands and specs (once its trust bundle holds command-signing roots), node-signed attested
  results and allocation reports, the server time mark (a `Welcome` never moves its working clock back),
  exec-ticket re-verification before it opens a tunnel (a ticket that names an instance is dialed to that
  instance's own address, never the host's), the SSH
  `access` section (node-bound principals and a KRL; a spec whose CA keys or principals could inject an sshd line is
  refused whole, signed or not), and node-signed `SecretRequest` and `WorkloadTokenRequest` answered to a one-time
  key (the site agent sends them for BMC credentials and discovery tokens, the ramdisk and VPS hosts for user data,
  the metadata service for workload tokens). The site
  agent's boot server answers PXE only for prepared machines while it holds the boot lease. Driver plugins run
  sandboxed (below), and each `bmc.*` kind admits only its own BMC operations, so an unsigned `bmc.query` cannot carry
  a power or RAID change. With approver keys in its trust bundle it enforces the destructive-batch quorum. Its node key is a 0600
  file, not a TPM key, and it has no privilege-separated helper yet. See
  [the daemon](/docs/daemon#what-bcd-does-today).
</Callout>

## Gateway processes

The gateway package holds no CA, signing or encryption key: it relays `Join`, `Renew`, `SecretRequest` and
`WorkloadTokenRequest` to `gatewayServices` and returns the answers verbatim. The design puts those services in the api process behind
internal mutual TLS.

In this release, `serve --roles gateway` builds `compute.gatewayServices` in the gateway's own process from the
shared configuration, so that process loads the PKI bundle and the deployment secret like any other. Treat gateway
hosts with the same care as api hosts until the services move out. `createGateway({ services })` takes any
implementation of `GatewayServices`, so a remote implementation can replace the in-process one without changing the
gateway.

## Controls

### Mutual TLS, failing closed

- Daemons connect to gateways over mutual TLS. `certificateAuthenticate` checks the chain against the node CA, the
  SPIFFE trust domain, revocation, role and expiry. `Join` alone accepts a client without a certificate; `Renew`,
  `Session` and `Tunnel` require one.
- The gateway role refuses to start without node-CA roots and a trust domain (`INVALID_CONFIG`). `serveGateway`
  refuses without `nodeRoots` or an explicit `authenticate`: there is no weaker default.
- `unsafeSanOnlyAuthenticate` and `insecure: true` (cleartext h2c) exist for tests only. `better-compute dev --sim`
  runs its gateway on loopback h2c with header authentication, for local development only.
- The api reaches gateways' internal control APIs (pokes, tunnels, revocations, closing an agent's streams) over
  mutual TLS from the internal CA. The client side is configured in `notifier: gatewayNotifier({ sql, tls })` and
  `host.tunnels.control.tls`.

### Allowlisted command kinds

Each certificate role accepts only its own command kinds. A certificate can be narrowed further with
`node_certs.allowed_kinds`, read at `Hello`: any other kind is cancelled `kind-not-allowed`, including in-flight
ones after a restricted re-join. A ramdisk admitted through discovery gets a certificate of at most 2 h limited to
the commissioning kinds. A `node-tenant` certificate gets no secrets, and destructive kinds sent to it are
cancelled `tenant-controlled`.

### Duplicate identities

A second live `Hello` for a node from another boot wins the session and publishes `security.node.duplicate-session`
(with both boot ids and the running count). A certificate that keeps alternating between two machines, the sign of a
cloned key, is quarantined once it does so more than 3 times within 10 minutes: its serial is revoked with reason
`duplicate-identity`, so every gateway's revocation feed drops the other clone too, `security.node.quarantined` is
published, and the `Hello` is refused `UNAUTHENTICATED` after the revocation commits. Re-join the real machine with a
new token. A session that already went quiet is superseded without counting. See
[sessions](/docs/daemon/sessions#duplicate-identity).

### Signed commands

With `pki.commandSigning`, every command is signed by a 24 h worker key that the command-signing root certifies,
and so is every NodeSpec generation (v0.4): the NodeSpec controller signs the exact `DesiredStateBody` bytes of each
new generation (purpose `desired-state`) and stores them in `nodes.spec_body` and `nodes.spec_signature`. The gateway
relays those signatures verbatim; it cannot produce them. A daemon requires a signature for the kinds its own table
marks destructive and checks any that is present. For desired state, the FakeDaemon with command-signing roots
requires a signature on every spec by default (`signedSpecs: 'always'`, v0.4), and so does bcd, since an unsigned
spec with a high generation would freeze all later ones; `signedSpecs: 'access'` requires one only on a spec that
changes the `access` section (v0.2). Because `Welcome.server_time` is unsigned, both daemons also refuse a `Welcome`
more than 5 minutes before the highest server time they have seen, so a gateway cannot replay an expired worker's
signed command by rewinding the daemon's clock. See
[PKI](/docs/operations/pki#signed-intent).

A worker key can still sign anything, so a compromised api or worker could wipe the fleet with valid signatures.
PLAN.md §13's v1.0 answer is the destructive-batch quorum: `pki.approvers` pins operator approver keys, held off the
control plane, in the join-key-signed trust bundle, and a destructive command then runs only as part of a batch that
enough of them approved, proven by a Merkle inclusion proof the machine checks itself; unbatched destructive commands
are refused by default. bcd and the FakeDaemon enforce it, the server's `quorum` module stores batches and collects
approvals (`commandBatches.approve`), the command queue holds batched commands until approval, and
`better-compute batch keygen` and `batch sign` are the approvers' tools; but the gateway does not yet attach the
approval to a batched command and no built-in workflow creates batches, so with `pki.approvers` set every
destructive command would be refused `UNBATCHED_LIMIT`. Do not set it on a live deployment yet. See
[the quorum](/docs/operations/pki#the-destructive-batch-quorum-v10).

### Driver plugins on the host

bcx driver plugins run next to bcd, which runs as root, so bcd confines them (`[plugins]` in `config.toml`):

- **What runs is what was pinned.** Each binary is hashed through an open file and, on Linux, executed from that
  file (`/proc/self/fd/3`), never by path again, so swapping the file between the check and the exec runs nothing
  else.
- **Not as root, and not as each other.** When bcd is root, each plugin runs under its own uid and gid (stable per
  name, in systemd's dynamic range), so none can read another's memory, or all as `[plugins] user`; no
  supplementary groups. `user = "root"` is refused: plugins that need root (a Kata runtime) are named in
  `[plugins] privileged` and run without the filter, and bcd logs each one.
- **A narrow kernel surface.** With `[plugins] sandbox` (default on), bcd's `__bcx-exec` shim sets `no_new_privs`
  and installs a seccomp filter on every thread (TSYNC) that refuses kexec, kernel modules, mounts, namespaces
  (`unshare`, `setns`, `clone` with `CLONE_NEW*`; `clone3` answers `ENOSYS`), swap, reboot, `bpf`, `io_uring`,
  `ptrace` and `process_vm_*`, the keyring, `perf_event_open`, `userfaultfd`, `open_by_handle_at`, raw I/O ports,
  clock changes, `acct`, `quotactl`, `lookup_dcookie` and `syslog` with `EPERM`, and kills a call from a foreign ABI.
- **Bounded and reaped.** `[plugins] cgroup` puts each plugin in its own child cgroup with `memory_max` and
  `pids_max`; every plugin has its own process group, dies with bcd and is killed as a group on close.

The install script's systemd unit does not yet grant what the user switch and the cgroup limits need (`CAP_SETUID`,
`CAP_SETGID`, a writable cgroup directory); see [installing bcd](/docs/daemon/install#the-systemd-unit) and
[the plugin sandbox](/docs/extending/drivers#the-plugin-sandbox).

### Attested results

A wipe or diagnostics result counts as attested only when the node signed it: the gateway stores
`CommandUpdate.node_sig`, and metal verifies it against `node_certs`. A revoked certificate is refused; an expired
one is accepted for 7 more days, for results journaled offline. Before this fix a kind's `attested` flag was
trusted, so a gateway could have forged a wipe. A `node-tenant` certificate never attests.

GPU bindings get the same treatment. With `pki.commandSigning`, capacity's `attestedBindings` defaults to
`pkiAllocationBindingCheck()`: a reservation goes `active` only once the node's own signed `AllocationBound`
verifies, the signed CDI devices replace whatever the gateway said, and a rejected report publishes
`reservation.binding-rejected`. A forged re-report of an active binding marks it lost instead of replacing it. The
gateway's report handlers also ignore reports about allocations placed on another node. See
[attested bindings](/docs/guides/capacity/reservations#attested-bindings).

### Sealed secrets

- PostgreSQL holds only `secret://` references. The default store seals values in `sealed_secrets` with
  AES-256-GCM; the authenticated data binds each ciphertext to its reference and tenant.
- `secrets.put` is write-only: the API never reads a value back. Events and audit rows carry the reference and
  version, never the value.
- The broker (`gatewayServices.secret`) releases a value only when the request is signed by the node's current,
  unrevoked, platform certificate, names the session's node, is bound to work that node is doing right now (a live
  command of the step that carries the reference, or a live allocation on it), and uses a fresh request id. The
  answer is a JWE to the request's one-time key, expiring within 5 minutes.
- A hosted VPS instance's user data is released only when its `secret://` reference belongs to the instance's own
  tenant, so one tenant's VM cannot boot with another tenant's secret. Since the guest reads its user data,
  `instances.create` accepts only a secret the tenant wrote with `secrets.put` (a `secret_refs` row; never a
  platform-minted one such as a join token, a BMC credential or another instance's sealed user data) and also
  decides `compute:secrets:manage` on the tenant with the caller's own credential (and on the fleet in the root
  tenant), so `compute:instances:create` alone cannot read a write-only secret. A fleet secret (`secret_refs.scope`
  `fleet`, such as a shared site's BMC credentials in the root tenant) is never user data: `instances.create` refuses
  it with `INVALID_INPUT` even for a holder of fleet `compute:secrets:manage` (aac73a1). Sandbox templates follow the
  same rule.
- `secrets.put` records the scope it was decided on (`secret_refs.scope`, `tenant` or `fleet`), and a tenant-scoped
  put or delete never changes a fleet secret (`INVALID_STATE`).
- Nothing is released for a tenant that is suspended or deleted: after the signature and binding checks, a reference
  whose tenant has a non-active `compute_tenant_states` row is refused (reason `tenant-suspended` or
  `tenant-deleted`, recorded as `security.secret.refused`), so a deleted tenant's instance cannot fetch its user data
  while teardown is still reaching it. It is released again once the tenant is active.
- Commands carry references, never values.

### Workload identity (v0.5)

With `workloadIdentity` configured, a VPS host's metadata service can get a hosted instance's OIDC token. The
broker (`gatewayServices.workloadToken`) mints one only when the request is signed by the node's current platform
certificate of role `node` (never `node-tenant`, ramdisk, site or a kind-restricted certificate) naming the session's
node, for a live instance placed on that node with its live allocation there, in a pool with
`policy.workloadIdentity: true`, for an allowed audience, with a fresh request id and within the instance's rate.
The gateway refuses a tenant-controlled session without asking, since the lessee holds root there. The token is a
JWE to the request's one-time key, lives at most 15 minutes, and its audit row carries only the `jti`. Refusals
publish `security.workload.refused`. On the host, a session token binds each metadata request to one instance and
forwarded requests are refused. Since the metadata service and instance tunnels name an instance by its address, bcd
guards every instance tap with host nftables rules (only the NIC's own MAC, IP addresses and ARP; each guarded
address bound to its own tap so no other bridge port can send from it or claim it; no rogue DHCP server, router
advertisement or foreign neighbour advert), trusts only addresses those loaded rules bind to an instance, rechecks
every 30 seconds that the table was not flushed, and never serves an address two instances claim or a loopback
caller. See [workload identity](/docs/guides/vps/instances#workload-identity).

### Tunnels, tickets and break-glass SSH

- `tunnels.open` decides the caller with Better IAM, then issues a 60 s, single-use exec ticket for one node. The
  gateway and the daemon each verify it again, including its `jti`.
- While a tunnel is open, the caller is re-authorized every 60 s by the ticket's own action; after 2 minutes of IAM
  failures it closes. A ticket with an unexpected action fails closed. Tunnels last at most 12 h. A revoked
  delegation or suspended agent closes its tunnels on every gateway when `host.iam` is configured.
- Break-glass shells use `nodes.issueSshCert`: `compute:nodes:ssh-root` on the node and, by default, an MFA session.
  Certificates last at most 1 h and never beyond the session, name `<account>@<nodeId>`, and grant only
  `permit-pty`. Each issuance is recorded; `nodes.revokeSshCert` puts the serial in the node's key revocation list.
  With `host.iam`, a role deactivation, an identity's offboarding, expiry or deletion, and its session revocations
  revoke its certificates too, and the `tunnels.ssh-certificates-reauthorize` reconciler re-decides every live
  certificate for its issuing session each minute. Only a `false` answer, `NOT_FOUND` or `TENANT_SUSPENDED` revokes.
  When IAM is unreachable, or refuses compute's own credential (a thrown `ACCESS_DENIED` or `UNAUTHENTICATED`), a
  certificate stays valid until it expires, on purpose: break-glass is for outages, and an expired service token
  must not revoke every certificate mid-outage.
- Per identity and per api replica: 10 tunnels a minute and 20 certificates an hour, then `RATE_LIMITED`.
- `ssh-cert --connect HOST` accepts only a host name or an IP address, never something ssh would read as an option.
  `ssh-cert` checks the server's answer before using it: the account must be a Unix account name (it reaches ssh's
  `%r` and `%u`), and the certificate an OpenSSH user certificate for the caller's own key.

See [interactive access](/docs/guides/access).

### Sandboxes (v0.5)

A sandbox is a tenant VM for code you do not trust, often written by an agent. The controls:

- **One way in.** `sandboxes.exec` needs a signed-in session (not an API key), decides `compute:sandboxes:exec` on the
  sandbox, and signs a certificate of at most 15 minutes, never past the session or the sandbox's expiry, for a
  principal that names one instance. It refuses a sandbox that expires within a minute. `tunnels.open` refuses a
  sandbox's instance and a warm one (`sandbox-managed`), so `compute:instances:exec` cannot bypass that decision.
- **Re-decided on the sandbox.** The ticket carries the sandbox (`sbx`); the gateway keeps it and every 60-second
  re-check decides `compute:sandboxes:exec` on the sandbox, never on the instance it drives.
- **Separate CAs.** The sandbox SSH CA is never the break-glass CA: the tunnels module refuses the same key for both
  (`INVALID_CONFIG`), so a sandbox certificate never opens a node.
- **Secrets sealed before storage.** Template `env` values and a `secret://` user data are resolved into user data
  that is sealed through the secret broker before the instance row is written; without a broker such a template is
  `INVALID_CONFIG`.
- **Secrets only the tenant put.** A template's `env` and `secret://` user data must be secrets the tenant wrote with
  `secrets.put`, never fleet-scoped ones, and naming them decides `compute:secrets:manage` (on the fleet too in the root tenant, whose store
  also holds fleet secrets). An update that changes what the guest runs is decided on the template's secrets even
  when it names none, and each new instance re-checks them.
- **Snapshots are the owner's.** A snapshot holds memory and `/etc/sandbox/env`, so it belongs to the sandbox's owner,
  whoever took it, and only that owner can restore it (`NOT_FOUND` for anyone else in the tenant); someone allowed
  to snapshot another user's sandbox cannot boot its memory as their own. A deleted snapshot's object is purged only
  once its upload settled and no live instance restores from it.
- **The CLI treats the guest as hostile.** `sandbox exec` puts `--` before the host, so a generated command is never
  an ssh option, and turns off agent and X11 forwarding, port forwardings, proxies, connection sharing and local
  commands for that connection. CLI output strips control characters from server text (table cells, string results,
  hints) and JSON escapes DEL and the C1 controls.

- **Network policy on the host.** A template's `network` (`private`, `none`) becomes host nftables rules on the
  instance's taps, whatever runs inside; bcd fails closed, stopping an instance whose rules cannot be expressed or
  loaded, and vps refuses `private` or `none` on a pool without an IP range. Such instances are placed only on hosts
  labelled `bc.dev/cap.instance.network-policy`, since an older bcd would drop the policy and give full egress.
  `private` spans the pool's whole IPAM subnet, other tenants' instances included on a shared pool.

- **The guest is pinned too.** With `vps({ sandboxExec: { certifyHostKey } })`, each guest presents a host key the
  sandbox CA certified (its private key only in sealed user data), and `sandbox exec` checks it with
  `@cert-authority` and `StrictHostKeyChecking=yes`. `hostCertified` is reported only while the guest's certificate
  (30 days, never renewed) still holds, and a sandbox's lifetime, extensions and memory restores never run past it; a guest without a valid one is refused unless `--accept-host-key` asks for trust on first
  use for that connection. `sandbox exec` also runs ssh with `-F none`, so no user or system `ssh_config` applies.

See [sandboxes](/docs/guides/vps/sandboxes#run-code-inside).

### Tenant isolation

- **Pre-check first.** A caller outside the input's tenant and the root tenant gets `ACCESS_DENIED` before any
  database access or IAM decision, identical to an IAM denial, so there is no existence oracle and outsiders put no
  traffic on another tenant's audit chain.
- **No ambient tenant.** Tenant-scoped repository functions take `tenantId` as a required parameter.
- **Attributes from the projection.** IAM decides on attributes from compute's own
  <Term id="authz-projection">authorization projection</Term>, never from the request.
- **Idempotency keys** are scoped to `(tenant, identity)`, so one tenant cannot replay another's request.
- **Tenant-controlled machines.** Under a dedicated-root lease the node's identity is reissued as `node-tenant`,
  and its inventory becomes advisory.
- **Suspended and deleted tenants.** Once the IAM bridge's `tenant` reaction (`tenantStateHandler`) mirrors a
  tenant's state, the envelope refuses a suspended tenant's mutations and every call of a deleted one with
  `TENANT_SUSPENDED`, root callers exempt, within 5 seconds in every process. A deleted tenant is then torn down:
  its reservations end, offers to it are withdrawn, its pools archived, its workflows aborted, its private images
  soft deleted, its image signers revoked, its bare-metal machines retired (deployed ones wiped first) and its VPS
  instances deleted. The subtree is read from IAM by the `tenancy` reconciler, outside the inbox transaction; while
  IAM is down the read is retried, so a suspension is delayed, never dropped.

See [tenancy](/docs/guides/iam/tenancy).

### Nothing leaks

- Unexpected errors answer `500` with `INTERNAL_ERROR` and a generic message; the detail goes only to `log.error`.
- Join, renew and secret refusals are one generic `ACCESS_DENIED` to the agent; the reason goes to audit
  (`security.join.refused`, `security.secret.refused`), rate-limited per reason.
- A report a node sends about another node becomes `security.node-mismatch` and never reaches a handler, and a
  report about another node's allocation is ignored.
- `/.well-known/better-compute` publishes only public key members; a private JWK member never passes.
- The PKI bundle is sealed at rest, and `pki show` reads only its public half.
- `bcd` reads its join token from `BCD_JOIN_TOKEN` or standard input, never from arguments, and never echoes a
  positional argument.

### The HTTP API

- `POST` requests need `content-type: application/json` and `X-Better-Compute: 1`, else `CSRF_REJECTED`. A plain
  HTML form cannot set that header.
- The IAM session cookie is ignored unless `acceptIamCookie` is set. Even then a cookie request needs an `Origin`
  exactly equal to `baseURL`'s origin: a missing one is `CSRF_REJECTED`, another one `UNTRUSTED_ORIGIN`.
- Bodies are JSON objects of at most 64 KiB (`PAYLOAD_TOO_LARGE`). `TRACE`, `CONNECT` and `TRACK` are refused.
- Every answer carries `cache-control: no-store`, `x-content-type-options: nosniff` and `referrer-policy:
  no-referrer`.
- `X-Request-Id` is echoed only when it matches `^[A-Za-z0-9._:-]{1,128}$`, and IAM sees the same id.

### Rate limits and admission

| Where | Limit |
| --- | --- |
| Gateway handshakes | A token bucket of 200 a second |
| Gateway sessions | `maxStreams` (default 5,000) |
| Pending `Hello`s | 64; more are refused `RESOURCE_EXHAUSTED` so a reconnect storm cannot starve the lease |
| Duplicate `Hello`s | More than 3 from a second machine within 10 minutes quarantine the certificate (`createGateway({ duplicateHellos: { max, windowMs } })`) |
| Tunnels, break-glass certificates | 10 a minute and 20 an hour per identity, per api replica |
| Better IAM | A 429 from IAM becomes `RATE_LIMITED`, with `Retry-After` |
| Security events | Join, secret and workload-token refusal events: 60 a minute per reason by default; the rest are counted as suppressed |
| Workload tokens | 30 a minute per instance by default (`workloadIdentity.perInstancePerMinute`) |

### Tamper-evident audit

Every allowed mutation writes an `audit_events` row with its admission context in the same transaction (composite
methods write one per sub-call). So do node joins and reclaims, secret releases by the broker, and workload tokens
issued to instances (`workload.token.issued`). Commands, workflow steps and exec tickets are not audit rows today;
they are recorded in their own tables and events. With `auditModule`, an hourly job seals new rows into signed,
hash-chained Merkle checkpoints per tenant (RFC 6962), in commit order so a long transaction cannot land behind a
checkpoint. `better-compute audit verify --tenant ID` recomputes the chain and finds an edited, deleted or inserted
row, a removed checkpoint or a foreign signature; `audit prove` writes an inclusion proof a third party checks
offline with `audit check-proof`. The module's self-check warns when rows older than 3 hours are still unsealed. An
audit sink (`sinks.audit`) copies every committed row, in commit order, to a store the database's operators cannot
change; see [sinks](/docs/extending/sinks#audit-sinks).

## Hardening checklist

<Steps>
<Step>

### Secrets and keys

- A deployment secret of at least 32 random characters, from a secret manager, identical in every process.
- `pki init` with the secret (never `--plaintext` outside development) and `--offline-root`, with the root key
  kept off every server.
- The bundle, the secret and the root key backed up, separately.
- A bundle sealed in the former format resealed once: `pki reseal` prints its pins, you compare them with your
  records, then `pki reseal --accept-unauthenticated`. `BETTER_COMPUTE_PKI_ALLOW_UNAUTHENTICATED` unset afterwards;
  the commands that write the bundle refuse it anyway. See [PKI](/docs/operations/pki#pki-reseal).
- Machines installed with their pins, taken from the sealed bundle (`bootstrapPins(bundle)` into provision's user
  data and `vps({ bootstrap: { pins } })`): a host build of `bcd join --server` without `config.toml` requires all
  three and refuses a `/.well-known/better-compute` whose pins differ, since only the control plane's TLS
  certificate vouches for that document. Only fakehw builds join on the document's word (trust on first use). See
  [installing bcd](/docs/daemon/install#joining-from-the-well-known-document).

</Step>
<Step>

### Network

- api behind an L7 load balancer that terminates TLS; `baseURL` is exactly the public origin.
- Gateways behind an L4 load balancer with TLS passthrough. Machines need only outbound 443.
- Internal control APIs (`host.gateway.internal`) reachable only from the control plane, over internal-CA mTLS.
- `GET /metrics` only with a `bearerToken`, and not exposed publicly.
- BMC networks reachable only from site agents.

</Step>
<Step>

### Configuration

- Better IAM wired through the bridge; `doctor` reports `iam.not-configured` otherwise.
- `acceptIamCookie` only for a console on the same origin.
- `pki.commandSigning` set, so commands and NodeSpecs are signed and GPU bindings are attested.
- `tunnels` only if you need interactive access, with the SSH CA's MFA requirement left on.
- `auditModule` registered with the bundle's audit key.

</Step>
<Step>

### Operations

- `better-compute doctor --strict` in CI and after every deploy.
- Gateway serving certificates reissued before their 30 days end, and CA expiry watched (`doctor` warns 30 days
  ahead).
- Revocations checked in practice: `nodes.revokeIdentity` should close the node's session within seconds.
- `audit verify` run on a schedule for the tenants that matter.

</Step>
</Steps>

## Reporting a vulnerability

The repository has no security policy file or dedicated disclosure address yet. Until it does, report a
vulnerability privately to the maintainers rather than in a public issue, and include the version, the
configuration involved, and steps to reproduce.
